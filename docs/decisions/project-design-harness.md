# project-design-harness 設計裁定記録

Skill 2（project-design-harness）の企画を詰める過程で確定した判断を、確定した順に記録する。
Skill 1（project-design-opening）の収集項目と終了条件は、ここで決まる Skill 2 の入力から逆算する
（経緯は [project-design-opening.md](project-design-opening.md) の D2）。

## 前提（元の設計方針から引き継ぐもの）

- Skill 2 は Skill 1 の成果物 `docs/project-definition.md` を入力とし、
  「どの Agent を、どの責務・ツール・権限・検証・状態管理で構成するか」を設計する。
- 成果物の想定は `docs/agent-architecture.md`。
- Skill 3 は Skill 2 で定義された Agent 群を使って、詳細要件・システム設計・実装方法を調査・定義する。
- コンポーネント数と Agent 数を 1 対 1 にしない。Agent 分割は責務・ツール・権限・リスク・検証方法・状態・実行境界から決める。
- ここでいう Agent は「プロダクトを開発する側の Agent」であり、プロダクトに組み込む AI 機能のことではない。

## 裁定

### H1. 設計本体は基盤中立、末尾に Claude Code 対応表を持つ（2026-09-19）

- `agent-architecture.md` 本体は基盤中立の語彙（責務・ツール・権限・検証・状態・承認点）で書く。
- 末尾に「Claude Code での実現」対応表（subagent / settings.json の permissions / hooks / CLAUDE.md / skills）を持つ。
- 退けた案: Claude Code のプリミティブで直接設計を書く専用案／対応付けを一切持たない完全中立案。
- 帰結: 本体と対応表の二層を保守する。Claude Code の仕様変更の影響は対応表の側に閉じ込める。
- 未確認の前提: 「Agent = プロダクトを開発する側の Agent」という解釈は作者に提示済みで、訂正は入っていない。
- 注意: H2 により主成果物が `.claude/` になったため、H1 の「設計本体」の位置づけは H3 で再裁定する。

### H2. Skill 2 は `.claude/` 以下を埋めるスキルで、プロジェクト設計には関わらない（2026-09-19）

- 作者の言葉: 「skill2は、.claude以下を埋めるスキルで、プロジェクト設計にはかかわらないです。」
- Skill 2 の主成果物は対象プロジェクトの `.claude/` 以下（agents / settings / hooks / skills など。具体的な範囲は別途裁定）。
- Skill 2 は機能・要件・システム設計といったプロジェクト設計の判断をしない。それは Skill 1（境界）と Skill 3（詳細）の仕事。
- 「設計書まで／設計書だけ／一気に生成」の3択は、前提（設計書が主成果物）が違っていたため不採用。

### H3. `docs/agent-architecture.md` は根拠記録として残す（2026-09-19）

- 主成果物は `.claude/`。`docs/agent-architecture.md` は「なぜこの Agent 分割・権限・検証にしたか」を書く短い根拠記録。
- 目的は2つ。Skill 2 を再実行するときに前回の判断を引き継ぐこと、Skill 3 が「どの Agent を何に使うか」を読めること。
- H1 の再裁定: 基盤中立の語彙は、この根拠記録の書き方として残す。「設計本体」という位置づけは取り下げ、正本は `.claude/` の実体とする。
- 退けた案: `.claude/` だけを成果物とし、理由は各 agent 定義に書く案。

### H4. 生成範囲はハーネス一式。ルートの CLAUDE.md と .mcp.json も担当する（2026-09-19）

- 生成対象: `.claude/agents`、`.claude/settings.json`（permissions と hooks 登録）、hook スクリプト、
  `.claude/skills`（検証手順やタスク契約などプロセス系のみ）、ルートの `CLAUDE.md`、`.mcp.json`。
- 理由: Project Map（CLAUDE.md）と Tool Gateway（.mcp.json）を欠くとハーネスとして成立しない。
- CLAUDE.md には `project-definition.md` の要約と `docs/` へのポインタだけを書き、設計判断は書かない（H2 と整合）。
- 退けた案: `.claude/` の中だけに限定する案／agents と permissions だけに絞る案。
- 帰結: 既存の CLAUDE.md・.mcp.json・`.claude/` があるリポジトリでの衝突処理を Skill 2 に作り込む必要がある（別途裁定）。

### H5. 調査・設計エージェントと本実装エージェントの両方を Skill 2 で作る（2026-09-19）

- 作者の言葉: 「今後、設計書ベースで変更、実装修正もするので調査・設計エージェントも、本実装のためのエージェントも両方このスキルで作成する」
- 運用の前提は設計書駆動。初期開発のあとも、変更や実装修正は設計書の更新から始める。
  したがって調査・設計エージェントは Skill 3 のための使い捨てではなく、常設のハーネスの一部。
- 退けた案: 実装フェーズ用だけを作り、Skill 3 は素の Claude Code で行う案。
- 未裁定: 1回の実行で両方を作るのか、Skill 3 の後に再実行して実装用を足すのか。
  作者の回答は「両方このスキルで作成する」で、実行回数には触れていない。技術粒度の裁定（H6）と合わせて確定させる。

### H6. Skill 2 は「ツールチェーンが決まる粒度」の技術情報を入力に要求し、1回の実行で動くハーネスを出す（2026-09-19）

- Skill 2 が入力として要求する技術情報: 言語、ランタイム、パッケージマネージャ、主要フレームワーク、DB 種別、デプロイ先種別。
- テストランナー・linter・ORM・UI ライブラリなどは Skill 3 で決まる。Skill 2 はそれらに依存しない。
- 検証の配線: 「プロジェクトが verify 相当の単一コマンドを提供する」という取り決めをハーネス側が定め、
  hooks と検証手順はそのコマンドを呼ぶ。中身（何のテストを走らせるか）は Skill 3 と実装が埋める。
- H5 の未裁定を解消: 初回の1回の実行で、調査・設計用と本実装用の両方を生成する。流れは 1→2→3→開発 の直線。
- 退けた案: 境界レベルに留めてコマンド名を穴のまま残す案／フルスタックまで Skill 1 で確定させる案。
- Skill 1 への逆算: [project-design-opening.md](project-design-opening.md) の D3。

### H8. ハーネスの重さはユーザーがプリセットから選ぶ（2026-09-19）

- 背景: 元記事は 15・16・19 章で「最小のハーネスから始め、複雑さは観測された失敗で獲得せよ」と述べる。
  Skill 2 は失敗を観測する前に設計するので、どの重さで作るかを決める仕組みが要る。
- 裁定: light / standard / heavy のようなプリセットを用意し、実行時にユーザーが選ぶ。
- 退けた案: 最小を既定にしてリスクから自動で足す案（提示時の推奨）／常にフル構成で生成する案。
- 提示済みの代償: ユーザーにハーネス設計寄りの判断を1つ求めることになる。リスクが高いのに軽いプリセットが
  選ばれる事故は、この裁定だけでは防げない。下限の扱いは H9 で裁定する。
- 未裁定: プリセットの数と名前、各プリセットが 8 区分のどこをどう変えるか。

### H9. 推奨プリセットを提示し、Policy の下限はどのプリセットでも外さない（2026-09-19）

- Skill 2 は `project-definition.md` のリスク情報から推奨プリセットを理由つきで提示し、ユーザーが選ぶ。
- どのプリセットでも、外部作用と不可逆操作に対する承認ゲートと禁止ルール（Policy）は必ず生成する。
- プリセットが変えるのは Agent の数、検証の厚み、状態管理、観測の量。Policy の下限はプリセットの対象外。
- 根拠: 元記事 9 章「ポリシーは推論の外に置く。結果が重いほどゲートを固くする」。
- 退けた案: 推奨は出すが下限を持たない案／推奨も下限も持たない案。
- Skill 1 への逆算: リスク情報の収集が必須になる。[project-design-opening.md](project-design-opening.md) の D4。

### H10. プリセットは元記事の6レベルをそのまま見せ、どこまで入れるかを選ばせる（2026-09-19）

- H8 の「light / standard / heavy」は取り下げ、段階は元記事 16 章の6レベルの累積とする。
  1. 境界のあるタスク（目的・スコープ・制約・受け入れ条件）
  2. 読める環境（プロジェクトマップ・コマンド・ローカルな指示・既知の依存）
  3. 制御された操作（ツールの型・引数検証・パスと権限の境界・構造化された結果）
  4. 永続実行（明示的な実行状態・チェックポイント・判断・教訓）
  5. 証拠（決定的チェック・敵対的検証・変更レシート）
  6. 回復と学習（失敗分類・回数制限つきリトライ・エスカレーション・繰り返す失敗からのハーネス更新）
- Skill 2 は各レベルで何が生成されるかを説明し、推奨レベルを理由つきで示し（H9）、ユーザーが選ぶ。
- 退けた案: 使い方（伴走／委任／自走）で選ばせる案（提示時の推奨）／Agent の数を軸にする案。
- 提示済みの代償: ハーネスに詳しくないユーザーはレベルの意味を理解してからでないと選べない。
  したがって各レベルの説明文（何が生成され、何の失敗を防ぐか）の分かりやすさが、このスキルの品質を左右する。
- 他の裁定との関係（導出。作者の個別確認は未了）:
  - H9 の Policy 下限は記事ではレベル 3 に属するが、レベル 1〜2 を選んでも生成する。
  - H5 により、調査・設計エージェントと本実装エージェントはどのレベルでも作る。
    検証エージェント（作る側と別の文脈で結果を壊しにいく役）はレベル 5 から。

### H11. Skill 2 の入力契約は A〜H の8区分（2026-09-20）

Skill 2 の8区分（元記事 17 章）それぞれが、プロジェクトについて何を知らないと書けないかを洗い出して導いた。
Skill 2 は `docs/project-definition.md` に次の区分があることを前提にし、プロジェクトの基本情報をユーザーに聞き直さない。

| 区分 | 内容 | Skill 2 での使い道 |
|---|---|---|
| A 目的とスコープ | 目的／やること／やらないこと／制約 | Contract（タスク契約の雛形） |
| B システム境界 | UI・Backend・DB・外部サービス・認証・デプロイの有無と一行の役割、相互の関係 | Context（マップ）、Agent 分割の材料 |
| C 技術 | 言語・ランタイム・パッケージマネージャ・主要フレームワーク・DB 種別・デプロイ先種別（H6） | Tools（permissions の具体コマンド） |
| D リスク | 外部作用／不可逆・機微な操作／秘密情報・個人情報（H9） | Policy 下限、推奨レベル |
| E 環境 | 開発環境（OS・コンテナ利用）／local・staging・本番の有無／リポジトリのホスティングと CI の有無 | Tools、Policy、Recovery |
| F リポジトリ構成 | 単一か分離か／最上位の配置／新規か既存コードありか | Context（マップ）、パス境界 |
| G 運用前提 | ソロかチームか／試作か本番品質か | 推奨レベル、承認者 |
| H 未決・持ち越し | 未決事項／Skill 3 への持ち越しメモ | 読むだけ |

- 各項目は「決定／仮定（ユーザー確認済み）／なし／持ち越し」のいずれかの状態を持つ。
- 退けた案: G（運用前提）を外して Skill 2 側で聞く案／検証可能性（外部サービスのテスト環境の有無など）も Skill 1 で集める案。
  後者は、アイデア段階では答えられず調査が要るため Skill 3 の領域とした。
- Skill 2 がユーザーに聞いてよいのはハーネス側の判断（レベルの選択、Policy の確認など）だけ。
- 追記（2026-09-20）: Skill 1 の D12 により、対象の種類は Web に限定しない。区分 B の中身は
  「利用者との接点／処理／データの保存先／外部とのやりとり／配布・実行場所」という一般的な問いで書かれ、
  該当しないものは `none` になる。上の表の B の記述（UI・Backend・DB …）は Web の場合の典型例として読む。

### H12. 既存ファイルがあっても動く。計画を提示し、承認後に適用する（2026-09-20）

  「新規作成／変更／そのまま」の3分類で計画を提示し、承認されてから書く。新規プロジェクトでも同じ手順を踏む。

- 人が書いた部分は保持する。`settings.json` は追記マージする。
- Skill 2 自身の再実行（レベルを上げる、失敗を受けてハーネスを直す）も同じ手順で扱う。
- 退けた案: 既存ファイルがあれば中止する新規プロジェクト専用案／退避したうえで毎回上書きする案。
- H2 の時点で保留にした「書き込み前に承認を挟むか」は、これで確定（挟む）。

### H15. 基本役を超える Agent 分割は、ツールチェーンかリスク階級が違うときだけ（2026-09-20）

- 基本役: 調査・設計／実装／（レベル 5 以上で）検証。
- 分割の引き金は2つに限定する。
  1. ツールチェーンが違う（例: Swift のモバイルアプリと Go の Backend）。使うコマンドも検証方法も別物なので実装役を分ける。
  2. リスク階級が違う（例: デプロイやマイグレーションのような外部作用・不可逆操作を扱う役）。承認ゲートつきの別 Agent にする。
- 同一ツールチェーンの Web + API（例: Next.js のフルスタック）は実装役1つのまま。コンポーネントの数は分割の理由にならない（方針書 9.1）。
- 分割するたびに「どの失敗を防ぐためか」を根拠記録に書く。
- 判定の材料は入力契約の C（技術）・D（リスク）・E（環境）。同じ入力からは同じ構成が出ることを目指す。
- 退けた案: 初回は基本役で固定し分割は失敗の観測後に限る案／分割条件を規則化せず実行時の裁量に任せる案。

### H16. 設計書駆動の運用を、役ごとの書き込み境界として仕組みで強制する（2026-09-20）

- 調査・設計役は `docs/` にしか書けず、ソースコードは読むだけ。
- 実装役はコードと作業状態（進捗・教訓）には書けるが、設計文書は読むだけ。
  実装中に設計の誤りを見つけたら、自分で直さず調査・設計役に差し戻す。
- 検証役は何も修正できず、合否と証拠を返すだけ（元記事 8 章「直さずに却下できる権限」）。
- どのレベルを選んでも強制する。レベル次第で守られたり守られなかったりする形にはしない。
- 根拠: 元記事 11 章「繰り返し重要になるルールは、指示文ではなく仕組みに落とす」、9 章「ポリシーは推論の外に置く」。
- 退けた案: 役割を指示文で伝えるだけの案／レベル 3 以上でだけ強制する案。
- 提示済みの代償: 軽微な設計修正でも役の往復が発生し、小さな変更が遅くなる。
- Claude Code での実現（2026-09-20 に公式ドキュメントで確認）:
  - `settings.json` の `permissions`（allow / ask / deny）はセッション全体に効き、subagent ごとには分けられない。
  - 粗い制限は subagent 定義の `tools` / `disallowedTools` で行う（例: 検証役から Edit / Write を外す）。
  - パス単位の書き込み境界は PreToolUse hook で行う。hook の入力には `agent_type`（Agent 名）と
    `agent_id`（subagent 内でだけ付く）が入るので、1本の hook で役ごと・主セッション込みで判定できる。
    subagent 定義の `hooks` に書けば、その subagent が動いている間だけ効く hook にもできる。
  - 出典: <https://code.claude.com/docs/en/hooks.md>、<https://code.claude.com/docs/en/sub-agents.md>
- 既知の限界: Edit / Write を hook で止めても、Bash 経由の書き込み（リダイレクトなど）は同じ hook では防げない。
  どこまで塞ぐかは実装時に決める。
- 未検証: subagent の `tools` に `Edit(src/**)` のようなパス付きパターンを書けるかどうか。

### H17. 主セッションが設計の対話役を兼ねる。調査・実装・検証は subagent（2026-09-20）

- 前提となる事実（2026-09-20 に公式ドキュメントで確認）: subagent は `AskUserQuestion` を使えない。
  `tools` に書いても外される。したがって subagent にした役はユーザーに質問できない。
  出典: <https://code.claude.com/docs/en/sub-agents.md>
- 裁定:
  - ユーザーとの往復が要る設計判断は主セッションが行い、`docs/` に書く。
  - ユーザーとの往復が要らない調査（Web 検索、コード読解）は、読み取り専用の subagent に委任する。
  - コードは主セッションからは書けない。実装役 subagent に委任する。
  - 主セッションの役割は `CLAUDE.md` とプロジェクト skill で定義し、書き込み境界は hook で強制する
    （hook 入力に `agent_id` が無い＝主セッション）。
- H5 の実体化: 「調査・設計エージェント」は、調査＝subagent、設計＝主セッションの役割、として実体化する。
- 退けた案: 主セッションを純粋な司令塔にして設計も subagent に委任する案（設計役の質問が伝言になる）／
  主セッションを制限せず何でも書ける逃げ道として残す案（最もよく使われる経路で H16 の強制が効かなくなる）。
- 検討して採らなかった実現方法: `--agent` や `agent` 設定で主セッション自体を特定の Agent にする方法。
  Agent のシステムプロンプトが Claude Code 既定のものを丸ごと置き換えるため、既定の振る舞いを失う。

### H18. 生成物は「常に生成する土台」＋「6レベルの累積」（2026-09-20）

- 背景: H5・H9・H16・H17 は「どのレベルでも必ず生成する」と決めたが、これらは記事の区分ではレベル 2〜3 に属する。
  レベル 1 を選んでもレベル 2〜3 の一部が入ることになるため、必ず入るものと選べるものを分けて整理した。
- 土台（レベルに関係なく常に生成）:
  - 実装役 subagent、調査役 subagent（H5・H15）
  - 主セッションの役割定義（`CLAUDE.md`）（H17）
  - 役ごとの書き込み境界 hook（H16）
  - Policy 下限: 外部作用は承認、不可逆・機微は禁止（`settings.json`）（H9）
  - 根拠記録 `docs/agent-architecture.md`（H3）
- レベルで足されるもの（累積）:
  - L1 境界のあるタスク: タスク契約の skill と雛形
  - L2 読める環境: `CLAUDE.md` のプロジェクトマップとコマンド一覧、`.claude/rules/`（パス別のローカル指示）
  - L3 制御された操作: permissions の許可リスト（下限を超える分）、`.mcp.json`、役ごとの tools 絞り込み
  - L4 永続実行: `docs/` の状態ファイル（事実・判断・進捗・教訓）と更新手順（H13）
  - L5 証拠: verify コマンドの取り決めと完了ブロック hook、検証役 subagent、変更レシート（H6）
  - L6 回復と学習: 失敗分類とリトライ上限、トレース記録 hook、ハーネス振り返り skill（育てる／外す）
- ユーザーへの説明は「土台は必ず入る。その上にどこまで足すか」。
- 退けた案: 土台を Policy 下限だけにしてレベルを記事どおりに保つ案（H16・H17 と矛盾する）／
  土台の概念を作らず最低レベルを 3 にして選択肢を 4 段階にする案。
- 提示済みの代償: L2・L3 は、記事の定義から土台に移ったぶんだけ中身が薄くなる。

### H19. 設計文書は `docs/` 直下、作業状態は `docs/harness/` にまとめる（2026-09-20）

```text
docs/
├── project-definition.md     ← Skill 1
├── agent-architecture.md     ← Skill 2（根拠記録）
├── system-design.md ほか      ← Skill 3（設計文書）
```

- タスク契約と変更レシートは同じタスクのフォルダに並べる。「何を約束して、何が証明されたか」が一箇所で読める。
- 書き込み境界（H16）はこの構成で1ルールになる。
  - 主セッション: `docs/**` に書ける。
  - 実装役: `docs/harness/**` には書けるが、それ以外の `docs/**` は読むだけ。
  - 検証役・調査役: どこにも書けない。
- タスク契約の項目は元記事 2 章の5つの問い（あるべき結果／スコープ内／変えてはいけないもの／完了の証拠／承認が要る操作）、
  変更レシートの項目は 13 章（目的／変更点／検証済み／未検証／判断／リスク／承認待ち）に沿う。文面は自前の言葉で書く。
- H13 の未裁定（`docs/` のサブフォルダの切り方）は、これで解消。
- 退けた案: 種類別に `docs/` 直下へ並べる案（書き込み境界の定義が列挙になる）／

### H20. 入力が無い・不完全なら、何も生成せず中止して Skill 1 を案内する（2026-09-20）

- `docs/project-definition.md` が無い、または A〜H に状態の付いていない項目が残っているときは、
  足りない項目を名指しして `project-design-opening` の実行（または再実行）を案内し、何も生成しない。
- 理由: H11「Skill 2 はプロジェクトの基本情報を聞き直さない」を保ち、聴取ロジックを2スキルに重複させない。
- 退けた案: 足りない項目だけ Skill 2 が聞く案／既存コードから推定して続行する案
  （リスクや運用前提はコードから読み取れず、Policy 下限が誤った前提の上に作られるおそれがある）。
- 帰結:
  - Skill 2 は単体では動かない。README に「Skill 1 とセットで使う」と明記する。
  - 既存コードがあるプロジェクトへの後付け導入は、Skill 1 が既存リポジトリを読んで A〜H を埋められるかどうかに懸かる。

  - 追記（2026-09-20）: Skill 1 の D9 で「新規プロジェクト専用」と裁定された。既存プロジェクトへの後付け導入には対応しない。
    `project-definition.md` が無く既存コードがあるときは、Skill 1 を案内せず「対象外」と伝える。

### H21. トレースは節目の出来事だけを記録する（2026-09-20）

- レベル 6 で生成する hook は、検証の合否・ブロックされた操作・承認要求・設計への差し戻し・リトライといった
  節目の出来事だけを、1行ずつ `docs/harness/traces/` に追記する。
- ツールの入力内容は記録しない。秘密情報や個人情報がリポジトリに混入する事故を避けるため。
- 生の全履歴は Claude Code の transcript に任せる。
  根拠: 元記事 6 章「生の履歴は監査用に残し、実行に使うのは編集された状態」。
- 用途は、失敗したときにどの節目で何が起きたかを追うことと、ハーネス振り返りの材料。
- 退けた案: 全ツール呼び出しを記録する案（transcript と重複し、秘密情報が `docs/` に書き出される）／
  トレースを生成しない案（セッションをまたいだ経緯が追えない）。

### H22. ハーネスの更新は skill が提案し、人が承認して適用する。ハーネス自身への書き込みは常に承認必須（2026-09-20）

- レベル 6 で生成する振り返り skill が、教訓（`state.md`）とトレースから改善案を作る。
  改善案は、新しいルール・hook・許可・マップ項目の追加（元記事 14 章）と、不要になった部品の削除（15 章）の両方を含む。
- 適用は主セッションが人の承認を得て行い、根拠記録（`docs/agent-architecture.md`）にも追記する。
- 土台（H18）への追加: `.claude/`・`CLAUDE.md`・`.mcp.json` への書き込みは、どのレベルでも承認必須とする。
  Agent が自分の権限を黙って広げる経路を塞ぐため。Policy 下限（H9）の一部として扱う。
- 退けた案: 改善は必ず Skill 2 の再実行で行う案（再実行を思い出さない限り学習が回らない）／
  小さな改善は Agent が承認なしで適用する案（`CLAUDE.md` の書き換えで間接的に振る舞いを変える経路が残る）。
- 部品を外すかどうかの判断材料は元記事 15 章の5つの問い
  （どの失敗を防ぐか／その失敗は今も起きるか／遅延と複雑さはどれだけか／もっと単純にできないか／外したらどうなるか）。

### H23. Skill 2 がユーザーに確認を求める場面は3段階（2026-09-20）

1. レベルの選択。推奨レベルを理由つきで示す（H9・H10）。
2. Policy 表の確認。リスク情報（入力契約の D）から導いた「どの操作が自動／承認／禁止か」の表を単独で見せる
   （例:「Stripe への課金呼び出し→承認」「本番 DB への接続→禁止」）。
3. ファイル計画の承認。生成・変更するファイルを「新規作成／変更／そのまま」で示す（H12）。

- Policy 表を単独の段階にする理由: 安全の要であり、しかも Skill 2 の推論で導いたものなので、
  ファイル一覧の中に埋もれさせず人の目で確かめてもらう。
- Agent 構成は確認の対象にしない。H15 の規則で機械的に決まり、根拠記録に理由が残る。方針書 9.3 とも整合する。
- 退けた案: Policy 表をファイル計画に含める2段階案／Agent 構成の確認を足す4段階案。

### H24. Skill 3 が Skill 2 の成果物に期待するものは、土台で満たされる（2026-09-20、導出）

作者の裁定ではなく、H17・H18・H19 からの導出。Skill 3 を企画するときに再確認する。

- Skill 3（詳細設計・調査）はユーザーとの往復が要るので、主セッションで動く（H17）。
- Skill 3 が必要とするのは、調査役 subagent が存在すること、主セッションが `docs/**` に書けること、
  どの役を何に使うかが `docs/agent-architecture.md` から読めること。いずれも土台（H18）に含まれる。
- したがって Skill 3 は、ユーザーがどのレベルを選んでいても動く。

### H25. 生成する hook は Node.js スクリプト（2026-09-20）

- hook（書き込み境界の判定、完了ブロック、トレース記録）は node で実行する `.js` / `.mjs` として生成する。
- 理由: hook は JSON を受け取って判定する。Node.js なら JSON の扱いとパス判定を標準機能だけで書け、
  Windows・macOS・Linux で同じコードが動く。作者自身の環境が Windows である。
- 前提: 対象プロジェクトの言語に関係なく Node.js の導入が要る。README に前提として書き、
  Skill 2 は実行時に node の有無を確かめる。
- 退けた案: bash スクリプト（JSON の解析に jq が要り、Windows の Git Bash にも macOS にも標準では入っていない）／
  プロジェクトの言語に合わせて生成する案（雛形を言語の数だけ保守・評価することになる）。

### H28. 推奨レベルは常に L3（2026-09-20）

- Skill 2 は入力によらず L3（制御された操作）を推奨し、上げ下げは利用者に任せる。
  利用者への説明は「標準は L3。試作なら下げて、本番運用なら上げてください」。
- H9 の修正: H9 は「リスク情報から推奨プリセットを理由つきで提示する」としていたが、推奨はリスク情報から導かない。
  H9 のうち「Policy の下限はどのレベルでも外さない」は変わらない。
- Skill 1 の D4 への影響: リスク情報（区分 D）の用途は、推奨レベルの決定ではなく Policy 下限と Policy 表（H23）の導出だけになる。
  収集は引き続き必須。区分 G（運用前提）は推奨レベルには使われなくなり、用途は承認者の把握が中心になる。
- 退けた案: 運用前提×リスクの表で決め、初回は L6 を推奨しない案（提示時の推奨）／実行時の判断に任せる案。
- 提示済みの代償: 本番品質で決済を扱うプロジェクトにも、証拠（L5）も状態管理（L4）も無い構成が既定値として出る。
  ハーネスに詳しくない利用者は推奨をそのまま受け入れやすい。安全面は Policy 下限（H9・H22）が受け持つ。

### H27. 生成するハーネスに「`project-definition.md` を更新するときの決まり」を含める（2026-09-20、Skill 1 の D11 から逆算）
