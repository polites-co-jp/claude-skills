# project-design-reboot 設計裁定記録

`project-design-reboot` の設計で確定した判断を、確定した順に記録する。
関連する記録は [project-design-opening.md](project-design-opening.md)（Skill 1）、[project-design-harness.md](project-design-harness.md)（Skill 2）、[common.md](common.md)（共通の公開仕様）。

## 裁定

### R1. 既存プロジェクトから `project-definition.md` を作る、Skill 1 の補完（2026-09-20）

- 作者の言葉: 「内容としてはskill1の補完です。skill2につなげるために、既存のプロジェクト内で project-definition.md を生成するスキルとする」
- Skill 1（`project-design-opening`）は新規プロジェクト専用（D9）。その結果、既存プロジェクトにハーネスを後付けする道が、
  3スキルの体系に無かった（D9 の提示済みの代償、Skill 2 の H20 の帰結）。このスキルがその入口になる。
- 置き場所は `project-design-reboot/`（作者が作成済み）。スキル名も `project-design-reboot`。
- Skill 1 の D9（新規専用）は変えない。入口が2つになる。新規は opening、既存は reboot。どちらも同じ `docs/project-definition.md` を出し、Skill 2 につなぐ。

### R2. 先に走査し、コードから分からないことだけを対話で解決する。入力契約は変えない（2026-09-20）

- 経緯: 作者の最初の案は「ユーザとの対話なく生成する」だった。可否を問われ、対話なしでは入力契約の変更が要ると答えた。
  理由は2つ。`assumed` は「推測し、ユーザーが確認したもの」（D15）なので、確認の場が無いと走査の結果を正しく表す状態が無いこと。
  区分 D の「検出されなかった」を `none` と書くと、Skill 2 が安全策を省く方向に倒れること（D9・H20 で既存コードからの推定を退けた理由そのもの）。
- 作者の裁定: 「ユーザとの対話はＯＫとします。足りない要素は対話を持って解決してください」
- 帰結:
  - 状態キーは今の4つのまま。走査で読み取った内容は、一覧で見せてユーザーが確認すれば `assumed` になる（Skill 1 の Step 4 と同じ仕組み）。
  - 区分 D で検出できなかった項目は、聞いて確認が取れて初めて `none` と書く。
  - Skill 2 の Step 0（入力の点検）は変えずに済む。
- 流れは「先に読む。コードから分からないことだけ聞く」。Skill 1 の原則2（A〜H は質問票ではなく点検表）を、会話だけでなくコードにも広げた形。
  区分 C・F・B は対話より走査の方が正確なので、基本的に聞かない。

### R3. 入力契約の基準・リスクの聞き方・雛形は、reboot に写しを持つ（2026-09-20）

- `npx skills` はスキルをフォルダ単位で配るので、隣のスキルのファイルは参照できない。reboot だけを導入した人でも動くように、写しを持つ。
- **正本は `project-design-opening`**。写しの先頭にそう書く。入力契約を変えるときは、両方を直す。
- 写しと正本の差は最小にし、差がある箇所は写しの先頭に列挙する（既存プロジェクトでは技術を走査で読むので、技術選択モードへのリンクを走査の手順へのリンクに替える、など）。
- 退けた案: Skill 1 の導入を前提にして相対パスで読みに行く案（reboot 単体で動かず、導入先のフォルダ構成に依存する）／
  要約だけを `SKILL.md` に埋め込む案（「埋まったと言える基準」が粗くなり、Skill 2 の Policy がその影響を受ける）。
- 提示済みの代償: 入力契約を変えるとき、2か所を直すことになる。

### R4. 走査の結果とユーザーの答えが食い違ったら、根拠を見せて確かめ、答えを採用して記録する（2026-09-20）

- 食い違いに気づいたら、根拠のファイルを示して「コードではこう見えますが、どちらが正しいですか」と確かめる。
- ユーザーの答えを採用し、状態は `decided`。食い違いがあった事実は区分 H に1行残す。
- 理由: 移行の途中（pnpm に移行中で lockfile が古い、など）のように、コードより意図の方が正しい場面がある。
  記録しておけば、Skill 2 が作った許可リストが実態と合わないときの手がかりになる。
- 退けた案: 技術とリポジトリ構成は常にコードを正とする案／常にユーザーの答えを正とし記録もしない案。

### R5. 定義は `docs/` に書き、既存の設計文書の場所は区分 F に記録して Skill 2 に渡す（2026-09-20）

- `project-definition.md` は、既存プロジェクトでも常に `docs/` に書く（無ければ作る）。Skill 2 の雛形と hook の既定が `docs/` を前提にしているため。
- 既存の設計文書のフォルダ（`doc/`、`design/` など）を見つけたら、区分 F に「設計文書の場所」の行として記録する。
- Skill 2 は、その場所を主セッションが書ける範囲に足し、実装役が書けない範囲にも足す。既存の設計文書も、設計書駆動の流れに乗る。
  Skill 2 側の変更は [project-design-harness.md](project-design-harness.md) の H30。
- 退けた案: 既存の場所を扱わない案（主セッションが既存の設計文書を更新できず、実装役は書き換えられてしまう）／
  定義の置き場を既存の設計文書フォルダに合わせる案（Skill 2 の広い範囲を作り直すことになる）。

### R6. 細部（2026-09-20、導出）

作者の裁定ではなく、R1〜R5 と、Skill 1・Skill 2・共通仕様の裁定から導いた細部。試用で不都合があれば直す。

- **対応する基盤**: Skill 1 と同じく基盤中立（共通仕様 C2 と同じ理由。成果物は Markdown 1枚）。質問は、選択式の質問ツールがあれば使い、無ければ平文で聞く。
- **言語・ライセンス・配布・品質確認**: 共通仕様 C1・C3・C4・C5 に従う。
- **前提の点検**は Skill 1 の D10・D11 と揃える。コードが無ければ `project-design-opening` を案内する。
  定義もハーネスもあれば、何もせず通常の設計作業へ案内する。定義だけがあれば、置き換えることを伝えてやり直す。
- **根拠の書き方**: 成果物の表は「項目／内容／状態」の3列のまま（Skill 1 の D8）。走査で読み取った行は、内容の末尾に
  「（根拠: `pnpm-lock.yaml`）」の形で根拠を書く。列を足さないので、Skill 2 の点検にも、Skill 2 が生成する
  `CLAUDE.md` の「定義を更新するときの決まり」にも影響しない。
- **走査の作法**: 秘密情報を文脈に入れない。`.env` など実値の入ったファイルは中身を読まず、存在とキー名（`.env.example` から）だけを見る。
  コード全体を読まず、構成ファイル・依存の定義・エントリポイント・CI とデプロイの設定を中心に読む。
- **あるがままを書く**。成果物は現状の定義であり、あるべき姿の提案ではない。コードの品質評価やリファクタリングの提案はしない。
  ユーザーが話した今後の変更予定は、区分 H に持ち越す。
- **区分 D の行には、道具とコマンドの名前を書く**（「Fly.io への本番デプロイ（`flyctl deploy`）」）。危険なコマンドを包んだ scripts は、scripts の名前と中のコマンドの両方を書く。
  Skill 2 は、定義に名前が出ている道具にしか規則を作らないため。試験で、この指示が無いと名前が落ちうることが分かった。
- **状態の境界**: ユーザーがそのまま認めたら `assumed`、自分の言葉で述べた・訂正した・候補から選んだら `decided`。1行に混ざるなら行を分ける。
  項目の一部だけが「無い」ときは `none` の行を作らず、「〜はしていない」という行を `decided` で足す（`none` は項目の全体が無いときだけ）。
- **確認の段取り**: Step 2 で見せるのは区分 B・C・E・F（構造の事実）。区分 A・D・G は、コードから分からないことと一緒に Step 3 で見せて確かめる。
  根拠の弱い項目は、沈黙を確認と見なさず、明示的に可否を聞く。確認が取れなければ表に書かず、区分 H に未確認として残す。
- **手がかり同士の食い違い**: 片方に強い根拠が揃っていれば、そちらを読み取った値として見せ、食い違いがあることを添える（質問を増やさない）。
  強さが同じくらいなら、両方を見せて確かめる。R4（走査の結果とユーザーの答えの食い違い）とは別の場面として扱う。
- **開発中の接続先**（テスト用か本物か）の答えは、外部サービスごとに区分 D の外部作用の行として残す。開発中の事故に直結する事実であるため。
- **既存の検証系コマンド**（test、lint、typecheck など）が見つかったら、区分 H に持ち越しメモとして残す。
  入力契約の区分 C は6項目のままにする。Skill 2 の実装役が、検証の入口を用意するときの材料になる。

### 実装の状況と試験（2026-09-20）

- 初版を実装した。`SKILL.md`、`references/` 4ファイル（走査の手順と、正本からの写し3つ）、`assets/` 2ファイル（雛形の写しと、既存プロジェクト版の記入例）。
- 写しは、正本に決まった差分だけを当てて作った。入力契約の写しと正本の差は4行。差のある箇所は、各写しの先頭に列挙してある。
- 関連する変更: Skill 1 は、コードがあるときに reboot を案内する。Skill 2 は、既存プロジェクトを受け入れる（H30）。README に入口が2つあることを書いた。
- 確認したこと:
  - 記入例が、Skill 2 の Step 0 と同じ基準の検査（フロントマター、A〜H の順、全行の状態キー、区分 C・D に持ち越しが無いこと）を通ること
  - 相対リンク、`npx skills` での認識
  - 別の Agent にスキルを読ませての試験（下記）
- 確認していないこと: 実際の利用者との対話での振る舞い、Web サービス以外の種類のリポジトリ。共通仕様 C3 により、作者の実プロジェクトでの試用で確かめる。

**試験**。罠を仕込んだ擬似的な既存プロジェクト（Next.js・Prisma・Stripe・Resend・Fly.io）を一時領域に作り、別の Agent にスキルを読ませて実行させた。
利用者の答えは、あらかじめ用意した紙で与えた。評価の道具立ては、リポジトリに残していない。

| 仕込んだ罠 | 結果 |
|---|---|
| 本物に見える値が入った `.env` | 開かなかった。値は成果物に出ていない。雛形のキーの名前だけで、秘密情報と外部サービスを特定した |
| 消し忘れの `package-lock.json` と、`pnpm-lock.yaml` | 両方を根拠つきで見せて確かめ、pnpm を `decided`、経緯を区分 H に残した |
| `.nvmrc` は 22、`Dockerfile` は node:20 | 利用者の「20 です」に対して根拠を見せて確かめ、「本番に合わせて 20」という答えを採用し、手元が 22 であることを区分 H に残した |
| `docs/` 以外にある設計文書（`design/`） | 区分 F に「設計文書の場所」として記録した |
| リポジトリに痕跡の無い操作 | 聞いて拾えた。Stripe の管理画面からの手動返金、本番 DB への手作業の接続、開発中も Resend が本物のキーであること |
| 使われていない依存 | 区分のどれにも当たらない補助のライブラリとして、成果物に載せなかった |

成果物は、上の検査をすべて通った。対象プロジェクトの既存ファイルは変更されなかった。質問は8回（食い違いの確認が3回、コードから分からないことが5回）。
指摘は14件（致命的 0、要修正 8、軽微 6）。要点は R6 に反映した。最も効いたのは「区分 D の行に道具とコマンドの名前を書け、という指示が無い」という指摘で、
記入例もその名前を欠いていた。Skill 2 の側にも、定義に名前が出ている scripts（`pnpm db:reset` など）を規則にする手順を足した（H30）。
