# project-design-opening 設計裁定記録

Skill 1（project-design-opening）の設計を詰める過程で確定した判断を、確定した順に記録する。
元になった設計方針は「Skill 1 設計方針 — Claude引き継ぎ用」（2026-09-19 のセッションで提示）。

## 前提（調査で確定した事実）

- リポジトリ `polites-co-jp/claude-skills` はコミットゼロ・`project-design-opening/` は空。既存構成への適合制約はない。
- 作者の環境は `~/.agents/skills` + `.skill-lock.json`（`npx skills` エコシステム）でスキルを管理している。
- 作者の既存自作スキルは `SKILL.md` + `references/` + `assets/` 構成、本文は日本語。

## 裁定

### D1. `project-design-opening` は Skill 1 そのものの名前（2026-09-19）

- `project-design-opening/SKILL.md` が Skill 1 本体。スキル名も `project-design-opening`。
- Skill 2 / Skill 3 は `claude-skills` 直下に兄弟フォルダとして並べる。3スキルを束ねる親フォルダは作らない。
- 退けた案: `project-design-opening/skills/<skill名>/` のスイート構成。
- 帰結: 3スキルの関係（成果物の連鎖）を説明する場所はリポジトリ直下の README になる。

### D2. Skill 2 を先に企画し、Skill 1 の収集項目はそこから逆算する（2026-09-19）

- Skill 1 の終了条件は「Skill 2 が追加質問なしで設計できる状態」だが、Skill 2 が未定義のままでは判定できない。
  そこで Skill 2 の企画（何を入力に何を決めるか）を先に固め、Skill 1 の収集項目と終了条件をそこから逆算する。
- Skill 2 の置き場所は `project-design-harness/`（作者が作成済み）。スキル名も `project-design-harness`。
- 退けた案: Skill 2 の入力契約を仮のチェックリストとして Skill 1 側で先に明文化する案／LLM の自己判定に任せる案。
- 帰結: 今回のスコープは Skill 1 単体から「Skill 2 の企画 → Skill 1 の設計」の順に広がる。
  Skill 2 の裁定は `docs/decisions/project-design-harness.md` に記録する。

### D3. Skill 1 の技術粒度は「ツールチェーンが決まるところまで」（2026-09-19、Skill 2 の H6 から逆算）

- Skill 1 が終了時点で確定させる技術: 言語、ランタイム、パッケージマネージャ、主要フレームワーク、DB 種別、デプロイ先種別。
  該当する境界が存在しない項目（例: DB なし）は「なし」で確定とする。
- 理由: Skill 2 は permissions と hooks に具体的なコマンド名を書く。本実装エージェントも初回に作るため、穴のままにできない。
- 元方針 4 章の「具体的な選択は、必要な場合に技術選択モードに従って決定する」の「必要な場合」は、この粒度で確定した。
  上記6項目は常に決める。それより細かい選択（テストランナー・linter・ORM・UI ライブラリ・REST/GraphQL など）は Skill 3。
- 決め方は元方針 5 章の技術選択モード（Mode 1: 候補提示 / Mode 2: 委任）をそのまま使う。

### D4. Skill 1 はリスク情報（外部作用・不可逆操作・機微情報）を収集する（2026-09-19、Skill 2 の H9 から逆算）

- 元方針 2 章の「Skill 1 で扱うもの」はシステムの構成要素（UI / Backend / DB / 外部 API / 認証 / デプロイ）が中心で、
  「その構成要素が外の世界に何をするか」を含んでいなかった。これを収集項目に加える。
- 収集する内容:
  - 外部作用: 開発中や運用中に、システムの外へ影響が出る操作（メッセージ送信、デプロイ、課金・購入、外部 API への書き込みなど）。
  - 不可逆・機微な操作: データ削除、本番データの変更、認証情報の扱い、全体公開など。
  - 秘密情報・個人情報の有無。
- 理由: Skill 2 はこの情報から推奨プリセットを決め、どのプリセットでも外さない Policy の下限（承認ゲートと禁止ルール）を書く。
  情報が無ければ、Skill 2 がユーザーにプロジェクトの基本情報を聞き直すことになり、Skill 1 の終了条件を満たさない。
- 粒度: 「何があるか」まで。個々の操作の承認フローや権限設計は Skill 2 の仕事。
- 追記（2026-09-20）: Skill 2 の H28 で推奨レベルは常に L3 と裁定された。リスク情報は推奨レベルの決定には使われず、
  用途は Policy 下限と Policy 表の導出になる。収集が必須であることは変わらない。

### D5. 終了条件は「入力契約 A〜H の全項目が状態を持つこと」（2026-09-20、Skill 2 の H11 から逆算）

- D2 で保留にした終了条件の判定方法が、これで確定した。
- `docs/project-definition.md` は Skill 2 の入力契約と同じ A〜H の8区分を持つ
  （A 目的とスコープ／B システム境界／C 技術／D リスク／E 環境／F リポジトリ構成／G 運用前提／H 未決・持ち越し）。
  区分の中身は [project-design-harness.md](project-design-harness.md) の H11。
- Skill 1 は、全項目が「決定／仮定（ユーザー確認済み）／なし／持ち越し」のいずれかになったら終了する。
- 元方針に対して増える収集項目は D（リスク）・E（環境）・G（運用前提）。
- 元方針 6 章の質問方式は変えない。アイデアの説明から読み取れる項目は聞かず、不足している項目だけを聞く。
  A〜H は質問票ではなく、埋まったかどうかを確かめるための点検表として使う。

### D6. Mode 2 の過去の採用実績は、毎回ユーザーに聞く（2026-09-20）

- Mode 2 を選んだときに「よく使う構成があれば教えてください」を1回聞く。答えが無ければ、要件に対して一般的な構成に進む。
- スキルはどこにも書き込まない。永続ファイルも、特定基盤の記憶機能も前提にしない（共通仕様 C2 と整合）。
- 聞く単位は個別技術ではなく構成（例: TypeScript + React + Node.js + PostgreSQL + Docker）。元方針 5 章のとおり。
- 退けた案: ホーム配下にスキル専用の実績ファイルを持つ案（提示時の推奨）／ユーザーが指した過去のリポジトリを読む案。
- 提示済みの代償: 「LLM に任せる」を選んでも毎回同じ質問に答えることになる。プロジェクトを重ねても構成が揃っていく効果は弱い。

### D7. 技術選択モードは、技術の話に入る直前に1回、構成単位で選ばせる（2026-09-20）

- 目的とシステム境界が見えてからモードを聞く。冒頭では聞かない。
- Mode 1: 6項目（D3）をばらばらに聞かず、要件に合う「構成」を 2〜3 案、理由つきで提示する。
  1つ選んでもらい、変えたい項目だけ調整する。
- Mode 2: 構成を1つ決めて理由とともに示し、異議がある項目だけ直す。決め方は元方針 5 章の優先順位と D6。
- ユーザーがアイデアの説明で既に指定している技術は、モードに関係なくそのまま採用する。
- どちらのモードも、技術に関する質問は実質 1〜2 回で済ませる。
- 退けた案: 冒頭で1回聞く案（何を決めるのか分からない段階で選ばされる）／
  項目ごとに選ばせる案（質問が6回以上に増え、構成として扱う考え方が崩れる）。

### D8. `project-definition.md` は固定見出し＋状態列つきの表＋フロントマター（2026-09-20）

- 1ファイルの Markdown。別ファイル（YAML など）は出さない。
- 先頭の YAML フロントマターに、書式バージョン（`schema: project-definition/1`）、
  完成状態（`status: draft | complete`）、更新日（`updated`）を持つ。
- 本文は A〜H の固定見出し。各区分は「項目／内容／状態」の表にする。
- 状態は言語によらない固定キー: `decided`（決定）／`assumed`（仮定。ユーザー確認済み）／`none`（なし）／`deferred`（持ち越し）。
  共通仕様 C1 の「機械的に読む部分は固定キー」に対応する。
- 区分 B にはシステム境界の図（テキスト）も置く。区分 H は持ち越し事項の箇条書き。
- Skill 2 は状態列を見るだけで H20 の点検ができる。Skill 1 自身も同じ列で D5 の終了判定をする。
- 退けた案: Markdown と別に YAML ファイルも出す案（二重に持つとずれる）／
  見出しだけ固定した自由な Markdown（点検が読解頼みになり、判定が実行のたびにぶれる）。

### D9. Skill 1 は新規プロジェクト専用。既存コードがあれば対象外と伝えて終了する（2026-09-20）

- `docs/project-definition.md` が無く、かつ既にコードがあるリポジトリで呼ばれたら、対象外であることを伝えて終了する。
- 理由: Skill 1 を「曖昧なアイデアの整理」という本来の役割に集中させ、コード読解の手順を持たせない。
- 退けた案: コードから読み取れる項目は読んで埋め、残りだけ聞く案（提示時の推奨）／既存コードを無視して通常どおり聞く案。
- 提示済みの代償: 既存プロジェクトにハーネスを後付けする道が、3スキルの体系から無くなる。
  Skill 2 の H20 は入力不足のとき Skill 1 を案内するが、既存プロジェクトではその案内先が行き止まりになる。
- 帰結: 両スキルの README に「新規プロジェクト向け。既存プロジェクトへの後付けには対応しない」と明記する。
  Skill 2 の H20 の案内文も、既存コードがある場合は「対象外」と伝える形にする。
- 追記（2026-09-20）: 既存プロジェクトの入口として `project-design-reboot` を作った（[project-design-reboot.md](project-design-reboot.md) の R1）。
  D9 そのもの（Skill 1 は新規専用）は変えない。コードがあるときの案内先が、「対象外」から `project-design-reboot` に変わった。
  入力契約の正本はこのスキルにあり、reboot は写しを持つ（R3）。**入力契約を変えるときは、reboot の写しも直す**。
  区分 F に、既存プロジェクト向けの任意の行「設計文書の場所」を足した（R5）。
- 注意: Skill 1 で始めたプロジェクトに後からコードが増えた場合は、この対象外には当たらない
  （`project-definition.md` が存在する）。その場合の振る舞いは D10。

### D10. 定義が既にあっても、ハーネスが未作成か削除済みなら最初からやり直す（2026-09-20）

- 作者の言葉: 「スキルやエージェントが作成されていないor削除されているのであれば、最初からやり直す」
- `docs/project-definition.md` が既にある状態で Skill 1 が呼ばれたとき、Skill 2 の生成物（対象プロジェクトの
  skill や Agent）がまだ作られていない、または削除されているなら、新規と同じ対話を最初から行う。
- 提示した3択（差分だけ聞いて更新／再実行は扱わない／旧版を退避して作り直す）はそのまま採用されず、
  ハーネスの有無で振る舞いを分ける形になった。
- ハーネスが存在する場合の振る舞いは D11。
- ハーネスの有無の判定（導出。実装時に確定）: Skill 2 の根拠記録 `docs/agent-architecture.md` と、
  そこに一覧された生成ファイルの存在で判定する。Skill 1 は基盤中立（共通仕様 C2）なので、ファイルの有無だけで判定する。
- やり直すときは、既存の `project-definition.md` を置き換えることをユーザーに伝えてから進める。

### D11. ハーネスが既にあるなら、Skill 1 は何もせず通常の設計作業へ案内する（2026-09-20）

- Skill 1 は「開幕」専用と割り切る。更新モードは持たない。
- ハーネスがあるプロジェクトでは、定義の変更（決済を足すなど）はハーネスの設計書駆動の流れの中で、
  設計の対話役である主セッション（Skill 2 の H17）が `project-definition.md` を直接更新する。
- Skill 1 はその旨と、「C（技術）・D（リスク）・E（環境）が変わったら `project-design-harness` を再実行する」ことを
  案内して終了する。
- 退けた案: ユーザーに確認してやり直しも選べるようにする案（作り直した定義と既存のハーネス・設計文書・コードが食い違う）／
  ハーネスがあっても差分更新モードで動く案（開幕専用という単純さが失われ、D9 の方向と逆になる）。
- Skill 2 への逆算: 定義を更新するときの決まり（状態キーの書き方、再実行の条件）を、Skill 2 が生成する
  `CLAUDE.md` か skill に書いておく必要がある。[project-design-harness.md](project-design-harness.md) の H27。

### D12. 対象の種類は限定しない。区分 B は一般的な問いで捉える（2026-09-20）

- 作者の言葉: 「例示としてWebアプリケーションとしただけで、ElectronでもC++のLib作りでもよいと思う」
- 「境界は不要」の意味は確認済み。対象の種類を限る線引き（Web かどうか）が不要、という意味。
  区分 B（システム境界）の把握そのものは残す。方針書 3・4・9.1 章とこれまでの裁定は変わらない。
- 区分 B の例示を Web 固有のもの（UI・Backend・DB・認証・デプロイ）から、種類を問わない問いに置き換える:
  利用者との接点／処理／データの保存先／外部とのやりとり／配布・実行場所。該当しないものは `none`。
  例: C++ のライブラリなら「接点＝公開 API、保存先 none、配布＝パッケージ」。
  Web サービスはその典型例として `references/` に載せる。
- 「難しければ止めてほしい」への回答: 難しくないと判断した。入力契約 A〜H は Web 固有の概念に依存しておらず、
  Skill 2 の検証も「verify 相当の単一コマンド」で配線するので（H6）ツールチェーンを問わない。
- 正直に残る制約:
  - 共通仕様 C3（実プロジェクトで試すだけ）により、試していない種類のプロジェクトでの品質は未確認のまま公開される。
    README に試用済みの範囲を書く。
  - Skill 2 の H25 により、対象プロジェクトの言語に関係なく hook のために Node.js が前提になる。
- 退けた案: Web サービス専用にする案。

### D13. 範囲外の情報は深掘りせず、区分 H に持ち越しメモとして残す（2026-09-20）

- ユーザーが詳細な機能、画面のイメージ、API やテーブルの案などを話したら、要点を区分 H に `deferred` として書き留める。
  追加の質問はしない。
- ユーザーには「詳細は次の段階（Skill 3）で扱うので、今はメモとして残す」と一言伝える。
- 話の中に入力契約に効く情報が含まれていれば、該当の区分に反映する
  （例:「クレジットカードで払えるようにしたい」→ 区分 D の外部作用）。
- 退けた案: 記録せず範囲外だと伝えるだけの案（Skill 3 で同じ話をもう一度することになる）／
  別ファイルにすべて書き留める案（整理し始めると詳細要件に踏み込む入口になる。方針書 9.2）。

### D14. Skill 1 自身のファイル構成と対話の流れ（2026-09-20、導出）

作者の裁定ではなく、D1〜D13 と共通仕様 C1〜C5 から導いた実装上の構成。実装時に過不足があれば直す。

```text
project-design-opening/
├── SKILL.md                       手順の本体
├── references/
│   ├── input-contract.md          入力契約 A〜H の各項目の意味と、埋まったと言える基準（D5・Skill 2 の H11）
│   ├── boundaries.md              区分 B の一般的な問いと、種類別の典型例（Web・CLI・ライブラリ・デスクトップ）（D12）
│   ├── tech-selection.md          技術選択モードと、構成の決め方（D3・D6・D7）
│   └── risk.md                    区分 D の聞き方。外部作用・不可逆操作・機微情報の例（D4）
└── assets/
    ├── project-definition.template.md   成果物の雛形（D8）
    └── example.md                        記入例
```

対話の流れ:

1. 前提の点検。既存コードがあり定義が無ければ対象外（D9）。ハーネスがあれば設計作業へ案内（D11）。
   定義だけがあれば、置き換えることを伝えてやり直す（D10）。
2. アイデアを聞く。話された内容から A〜H のうち読み取れる項目を埋める。範囲外の話は区分 H に持ち越す（D13）。
3. 不足している項目だけを聞く。A〜H は質問票ではなく点検表として使う（D5）。
4. 目的とシステム境界が見えたら、技術選択モードを聞き、構成単位で技術を決める（D7）。
5. 仮定で埋めた項目を一覧で見せ、まとめて確認してもらう。
6. 全項目が状態を持ったら `docs/project-definition.md` を `status: complete` で書き出す（D8）。
7. 次の段階として `project-design-harness` を案内する。

### D15. 実装時に確定した細部（2026-09-20、導出）

作者の裁定ではなく、初版を書く過程で D1〜D14 から導いて確定した細部。試用で不都合があれば直す。

- 区分 B の項目は6つ。D12 の5つの問いに「利用者の識別（認証）」を加えた。
  元方針 2 章と Skill 2 の H11 が認証の有無を含めており、種類を問わず成り立つ問い（CLI なら `none`）であるため。
- 区分 C の6項目と区分 D の3項目は `deferred` にできない。D3（6項目は常に決める）と D4（収集は必須）の帰結。
  ユーザーが決められない場合は、推測を提案して `assumed` の確認を取る。
- `assumed` は「推測し、ユーザーが確認したもの」に限る。確認を取っていない推測は成果物に書かない。
- 対話を途中で切り上げる場合は `status: draft` で書き出し、状態の付いていない項目を区分 H に列挙する。
  Skill 2 は `draft` の定義では動かない（Skill 2 の H20）。
- 区分 D は、完成したシステムが行う操作だけでなく、開発中の Agent が触れてしまう可能性のある操作も対象にする
  （テストの実行で実在の人にメールが飛ぶ、など）。ハーネスが守るのは開発中の事故であるため。
- ツールチェーンが複数ある場合は、区分 C の表を構成要素ごとに分ける（Skill 2 の H15 の判定材料になる）。
