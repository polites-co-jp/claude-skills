# project-design-opening 設計裁定記録

Skill 1（project-design-opening）の設計を詰める過程で確定した判断を、確定した順に記録する。
元になった設計方針は「Skill 1 設計方針 — Claude引き継ぎ用」（2026-09-19 のセッションで提示）。

## 前提（調査で確定した事実）

- リポジトリ `polites-co-jp/claude-skills` はコミットゼロ・`project-design-opening/` は空。既存構成への適合制約はない。
- 作者の環境は `~/.agents/skills` + `.skill-lock.json`（`npx skills` エコシステム）でスキルを管理している。
- 作者の既存自作スキルは `SKILL.md` + `references/` + `assets/` 構成、本文は日本語。

## 裁定

### D1. `project-design-opening` は Skill 1 そのものの名前（2026-09-19）

- `project-design-opening/SKILL.md` が Skill 1 本体。スキル名も `project-design-opening`。
- Skill 2 / Skill 3 は `claude-skills` 直下に兄弟フォルダとして並べる。3スキルを束ねる親フォルダは作らない。
- 退けた案: `project-design-opening/skills/<skill名>/` のスイート構成。
- 帰結: 3スキルの関係（成果物の連鎖）を説明する場所はリポジトリ直下の README になる。

### D2. Skill 2 を先に企画し、Skill 1 の収集項目はそこから逆算する（2026-09-19）

- Skill 1 の終了条件は「Skill 2 が追加質問なしで設計できる状態」だが、Skill 2 が未定義のままでは判定できない。
  そこで Skill 2 の企画（何を入力に何を決めるか）を先に固め、Skill 1 の収集項目と終了条件をそこから逆算する。
- Skill 2 の置き場所は `project-design-harness/`（作者が作成済み）。スキル名も `project-design-harness`。
- 退けた案: Skill 2 の入力契約を仮のチェックリストとして Skill 1 側で先に明文化する案／LLM の自己判定に任せる案。
- 帰結: 今回のスコープは Skill 1 単体から「Skill 2 の企画 → Skill 1 の設計」の順に広がる。
  Skill 2 の裁定は `docs/decisions/project-design-harness.md` に記録する。

### D3. Skill 1 の技術粒度は「ツールチェーンが決まるところまで」（2026-09-19、Skill 2 の H6 から逆算）

- Skill 1 が終了時点で確定させる技術: 言語、ランタイム、パッケージマネージャ、主要フレームワーク、DB 種別、デプロイ先種別。
  該当する境界が存在しない項目（例: DB なし）は「なし」で確定とする。
- 理由: Skill 2 は permissions と hooks に具体的なコマンド名を書く。本実装エージェントも初回に作るため、穴のままにできない。
- 元方針 4 章の「具体的な選択は、必要な場合に技術選択モードに従って決定する」の「必要な場合」は、この粒度で確定した。
  上記6項目は常に決める。それより細かい選択（テストランナー・linter・ORM・UI ライブラリ・REST/GraphQL など）は Skill 3。
- 決め方は元方針 5 章の技術選択モード（Mode 1: 候補提示 / Mode 2: 委任）をそのまま使う。

### D4. Skill 1 はリスク情報（外部作用・不可逆操作・機微情報）を収集する（2026-09-19、Skill 2 の H9 から逆算）

- 元方針 2 章の「Skill 1 で扱うもの」はシステムの構成要素（UI / Backend / DB / 外部 API / 認証 / デプロイ）が中心で、
  「その構成要素が外の世界に何をするか」を含んでいなかった。これを収集項目に加える。
- 収集する内容:
  - 外部作用: 開発中や運用中に、システムの外へ影響が出る操作（メッセージ送信、デプロイ、課金・購入、外部 API への書き込みなど）。
  - 不可逆・機微な操作: データ削除、本番データの変更、認証情報の扱い、全体公開など。
  - 秘密情報・個人情報の有無。
- 理由: Skill 2 はこの情報から推奨プリセットを決め、どのプリセットでも外さない Policy の下限（承認ゲートと禁止ルール）を書く。
  情報が無ければ、Skill 2 がユーザーにプロジェクトの基本情報を聞き直すことになり、Skill 1 の終了条件を満たさない。
- 粒度: 「何があるか」まで。個々の操作の承認フローや権限設計は Skill 2 の仕事。

### D5. 終了条件は「入力契約 A〜H の全項目が状態を持つこと」（2026-09-20、Skill 2 の H11 から逆算）

- D2 で保留にした終了条件の判定方法が、これで確定した。
- `docs/project-definition.md` は Skill 2 の入力契約と同じ A〜H の8区分を持つ
  （A 目的とスコープ／B システム境界／C 技術／D リスク／E 環境／F リポジトリ構成／G 運用前提／H 未決・持ち越し）。
  区分の中身は [project-design-harness.md](project-design-harness.md) の H11。
- Skill 1 は、全項目が「決定／仮定（ユーザー確認済み）／なし／持ち越し」のいずれかになったら終了する。
- 元方針に対して増える収集項目は D（リスク）・E（環境）・G（運用前提）。
- 元方針 6 章の質問方式は変えない。アイデアの説明から読み取れる項目は聞かず、不足している項目だけを聞く。
  A〜H は質問票ではなく、埋まったかどうかを確かめるための点検表として使う。
