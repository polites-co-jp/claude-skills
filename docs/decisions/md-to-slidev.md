# md-to-slidev 設計裁定記録

`md-to-slidev` の設計で確定した判断を、確定した順に記録する。
元の仕様は作者が用意した「プレゼンテーション生成Skill — Skill Creator引き継ぎドキュメント」（2026-09-24 に会話で受領）。
関連するスキル: 作者の環境にある `presentation-storyline-design`（このリポジトリの外。`~/.agents/skills/` に導入済み）。
共通の公開仕様は [common.md](common.md)。

## 裁定

### M1. 出力先は Slidev（2026-09-24）

- 仕様書の「3dev などの Markdown-to-Slide 環境」を、フォルダ名 `md-to-slidev` から Slidev の誤記と解釈した。
  前提として作者に提示し、指摘はなかった。
- スキル本文は日本語（C1）。

### M2. 単体で完結し、`presentation-storyline-design` のノウハウは項目ごとに選んで取り込む（2026-09-24）

- 作者の言葉: 「今回のマークダウンの指示と競合がない場合は、既存のノウハウとして、積極的に採用したい。
  ただ、すべてを登録するのは違うので、この要件はどうかとAskUserQuestionで確認してください」
- 内容分析からスライド分割までを md-to-slidev の中に持つ。storyline を呼び出す前提にはしない（`npx skills` はフォルダ単位で配るため）。
- 取り込む項目:
  - 前提の確認: 目的・聴衆・持ち時間・使われ方が入力から読めなければ、判断が変わるものだけ聞く。読めない項目は「仮定」と明記して進む
  - ストーリーの型: 結論先行型／対比型／段階型を選んでからセクションを組む
  - 消えては困る情報: 数値・固有名詞・定義・手順・比較の軸・URL・引用は、文字を減らすときも画面に残す
  - 文字量の目安: 本文の要素は3つ前後、1要素は全角20字程度まで。超えたら分割か発表者ノートへ
  - 結論だけで話が追えるか: 各スライドの結論行だけを順に読み、飛躍・重複がないかを検査する（storyline の Horizontal Logic Test を結論行に適用）
  - 発表者ノート: 画面から外した根拠・具体例・つなぎを Slidev の発表者ノートに書く
  - 本編外の情報の一覧: 入力にあったが本編から外した情報と、その置き場所を報告する
  - 想定時間の照合: 各スライドの想定時間をノートに書き、持ち時間と照合する。持ち時間が分からないときは行わない
- 取り込まない項目: 中心メッセージ（1文の主張＋キーメッセージ3つ）／聴衆の変化（現状・目標・反論）／
  体言止めの例外（否定・条件・比較・因果は文にする）／既存スライドの見直しモード
  - 体言止めは仕様書どおり一律を基本にする。
  - 入力は「スライド化されていない Markdown」に限る（仕様書 1 章）。

### M3. タイトルは話題名、結論行が主張の2段構成（2026-09-24）

- 仕様書（タイトル 32px → 結論 28px）と storyline（タイトル自体を主張にし、ラベルを禁止）が競合していた。
- 作者の裁定: 仕様書どおり2段。タイトルは話題名（例:「バイブコーディング」）、その下の結論行が主張。
  storyline の「主張にする」ルールは結論行に適用する。
- 退けた案: タイトルを主張にして結論行を消す案（標準レイアウトとタイポグラフィが変わる）／両方を主張にする案（重複して文字が増える）。

### M4. 汎用のプレゼン生成スキルとし、特定テーマの要件は対象外（2026-09-24）

- 作者の言葉: 「マークダウンの引き渡し範囲を誤った。現在の議題は汎用的なプレゼン生成スキルなので、15-34以降の特定の内容に偏ったスライドの要件は対象外とする」
- 仕様書の 15〜34 章（Context・Token・Model・Claude Code・IBM Bob・デモ設計など）はスキルに入れない。
  41 章のうち AI 開発・Claude Code・Bob に触れる段落も同じ扱い。
- 35〜43 章のうち汎用の部分（生成手順、図解を優先する内容、強調順位、避けること、画像生成の扱い、優先順位、拡張性、品質チェックリスト）は残す。
  「同じ概念には同じ図を使い回し、段階的に更新する」は汎用ルールとして残る。

### M5. 出力は slides.md と、スキルに同梱する部品一式（2026-09-24）

- 作者の裁定: 推奨どおり。スキルが Slidev 用の部品（変数で色・フォント・余白を持つ CSS、layouts、SVG の Vue コンポーネント）を同梱し、
  生成時に作業フォルダへ置く。slides.md は部品を呼び出すだけにする。
- 42 章（デザインとコンテンツの分離）は、CSS と部品を差し替えればコンテンツ側を変えずにデザインを変えられる形で満たす。
- 退けた案: slides.md だけで図を Mermaid で描く案（線幅・角丸・配置を仕様どおりに制御しにくい）／slides.md だけで図を直接 SVG で書く案（再利用と差し替えができない）。
- 提示済みの代償: 同梱するコードが増え、Slidev の更新に追従する手間がかかる。

### M6. 利用者への確認はスライド計画で一度だけ（2026-09-24）

- 分析のあと「セクション、各スライドのタイトル・結論・表現方法・レイアウト、本編外にした情報、仮定」を一覧で見せて承認を取り、
  その後は描画とファイル書き出しを一気に行う。
- 前提（目的・聴衆・持ち時間・使われ方）が入力から読めず判断が変わるときの質問は M2 のとおり別に行う。読めるときは計画の1回で済む。
- 退けた案: 確認なしで完成まで作る案（分割がずれていたとき全体を作り直す）。

### M7. Slidev プロジェクトが無ければ、確認のうえ最小の雛形を作る（2026-09-24）

- カレントに Slidev プロジェクト（`package.json` に slidev）があればそこへ slides.md・style・layouts・components を置く。
- 無ければ利用者に確認したうえで、指定フォルダに `package.json` と部品を書き出し、`npm install` で動く状態にする。
- 既存の部品ファイルがあれば、上書きする前に確認する。
- 退けた案: ファイルを書くだけで雛形は作らない案／`npm create slidev` に任せる案（対話式でエージェントから扱いにくい）。

### M8. 生成後はビルドを通してから報告する（2026-09-24）

- `slidev build`（または export）を実行し、コンポーネントの参照エラーや構文エラーが無いことを確かめてから報告する。
- 見た目（はみ出し・文字の重なり）はビルドでは分からないので、利用者が確認する点として報告に書く。
- 退けた案: 画像を書き出して目視する案（Playwright の導入が要る）／チェックリストの自己点検だけの案。

### M9. 画像は生成しない。候補を報告するだけ（2026-09-24）

- 図・矢印・ボックス・ラベルはすべて SVG/CSS の部品で作る。
- 抽象的なイラストが効くと判断したスライドは、画像の置き場所を空けずに文字と図だけで成立する形で作り、
  報告で「イラストを足すならこのスライドにこういう絵」と候補を列挙する。
- 退けた案: 画像生成ツールがあれば生成して埋め込む案（環境で出力が変わり、生成画像のトーンが白基調と合わないことがある）。

### M10. 同梱の例を CI でビルドする（2026-09-24）

- `assets/` に例の入力 Markdown と、そこから作った slides.md を置く。CI で部品一式とその slides.md を `slidev build` する。
- C6 の「最小限の回帰テスト」をこのスキルにも適用した形。部品を直したときの壊れを検知でき、例は利用者向けの完成例にもなる。
- 提示済みの代償: CI に Node と Slidev の導入が増え、1〜2分伸びる。

### M11. 入力は箇条書きの Markdown だけ。storyline の設計書は受け付けない（2026-09-24）

- 常に分析から始める。`presentation-storyline-design` の設計書を渡されても、設計書としては解釈しない。
- 退けた案: 設計書の形なら分析を飛ばして描画から始める案。
