# slide-design-review 設計裁定記録

`slide-design-review` の設計で決めた判断を、決めた順に記録する。
元の仕様は作者が用意した「Slidev デザイン改善ループ構築指示書」（2026-09-25 に会話で受領）。
共通の公開仕様は [common.md](common.md)。関連するスキルは同じリポジトリの [md-to-slidev](md-to-slidev.md)。

> **状態**: 仕様書には「構成案を提示し、確認を取ってから実装する」とある。作者が同席しない自律実行だったため、V1〜V14 は実装後に作者へ確認した。
> 2026-09-25、AskUserQuestion で「このまま確定」の裁定を得た。
> 仕様書の「最終的な成功条件」（1ページを指定して、レンダリング → レビュー → 修正 → 再レンダリング → 再レビューを、改善が十分になるか上限に達するまで回し、各反復を追跡できる）は、
> md-to-slidev の完成例の7ページ目で実際に回して確かめた（[../../slide-design-review/assets/example/](../../slide-design-review/assets/example/)）。

## 裁定

### V1. 汎用のスキルとして、リポジトリ直下の `slide-design-review/` に置く（2026-09-25）

- 作者の依頼は「`E:\develop\claude-skills\slide-design-review` にこのスキルを作る」。仕様書の例 `.claude/skills/slide-design-review/` は、利用者がプロジェクトへ入れるときの導入先として README に書く（C5 の手動コピー）。
- 仕様書の「現在の Slidev プロジェクトを調査する」は、スキルを使う時点のプロジェクトの調査と読み、ワークフローの Step 0（ページの一覧、`playwright-chromium` の有無、規約メモ、ソースの状態）に入れた。
  作者の手元の `E:/memo/presentation/slidev` は `package.json` の無い古い雛形で、調査と検証の対象にはしなかった。
- スキル本文は日本語、レビューの見出しは仕様書どおりの英語を固定のキーとし、中身は利用者の言語（C1）。

### V2. Claude Code 専用。役は `.claude/agents/` ではなく、同梱の指示書を subagent に渡して分ける（2026-09-25）

- 仕様書の「実装とレビューを分離する」を、主セッションが Agent ツールで毎回新しい subagent（`general-purpose`）を呼び、同梱の指示書（`references/reviewer.md` など）を読ませる形で実現する。
- 退けた案: `.claude/agents/` に Agent 定義を配る案（`npx skills` はスキルのフォルダ単位で配るので届かない。`.claude/` は保護パスで書き込みに確認が要る）／
  主セッションが自分でレビューする案（自己評価の甘さ。仕様書の「自己評価バイアスへの対策」に反する）。
- 代償: レビュー役・比較役に「ソースを読まない」を守らせるのは指示書だけで、ツールの制限では守れない。
- C2 の harness と同じく、基盤中立にはしない。

### V3. 役は3つ。進行役（主セッション）・レビュー役・実装役に、比較役を足す（2026-09-25）

- 進行役はスライドを直さず、デザインの良し悪しも判定しない。レンダリング、記録、終了の判定だけを行う。
- 比較役を足した理由: 「前回からほとんど改善しない」を、独立したレビューの件数や点数の比較で判定すると、レビューのぶれで誤る。
  前後の画像を、どちらが新しいかを伏せて A・B として並べ、どちらが良いかを直接判定させる（ブラインドの一対比較）。A・B の割り当ては毎回ランダム。
- レビュー役には前回のレビューも変更記録も渡さない（仕様書の「前回の評価より、今どう見えるかを優先」）。毎回新しい subagent なので記憶も持たない。

### V4. レンダリングは Slidev 公式の `slidev export --format png --scale 1` を同梱スクリプトで包む（2026-09-25）

- `scripts/render.mjs` がプロジェクトの Slidev の CLI を直接呼ぶ。キャンバス等倍（1920×1080 なら 1920×1080）。
  同時に Slidev のパーサで、ページ番号 → ソースのファイル・行・layout・タイトルの対応（`pages.json`）を作る。
- `slidev export` は書き出す前に出力先を消すので、一時フォルダに書かせてから移す。
- 退けた案: dev サーバーを立てて自前の Playwright で撮る案／`slidev build` した静的サイトを撮る案。どちらも Slidev の内部の URL や DOM に依存し、版の更新で壊れやすい。
- 代償: `playwright-chromium` がプロジェクトかグローバルに要る（Slidev と同じ探し方）。無ければ、プロジェクトに入れる（推奨）・グローバルに入れる・やめる、を利用者に聞く。
  作者の環境にはグローバルの `@playwright/test` があるが、Slidev はそれを使わない。
- 確認済み（2026-09-25、Slidev 53.0.0、playwright-chromium 1.63.0、Windows 11）: 13ページの書き出しが 6〜8 秒。

### V5. 修正のたびに全ページを書き出し、前後を画素で比べて影響の範囲を出す（2026-09-25）

- 同じソースを2回書き出すと PNG がバイト単位で一致することを確かめた（上と同じ環境、13ページすべて）。だから差は本当の変化。
- `scripts/compare-renders.mjs` が、変わったページ・変わった画素の割合・変化を囲む矩形を出す。PNG の復号は依存を足さずに Node.js の zlib で行う。
- 対象外のページが変わったら、比較役で後退していないかを見る。後退していれば戻し、「共通のファイルに触らず、このページの中で直す」条件でやり直す。
- 仕様書の「共通 CSS やテーマを変えるときは、ほかのページへの影響を確認する」を、実装役の自己申告ではなく画素の比較で満たす。

### V6. 終了の条件（2026-09-25）

- (1) レビューで Critical・Major が両方なし (2) 比較役が `same` → 戻して終了 (3) 新しい方が悪い、または新しい方にだけ破綻 → 戻して終了
  (4) 同じ箇所の同じ性質について、指摘の向きが2回入れ替わる（往復） → 終了 (5) 修正が上限に達する。
- 上限の既定は**修正3回**（レビューは最大4回）。1回の修正で最優先の1〜2件を直すので、3回でレビューの上位の問題を一巡する。それ以上は、独立したレビューのぶれで指摘が往復しやすい。
  利用者が回数を言えば従う。
- 差なしの変更も戻す。見た目に効かない変更は、ソースを複雑にするだけ。
- (4) は実地で直した。最初は「前回の修正を逆向きに戻す指摘」で終了としていたが、7ページ目の2回目のレビューが、修正1で大きくしすぎた箱の高さを詰める指摘を出した。
  これは行き過ぎの量の調整で、止めるのは誤り。1回の逆向きは数えず、向きが2回入れ替わったら往復とみなす形にした。
  同じ例の最後のレビューは、修正2で詰めた高さを再び広げる向きの案を出しており、上限の3回で止まったことで往復に入らずに済んだ。

### V7. 1回の修正で直すのは、最優先の1件（同じ場所・同じ原因なら2件まで）（2026-09-25）

- 仕様書の「一回のレビューですべてを直そうとしない。大きな問題から順番に」。どの変更が効いたか・後退の原因はどれかを切り分けられるようにする。

### V8. 実装役の範囲（2026-09-25）

- 内容（主張・事実・数値・固有名詞）を変えない。情報を消さない（画面から外すなら発表者ノートへ）。
- ページの分割・追加・削除・並べ替え・非表示はしない。ページ番号がずれて、比較と記録が壊れる。必要なら提案として返す。
- 直し方は、ページの中 → ページだけに効くスタイル（規約が許すとき）→ 共通のファイル、の順に検討する。
- プロジェクトの規約を先に読んで従う。md-to-slidev で作ったデッキ（`md-` で始まる layout がある）なら、`slides.md` に `<style>`・色・サイズを書かない決まりを、進行役が規約メモに入れて渡す。
- レビューの数値は目視の概算なので、ソースの実際の値を確かめてから直す。ほかのページと共通の見た目をこのページだけ変えたときは、デッキ内で揃わなくなることを提案に書く（どちらも実地で足した）。
- 実装役はレンダリングを見ない。評価は別の役が行う。

### V9. 記録はデッキの隣の `design-review/` に残す。画像と退避は git で追跡しない（2026-09-25）

- ページごとに `review-k.md`・`changes-k.md`・`diff-k.patch`・`compare-k.md`・`rk.png`・経過表 `log.md`。仕様書の「各反復で何を問題とし、何を変えたかを追跡できる」を満たす。
- `design-review/.gitignore` で `*.png`・`.renders/`・`.snapshots/` を追跡から外す。1枚 60〜100KB の画像が反復とページの数だけ溜まり、リポジトリが膨らむため。Markdown の記録と差分は残る。
- 修正の前に `scripts/snapshot.mjs` でソースを退避し、戻すときはそこから戻す。git の有無に依存しない。修正のあとに作られたファイルは消さずに退避先へ移す。
- 退けた案: 会話に残すだけ（次のセッションで追えない）／画像も追跡する。

### V10. デザインの共通化は作らない。症状と効いた直し方を `patterns.md` に貯める（2026-09-25）

- 仕様書の「最初からテンプレートを完成させない。個別の改善から良いパターンを見つけ、後から共通化する」に従う。
- 同じ症状が3ページ以上に出たら「共通化の候補」に挙げる。原因が共通の部品（layout の既定の文字組み、CSS の変数）にある症状は、同じ構造のページすべてに出るので、1ページでも候補にする（実地で足した）。
- 共通化そのもの（テーマ・部品の改修）は、この記録を見て人が決める。

### V11. 全ページのときは、1ページのループを先頭から順に回す（2026-09-25）

- 並列にしない。修正が同じ共通のファイルに触りうるため。
- 最初のレビューで Critical・Major が無いページはそこで終わるので、直すのは問題のあるページだけになる。
- 始める前に、ページ数と、1ページあたり最大でレビュー4回・修正3回・比較3回の subagent 呼び出しになることを伝える。依頼がそのとおりなら確認を待たない。
- 仕様書の「全ページの自動改善を最初から複雑に作らない」に従い、1ページの手順の繰り返し以上のことはしない。

### V12. レビューの形とレビュー基準（2026-09-25）

- 見出しは仕様書の形（Overall assessment／Critical・Major・Minor issues／Priority 1〜3／Positive aspects）。Priority は最大3つ、Issues は7件程度まで。
- 各 Priority に、問題・なぜ問題か・改善案・直ったと分かる見え方を、画像の上の場所を添えて書く。「直ったと分かる見え方」は仕様書に無い項目で、実装役の目標と次のレビューの判断材料になるので足した。
- 基準（`references/review-criteria.md`）は、仕様書の8観点ごとに見るべき症状を具体的に書き、見る順番（3秒の第一印象 → 目を細める → 構造線 → まとまり → 文字 → 量 → 一つずつ外す → まとめる）、
  重大度の定義、「素人っぽく見える」典型の症状と直し方の方向の表を持つ。日本語の文字組み（泣き別れ、行頭の約物、文節での改行）も入れた。
- Positive aspects は実装役に「壊してはいけないもの」として渡す。

### V13. テストはスクリプトだけ。レビューの質は機械テストにしない（2026-09-25）

- `slide-design-review/tests/scripts.mjs`: 合成した PNG での復号と画素比較、`compare-renders.mjs`、`snapshot.mjs` の退避・差分・復元、`render.mjs` の終了コード、
  そして md-to-slidev の完成例を実際に書き出して、寸法・同じソースでの一致・1枚だけ直すとそのページだけが変わること、を確かめる。CI に足した（C6・M10 の延長）。
- レビュー・実装・比較の振る舞いは決定的でないので、C3 のとおり実際に使って確かめる。
- CI の Node.js を 20 から 22 に上げた。Slidev 53 は `engines` で 22.12 以上を求めている。
- 代償: CI に Chromium とその依存ライブラリの導入が増え、1〜2分伸びる。

### V14. 実装時に問わずに決めた細部（2026-09-25）

- レビュー役に渡す手がかりは、画像・ページ番号・layout の名前・キャンバスの寸法だけ。layout の名前は、区切りのページに本文が無いのを問題にしないため。
- レビュー役と比較役はファイルを書かない。返答の本文を進行役がそのまま保存する。
- 比較役に渡す画像は `A.png`・`B.png` にコピーし、ファイル名（`r1.png` など）から新旧が分からないようにする。
- ページのフォルダは `page-NN/`。同じページを2回目に回すときは `page-NN-2/` を作り、前の記録を消さない。
- 書き出しの `--wait 300`・`--timeout 60000` は、Web フォントの読み込みを待つための控えめな値。
- 同梱の完成例は、実地で回した7ページ目の記録そのもの（画像4枚を含めて約 400KB）。
