# 文体と本文の組み立て

SKILL.md の Step 3〜4 で、タイトル・結論・本文・ノートを書くときの規則。末尾の「生成版と確定版の差」は、この Skill の出力を利用者が手で直した実例で、規則の根拠になっている。迷ったら実例に寄せる。

## タイトル: 話題名にする

タイトルは「このスライドが何の話か」を示す見出しで、主張は結論欄に書く。最上位の箇条書きが主張の文になっていても、タイトルにはその話題を名詞句で取り出す。

- 名詞句で、全角15字程度まで。「トークン」「Skills」「仕様書の書き方」「バイブコーディングの限界」「人とAIの業務分担」
- 同じ話題が続くときは、続きと分かる名前を付ける。「バイブコーディングの限界」→「バイブコーディングの限界の理由」
- 段階を追って積み上げるスライド群には、通し番号を前に付ける。「Lv1. 検索の上位互換としての生成AI」「Lv2. プログラミングの補助としての生成AI」
- 話題名だけでは足りないときは、2つの形を使う
  - 「話題：要点」の1行。「今日のゴール：開発の「判断」と「作業」の分離」
  - 2行目に一言を足す（YAML の `|-` で改行する）。`従来の開発` の下に `要件定義からリリースまでの全工程を人間が担当`
- タイトルに句点・読点で続く2文を入れない。「〜がある。コスト、〜」のような形は、話題名と結論に分ける

## 結論: 右の結論欄に、意味の切れ目で改行して置く

結論は右側の結論欄（幅 440px、30px）に出る。1行に入るのは全角12字程度。

- YAML の `|-` で書き、文節の切れ目で改行する。2〜5行
- 1行は全角12字程度まで。13字を超える行は、意味の切れ目でもう一度折る
- 強調したい語句は、前後に空行を置いて1行で独立させてよい

```yaml
conclusion: |-
  生成AIは文脈を考慮し
  直接の答えを返す

  「賢い検索」

  と捉えている人が存在
```

- 中身の導き方は [analysis.md](analysis.md) の「結論の導出」。体言止めか「〜する」で終える。「〜を担保」「〜が人間の仕事」のように、何が起きるか・誰が担うかで言い切る
- 比喩で結論を言わない（「店は変わらず、中のシェフが入れ替わる」ではなく「適切なモデル選択が出力精度を担保」）

## 本文: 見出し語と中身の階層で組む

本文は、画面だけ読んでも分かる密度にする。発表しながら配布もされる資料が前提。

- **1段目は見出し語、2段目は中身**。1段目に用語・対象・観点（「検索」「生成AI」「人間」「実装Agent」「対策」）を置き、2段目にその定義・性質・例を置く
- **定義は冒頭に**。用語を扱うスライドは、1段目に用語、2段目に定義を置くか、`用語 = 定義` の1行で始める（「トークン = 「よく出てくる文字列のかたまり」」「コンテキストウィンドウ = コンテキスト上限」）
- **1項目に1つの内容**。「・」でつないだ3つ以上の名詞は、それぞれ1行に分ける（「要件定義書・仕様書・設計書・テスト仕様書」→ 4行）。2文ある項目は2行に分ける（「この5つの活動は開発手法に影響されない」「変わるのは順番と粒度」）
- **例は `ex)` で始める**。`- ex)` の下に具体例を並べるか、`ex) GitHub、GoogleDrive、社内システム 等` の1行にする
- **手順は番号付きリスト**（`1.` `2.` `3.`）
- **理由を書く**。「必要なときだけ読み込まれる」の下に「コンテキストウィンドウを占有しない」のように、なぜそうなるかを1行足す。理由が入力にあれば画面に出す
- URL・製品名・数値は画面に残す
- 量の目安: 1段目 2〜5項目、全体で12行程度まで、1行は全角25字程度まで。超えたら、分割するか `md-wide`・`md-shots` にして横幅を使う
- 行内で折りたいときは `<br />` を使う

1段目を並べるだけの薄い本文（「- 開発速度が速い。1時間で動くものができる」の1行だけ）にしない。入力の3段目・4段目にある定義・例・理由を2段目へ引き上げて厚くする。

## 用語: 正式名で統一し、比喩を画面に出さない

- 製品や機能は、その製品での正式名を使う（Rules・Skills・Agents・MCP・Hooks）。「ルール・手順書・分担・接続口」のような言い換えの概念名を作らない
- 同じものを指す語は資料全体で1つに揃える。総称と略称が混ざるなら正式な方に寄せる（「AI」と「生成AI」が混ざる資料では「生成AI」）
- 技術用語で言い切る。比喩（机・本棚・シェフ・馬具・「毎朝記憶がリセットされるエンジニア」など）は、タイトル・結論・本文・図のラベルに使わない。入力が比喩を指定していても、画面では「机 → コンテキストウィンドウ」「机に載る → プロンプトに載る」のように技術用語に置き換え、比喩は発表者ノートで口頭の補助にとどめる
- 講演の段取りや自分の話し方に触れる語（「今日は一言だけ」「後半で説明」「（別資料）」「発表者自身の構成」）を画面に出さない。必要ならノートへ
- 評価語（勝者・最適・最強・圧倒的）と無条件の礼賛を使わない

## 発表者ノート: 短く、つなぎと要確認だけ

各スライドの末尾の HTML コメントに、1〜3行で書く。

- 書くこと: 前後のスライドへのつなぎ、発表前に確認が要る事項（「要確認: 登場時期」）、画面から外した比喩（入力が指定していたもの）
- 書かないこと: 台本、画面の繰り返し、想定時間
- 書くことが無いスライド（表紙・区切りなど）はノートを付けない

入力の4段目以降にあった説明は、定義・例・理由なら本文へ引き上げ、話し方の指示（問いかけ・挙手・伏線）ならノートか slide-plan.md の「本編に入れなかった情報」に回す。

## 生成版と確定版の差（実例）

「生成AIによる仕様書駆動開発の基本」を、旧版のこの Skill で生成し、利用者が確定させたときの差。

### タイトル

| 生成版 | 確定版 |
|---|---|
| AIは文字ではなくトークン単位で処理する。トークン数が机の消費量でありコスト | トークン |
| Skills は、AI に「仕事のやり方・手順・専門知識」を与える仕組み | Skills |
| AIに渡す仕様書は1ページでよい。ただし、迷う余地をなくす | 仕様書の書き方 |
| 従来の仕様書とAIに渡す仕様書は、読み手が違うので書き方が違う | 従来の仕様書との違い |
| 仕様書駆動にも限界がある。コスト、間違いも速くなる、暗黙知は書けない | 仕様書駆動開発の限界 |
| 開発工程がなくなったのではなく、人間とAIの担当範囲が変わった | 人とAIの業務分担 |
| 検索窓とチャット窓は見た目が同じなので、同じものに見える | Lv1. 検索の上位互換としての生成AI |
| 1. 検索エンジンと生成AIの違い（セクション） | 検索エンジンと／生成AIの違い（番号は自動、2行） |

### 結論

| 生成版 | 確定版（/ は改行） |
|---|---|
| AIに記憶装置はなく、毎回全部読み直している | 継続性のある会話は、/ 毎回全てを送信している / ことに由来 |
| 店は変わらず、中のシェフ（モデル）が半年単位で入れ替わる | 適切なモデル選択が / 出力精度を担保 |
| 繰り返す作業を手順書にし、必要なときだけ机に載せる | skillsは、/ 繰り返す作業を手順化し、/ 必要なときだけ実行させる |
| 実装とテストを別々に仕様書から作り、照合する | 同じ仕様書から / 実装とテストを別々に作り / 品質を担保する |
| 限界があるから、仕様の判断は人間が引き受ける | 限界があるから / 仕様の判断は / 人間が引き受ける |

最後の例のように、生成版の結論の中身が正しければ、改行を足すだけで確定版になる。

### 本文

生成版（Skills）:

```markdown
- 自作だけでなく、公開・共有されている Skill もある
- 普段は棚にあり、必要なときだけ読み込まれる
  - 「仕様書を書け」と言われたときだけ「仕様書の書き方」が机に載る
```

確定版:

```markdown
- Skills
  - 「仕事のやり方・手順・専門知識」を固定する仕組み
- 普段は棚にあり、必要なときだけ読み込まれる
  - コンテキストウィンドウを占有しない
  - ex)
    「仕様書を書け」と言われたときだけ
    「仕様書の書き方スキル」がプロンプトに載る
- 公開・共有されている Skill も存在
  - https://www.skills.sh/ など
```

定義を冒頭に置き、理由（占有しない）を足し、例を `ex)` にし、比喩（机）を技術用語（プロンプト）に替え、URL を残している。

生成版（業務分担）: 「人間は要求と仕様の判断に重点を置く」「AIが実装・テストなどを大きく担う」「受け入れの最終判定は人間」「新しく…が人間の仕事になる」の4行が平らに並ぶ。

確定版: 担い手を見出し語にして組み直す。

```markdown
- 人間
  - 要求・仕様の判断
  - 受け入れの最終判定
  - 生成AIが働く環境（ハーネス）の設計
- 生成AI
  - 仕様書の下書き
  - 実装・テスト
```

生成版（Hooks）: 例はノートにだけあった。確定版: 例を画面に出す。

```markdown
- Hooks
  - 特定の操作の前後に自動で実行される処理
- 生成AIの判断を待たない
  - 忘れず、必ず、機械的に実行される
- ex)
  - 危険なコマンドの実行前に止める
  - ファイル保存後に自動でLintを走らせる
  - コミット前にフォーマットを揃える
```
