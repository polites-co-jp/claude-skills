# 内容の分析と結論の導出

SKILL.md の Step 1〜3 の詳細。入力を読んでから、スライド計画を作るまでに使う。書き方（文体・改行・本文の組み方）は [writing.md](writing.md)。

## 前提の読み取り（Step 1）

`#` の直下、最初の `##` より前の箇条書きが前提。ラベルの書き方は固定しない。次の対応で読む。

| 読み取る項目 | 手がかりになる語 | 判断に効くこと |
|---|---|---|
| 目的 | 目的、ゴール、〜してほしい、合意、承認、理解 | 型の選択、結びの要否 |
| 聴衆 | 聴衆、対象、参加者、〜向け、前提知識 | 説明の粒度、用語の補足 |
| 持ち時間 | 分、持ち時間、枠、質疑 | 枚数の見積もり、論点の数 |
| 使われ方 | 口頭、発表、配布、読まれる、資料として送る | 本文の密度 |

**聞くのは判断が変わる項目だけ。** 目的と使われ方は判断に大きく効くので、読めなければ聞く。聴衆と持ち時間は、読めなければ仮定して進んでよい（仮定は計画に明記）。

- 既定は「発表し、配布もされる」前提の密度。本文は見出し語と中身の階層で、画面だけ読んでも分かるようにする
- 「口頭のみ」と明示されたときだけ、本文を1段目中心に薄くし、定義・例は2段目に1つずつまでにする

前提の箇条書きに、前提以外の内容（表紙のサブタイトル、発表者名、日付）があれば、表紙の `subtitle`・`author`・`date` に使う。

前提に「全体を貫くメタファー」のような比喩の指定があっても、画面には出さない（[writing.md](writing.md) の「用語」）。比喩と技術用語の対応を計画の用語表に書き、比喩はノートに回す。

## ストーリーの型（Step 2）

型は「聴衆がどの順で納得するか」の型。入力の `##` の順がその型と合っているかを見る。

| 型 | 合っている順 | 合わない例 |
|---|---|---|
| 結論先行型 | 状況・問題 → 結論（何をするか） → 理由・判断材料 → 次の一歩 | 理由を延々と述べてから最後に結論 |
| 対比型 | 現状 → あるべき姿（往復してもよい） → 行動 | あるべき姿だけを並べて現状に触れない |
| 段階型 | 全体像 → 要素1 → 要素2 → … → 統合 | 要素の説明の途中に全体像が出る |

合わないときは、並べ替えの提案を計画に書く。「セクション B を A の前に。理由: 聴衆は結論を先に求める場なので」の形。承認されなければ入力の順のまま。

セクション名は話題名にし、番号を付けない（章番号はレイアウトが自動で振る）。全角8字を超えるなら、意味の切れ目で2行にする（`検索エンジンと` / `生成AIの違い`）。

## タイトルと結論（Step 3）

### タイトル: 話題を取り出す

最上位の箇条書きから、そのスライドが扱う話題を名詞句で取り出す。

1. 箇条書きの主語・対象になっている語を探す（「Skills は、AI に…を与える仕組み」→ Skills）
2. 主張・評価・理由の部分は結論の材料に回す
3. 同じ話題が続くなら「〜の限界」「〜の限界の理由」「〜の書き方」「〜との違い」「〜の比較」「〜の選び方」のように観点を足して区別する
4. 段階を追うスライド群（Lv1 → Lv4、第1段階 → 第3段階）は、通し番号を前に付ける

| 最上位の箇条書き | タイトル |
|---|---|
| AIは文字ではなくトークン単位で処理する。トークン数が机の消費量でありコスト | トークン |
| バイブと仕様書駆動の使い分けは、期間・人数・保守の有無で決まる | バイブコーディングとの使い分け |
| 回帰テストは手作業で、リリース前に2人で3日かかっている | 回帰テストの現状 |
| ツールは A と B を比べて A にする | テストツールの比較 |

### 結論の導出

2段目以降を読み、「このスライドを見た人が覚えて帰ること」を1つにする。手順:

1. 2段目の各項目を「事実」「理由」「例」「手順」「比較」に分類する
2. 項目に共通する主張、または項目が支えている主張を探す。数値があれば数値を入れる。最上位の箇条書きが主張の文なら、それが結論の第一候補
3. 体言止めか「〜する」で言い切る。否定・条件・比較・因果が入るときは、体言止めで意味が変わるなら文にする（「回答しない」を「回答なし」にしない）
4. 文節の切れ目で改行し、1行12字程度・2〜5行にする（[writing.md](writing.md) の「結論」）
5. タイトルと同じ言葉の繰り返しになっていたら、視点を変える（タイトルが「何か」なら結論は「なぜ／どうなるか」、タイトルが「現状」なら結論は「数値で見た大きさ」）

| タイトル | 2段目 | 結論（/ は改行） |
|---|---|---|
| 回帰テストの現状 | 項目は約400／リリースは月2回 | 約400項目を / 月2回、2人で3日かけて / 手作業で繰り返す |
| 失敗したテストの扱い | 不具合なら修正／仕様変更なら更新／不安定なら隔離 | 失敗は / 不具合・仕様変更・不安定 / の3つに分けて対応 |
| 仕様書による実装と検証 | 実装Agent／テストAgent／同じ仕様書を読む | 同じ仕様書から / 実装とテストを別々に作り / 品質を担保する |

### 下の階層が無いとき

その文自体から結論を導く。文が主張になっていれば、話題名をタイトルに、主張を結論にする。文が話題名だけ（「バイブコーディングの登場」）で主張が読めなければ、**結論未定** として計画に載せ、候補を2つ示す。候補は入力の前後の箇条書きから作る。承認時に選ばれたものを使う。選ばれなかったときは、そのスライドは結論なしのまま書き出さず、利用者に入力への追記を頼む。

### 分割・統合・削除の判定

**分割を提案する**:

- 2段目に、互いに独立した主張が2つある（片方を消しても残りが成り立つ）
- 本文が12行を超える
- 図が2種類要る（プロセスと比較の両方、など）。ただし、2つ目の図が横長で `::note::` に収まるなら分割しなくてよい
- 分割後の各スライドに結論が1つずつ立つ

**統合を提案する**:

- 隣り合う箇条書きの結論が同じになる
- 片方が、もう片方の例か言い換えでしかない（「バイブコーディングは〜で形にする」と「バイブコーディングは速く、試作に向く」→ 1枚で本文に手順、図に向く／向かないの比較）

**削除を提案する**:

- 進行だけを伝えるスライド（全体の流れ、デモへの切り替え、「次は〜」）
- 冒頭で述べた内容を、まとめで同じ図のまま繰り返すだけのスライド

**提案の書き方**: 「入力の N 番目『…』を2枚に分ける。1枚目の結論『…』、2枚目の結論『…』。理由: …」。承認されなければ 1対1 のまま書き出す。

## 結論の並びの検査（Step 3 の最後）

結論だけを番号順に並べ、本文を見ずに読む。

- 最後まで読んで、目的（Step 1）に届くか
- 前の結論の「なぜ」「だから何」に、次の結論が答えているか
- 同じことを2回言っていないか

飛躍があれば「N と N+1 の間に、『…』という箇条書きを足すと通る」と提案する。スキルがスライドを足して埋めない。重複があれば統合を提案する。

## 入力の階層の振り分け

| 入力の階層 | 置き場所 |
|---|---|
| 最上位 | タイトル（話題名）と結論 |
| 2段目・3段目 | 本文。見出し語と中身の階層に組み直す。構造があれば図の材料 |
| 4段目以降の定義・例・理由・数値・固有名詞 | 本文の2段目へ引き上げる（例は `ex)`） |
| 4段目以降の話し方の指示（問いかけ、挙手、伏線、「〜と言う」） | 発表者ノートか、計画の「本編に入れなかった情報」 |
| 比喩 | 発表者ノート（画面は技術用語） |
| 「要確認」の印 | 発表者ノートと、計画の「確認が必要な事項」 |

次は、本文の量を抑えるときも画面に残す。聞き流すと失われるため: 数値（件数、期間、金額、割合）、固有名詞（製品名、部署名、人名）、定義、手順の順番、比較の軸、URL、引用。

## 時間の見積もり

持ち時間が分かっていれば、計画で枚数から見積もる。目安: 表紙・区切り 10〜20秒、説明スライド 60〜90秒、表や図の多いスライド 90〜120秒。デモなど別資料の時間は分けて書く。超えていれば「論点を減らす」提案を計画に書く（文字を削って収めようとしない）。ノートに想定時間は書かない。
