# 内容の分析と結論の導出

SKILL.md の Step 1〜3 の詳細。入力を読んでから、スライド計画を作るまでに使う。

## 前提の読み取り（Step 1）

`#` の直下、最初の `##` より前の箇条書きが前提。ラベルの書き方は固定しない。次の対応で読む。

| 読み取る項目 | 手がかりになる語 | 判断に効くこと |
|---|---|---|
| 目的 | 目的、ゴール、〜してほしい、合意、承認、理解 | 型の選択、結びの要否 |
| 聴衆 | 聴衆、対象、参加者、〜向け、前提知識 | 説明の粒度、用語の補足 |
| 持ち時間 | 分、持ち時間、枠、質疑 | 想定時間の照合、論点の数 |
| 使われ方 | 口頭、発表、配布、読まれる、資料として送る | 画面の文字量 |

**聞くのは判断が変わる項目だけ。** 目的と使われ方は判断に大きく効くので、読めなければ聞く。聴衆と持ち時間は、読めなければ仮定して進んでよい（仮定は計画に明記）。

- 「配布して読まれる」なら、本文の要素を5つ程度まで、1要素を全角30字程度まで緩める。発表者ノートに回すはずだった説明を、3段目（補足）として画面に残してよい
- 「口頭」なら基本の文字量。ノートを厚くする
- 「両方」なら口頭向けに作り、読まれるときに必要な情報をノートに書く

前提の箇条書きに、前提以外の内容（表紙のサブタイトル、発表者名、日付）があれば、表紙の `subtitle`・`author`・`date` に使う。

## ストーリーの型（Step 2）

型は「聴衆がどの順で納得するか」の型。入力の `##` の順がその型と合っているかを見る。

| 型 | 合っている順 | 合わない例 |
|---|---|---|
| 結論先行型 | 状況・問題 → 結論（何をするか） → 理由・判断材料 → 次の一歩 | 理由を延々と述べてから最後に結論 |
| 対比型 | 現状 → あるべき姿（往復してもよい） → 行動 | あるべき姿だけを並べて現状に触れない |
| 段階型 | 全体像 → 要素1 → 要素2 → … → 統合 | 要素の説明の途中に全体像が出る |

合わないときは、並べ替えの提案を計画に書く。「セクション B を A の前に。理由: 聴衆は結論を先に求める場なので」の形。承認されなければ入力の順のまま。

## タイトルと結論行（Step 3）

### タイトル

最上位の箇条書きの文をそのまま使う。整えるのは次の範囲まで。

- 末尾の句点を取る
- 「〜である」「〜です」を取る
- 全角40字を超えるなら、意味を変えずに語を削る（削った語は結論行か説明で拾う）

### 結論行の導出

2段目以降を読み、「このスライドを見た人が覚えて帰ること」を1文にする。手順:

1. 2段目の各項目を「事実」「理由」「例」「手順」「比較」に分類する
2. 項目に共通する主張、または項目が支えている主張を探す。数値があれば数値を入れる
3. 全角30字前後、体言止めか短い文にする。否定・条件・比較・因果が入るときは、体言止めで意味が変わるなら文にする（「回答しない」を「回答なし」にしない）
4. タイトルと同じ言葉の繰り返しになっていたら、視点を変える（タイトルが「何をするか」なら結論は「なぜ／どうなるか」、タイトルが「状況」なら結論は「数値で見た大きさ」）

| 最上位の箇条書き（タイトル） | 2段目 | 結論行 |
|---|---|---|
| 回帰テストは手作業で、リリース前に2人で3日かかっている | 項目は約400／リリースは月2回 | 約400項目を、月2回、2人で3日かけて手作業で繰り返している |
| 失敗したテストの扱いを最初に決めておく | 不具合なら修正／仕様変更なら更新／不安定なら隔離 | 失敗は「不具合・仕様変更・不安定」の3つに分けて対応する |
| ツールは A と B を比べて A にする | 対応範囲／言語／社内の実績 | 対応範囲が広く、社内に実績のある A を使う |

### 下の階層が無いとき

その文自体から結論を導く。文が主張になっていれば、短く整えたものを結論行にする（タイトルと同じにならないよう、数値や帰結を前に出す）。文が話題名だけ（「バイブコーディングの登場」）で主張が読めなければ、**結論未定** として計画に載せ、候補を2つ示す。候補は入力の前後の箇条書きから作る。承認時に選ばれたものを使う。選ばれなかったときは、そのスライドは結論行なしのまま書き出さず、利用者に入力への追記を頼む。

### 分割と統合の判定

**分割を提案する**:

- 2段目に、互いに独立した主張が2つある（「A は速い」と「B は安全」のように、片方を消しても残りが成り立つ）
- 2段目が5項目を超える
- 図が2種類要る（プロセスと比較の両方、など）
- 分割後の各スライドに結論が1つずつ立つ

**統合を提案する**:

- 隣り合う箇条書きの結論行が同じになる
- 片方が、もう片方の例か言い換えでしかない

**提案の書き方**: 「入力の N 番目『…』を2枚に分ける。1枚目の結論『…』、2枚目の結論『…』。理由: …」。承認されなければ 1対1 のまま書き出し、入らない分は発表者ノートへ。

## 結論の並びの検査（Step 3 の最後）

結論行だけを番号順に並べ、本文を見ずに読む。

- 最後まで読んで、目的（Step 1）に届くか
- 前の結論の「なぜ」「だから何」に、次の結論が答えているか
- 同じことを2回言っていないか

飛躍があれば「N と N+1 の間に、『…』という箇条書きを足すと通る」と提案する。スキルがスライドを足して埋めない。重複があれば統合を提案する。

## 画面の文字量と、消えては困る情報

本文（2段目）は3つ前後、1要素は全角20字程度まで。超えたら、分割するか、ノートへ移す。ただし次は、文字を減らすときも画面に残す。聞き流すと失われるため。

- 数値（件数、期間、金額、割合）
- 固有名詞（製品名、部署名、人名）
- 定義
- 手順の順番
- 比較の軸
- URL、引用

「減らすこと」自体は目的ではない。基準は「この要素が無いと、口頭の説明と合わせてもメッセージが誤解される、または伝わらないか」。

## 発表者ノートと想定時間

ノートは台本ではなく、話す要点。各スライドの末尾の HTML コメントに書く。

- 画面から外した根拠・詳細・具体例（4段目以降、長い説明）
- 前のスライドからのつなぎ、次への橋渡し
- 想定される質問と答え（入力にあるものだけ）
- 想定時間（秒）

想定時間の目安: 表紙・区切り 10〜20秒、目次 20秒、説明スライド 45〜90秒。合計を持ち時間と照合し、超えていれば「論点を減らす」提案を報告に書く（文字を削って収めようとしない）。足りない場合も水増しせず、例や対話をノートに足す。
