# md-to-slidev

箇条書きの Markdown を、Slidev のプレゼンテーションに変換する Skill。

- **入力**: 発表したい内容を箇条書きで整理した Markdown（構造は「入力の約束」のとおり）
- **出力**: `slides.md`、`slide-plan.md`、デザイン部品一式（`style.css`、`layouts/`、`components/`）。Slidev プロジェクトが無ければ最小の雛形も
- **扱わないこと**: PowerPoint・Marp・reveal.js への出力、既存スライドの手直し、画像の生成、入力にない事実の追加

## 5つの原則

### 1. 1スライド1結論

各スライドに「このスライドを見た人に何を覚えてほしいか」を1つ決め、結論行として画面に出す。説明が複数あっても結論は1つ。結論が2つあるなら分割を提案する。

### 2. 図解優先

プロセス・分岐・階層・比較・構成・役割分担・変化は、文章ではなく図で示す。図は同梱の部品（Step、Branch、Layer、Comparison、Architecture など）を組み合わせて作り、スライドごとに新しい見た目を考えない。同じ概念には同じ図を使い、話が進むにつれて同じ図を更新する（強調の位置を変える、範囲を重ねる）。

### 3. 画面の文字は短く

体言止め・短いフレーズ・キーワード。本文の要素は3つ前後、1要素は全角20字程度まで。ただし、数値・固有名詞・定義・手順・比較の軸・URL・引用は、聞き流すと失われるので画面に残す。画面から外した説明は捨てずに発表者ノートへ移す。

### 4. 入力にない事実を足さない

結論は入力から導く。補足が要りそうな箇所は「確認が必要な事項」として報告し、事実として書かない。最新情報（製品の機能・価格・対応状況など）に触れる箇所は、発表前の確認が要ることを明示する。

### 5. デザインは部品に閉じ込める

色・フォント・余白・線幅は `style.css` の変数と部品が持つ。`slides.md` には内容と部品の呼び出しだけを書き、スライドごとに `<style>` や色指定を書かない。デザインを変えるときは部品だけを差し替えられる。規則の詳細は [references/design-rules.md](references/design-rules.md)。

## 入力の約束

```markdown
# プレゼンタイトル

- 目的: …            ← 最初の ## より前の箇条書きは前提（目的・聴衆・持ち時間・使われ方）。スライドにしない
- 聴衆: …

## セクション名         ← セクション区切りのスライドになる

- スライド1枚分の文    ← 最上位の箇条書き1つ = スライド1枚。この文がタイトルになる
  - 説明              ← 2段目 = 左側の説明と図の材料
    - 補足            ← 3段目 = 補足（18px）。4段目以降は発表者ノートへ
- 次のスライド
```

- 対応は原則 1対1。分割・統合は Step 3 で提案し、承認されたものだけ行う
- 入力に表があれば Comparison に、コードブロックがあればそのままコード表示にする
- `##` が無い入力は、セクション区切りなしで扱う。`#` が無ければタイトルを聞く
- すでにスライド化された Markdown（`---` 区切り、layout 指定）や、他の Skill が作った設計書は対象外。箇条書きに直してもらう

## ワークフロー

### Step 0: 入力と環境の点検

- 入力が「入力の約束」の形か確かめる。違えば、どう直せばよいかを伝えて止まる
- カレントに Slidev プロジェクト（`package.json` の dependencies に `@slidev/cli`）があるか見る。あればそこに書く。無ければ Step 6 で雛形を作ることを伝え、置き場所（既定はカレント）を確認する
- 置き場所に `slides.md`・`style.css`・`layouts/`・`components/` が既にあれば、上書きしてよいかを Step 5 の承認と一緒に確認する

### Step 1: 前提の確認

`#` の直下の箇条書きから、目的・聴衆・持ち時間・使われ方（口頭で発表する／配布して読まれる／両方）を読み取る。読めない項目のうち、**判断が変わるものだけ**を聞く（選択式の質問ツールがあればそれを使う）。

- 使われ方が「配布して読まれる」なら、画面の文字を増やす方向に倒す（原則3の度合いを緩める。原則1・2・4は変えない）
- 持ち時間が分かれば、Step 6 で想定時間を照合する。分からなければ照合しない
- 聞かずに済む項目は「仮定」として計画に明記して進む

### Step 2: 内容理解と構造化

入力全体を読み、テーマ・主張・事実・具体例・比較対象・因果関係・時系列を把握する。そのうえでストーリーの型を推定する。

| 型 | 向いている場面 | 流れ |
|---|---|---|
| 結論先行型 | 報告、提案、合意を取る | 状況 → 問題 → 結論 → 理由 |
| 対比型 | 啓発、変革の呼びかけ | 現状 ↔ あるべき姿 → 行動 |
| 段階型 | 研修、概念の解説 | 全体像 → 要素を順に積む → 統合 |

入力の `##` の順が型と合わないときは、並べ替えを Step 5 の計画で提案する。承認されなければ入力の順のまま。並べ替えを黙って行わない。

### Step 3: スライド分割と結論の導出

最上位の箇条書きを1枚ずつスライドにし、各スライドの結論行を作る。

- **タイトル**: 最上位の箇条書きの文をそのまま使う（語尾を整える程度）
- **結論行**: 2段目以降の内容から、聴衆に覚えてほしいことを1文で導く。全角30字前後、体言止めか短い文。タイトルの繰り返しにしない
- 下の階層が無いときは、その文自体から結論を導く。導けないときは計画に **結論未定** と印を付け、候補を2つ示して承認時に決めてもらう。スキルが入力にない主張を断定しない
- **分割の提案**: 1つの箇条書きに結論が2つある、または下の階層が多くて1枚に入らない（説明が5項目を超える、図が2つ要る）
- **統合の提案**: 隣り合う箇条書きが同じ結論の言い換え
- **機能スライド**: 表紙（`#` から）、セクション区切り（`##` から）、目次（`##` が3つ以上のとき）。結び（まとめ・呼びかけ）は入力にそれにあたる箇条書きがあるときだけ。無いときに作らない

結論行を番号順に並べ、本文を見ずに読む。飛躍があれば「入力にこういう箇条書きを足すと通る」と提案し、重複があれば統合を提案する。導出と判定の詳細は [references/analysis.md](references/analysis.md)。

### Step 4: 表現方法とレイアウトの決定

各スライドについて、内容の型から図の部品を選ぶ。対応表は [references/components.md](references/components.md)。

- プロセス・手順・変化 → Step／分岐 → Branch／階層 → Layer／比較 → Comparison／構成 → Architecture／まとまり → Group／要点1つ → EmphasisBox
- 図にする内容が無いスライド（定義だけ、前提だけ）は図なしでよい。図を置くために内容を作らない
- 同じ概念が複数のスライドに出るなら、同じ部品・同じ並びで描き、`highlight` や `overlay` で今の話題を示す
- レイアウトは `md-standard`（タイトル → 結論 → 左に説明、右に図）を基本にする。図が大きい比較表や全面図解なら `md-wide`。図の幅は既定 45%、必要なら `figureWidth` で 33〜55% の範囲で変える
- 画面の説明文（2段目）は、体言止め・短いフレーズに整える。3段目は補足として 18px で置く。4段目以降と、長い説明は発表者ノートへ
- 抽象的なイラストがあれば効くと思うスライドは、文字と図だけで成立する形で作り、報告で候補として挙げる。画像は生成しない

### Step 5: スライド計画の承認

ここまでの結果を [assets/slide-plan.template.md](assets/slide-plan.template.md) の形にまとめ、利用者に見せて承認を取る。確認を取るのはこの1回。

計画に含めるもの: 前提と仮定、型と並べ替えの提案、目次・結びの有無、スライド一覧（種別・タイトル・結論・表現・レイアウト）、分割・統合の提案、結論の並びと飛躍・重複、本編に入れなかった情報、確認が必要な事項。

直しが入ったら計画を更新し、承認されたら `slide-plan.md` として `slides.md` の隣に保存する。以降のステップは確認なしで進める。

### Step 6: 書き出し

1. Slidev プロジェクトが無ければ、[assets/slidev/package.json](assets/slidev/package.json) と `gitignore`（`.gitignore` に改名）を置き場所へ書き、`npm install` を実行する
2. [assets/slidev/](assets/slidev/) の `style.css`・`layouts/`・`components/` を置き場所へコピーする。既存のものがあれば Step 0 の確認に従う
3. `slides.md` を書く。書式は [references/components.md](references/components.md) の「slides.md の書き方」。完成例は [assets/example/slides.md](assets/example/slides.md)（入力は [assets/example/input.md](assets/example/input.md)、計画は [assets/example/slide-plan.md](assets/example/slide-plan.md)）
   - 各スライドの末尾の HTML コメントが発表者ノート。画面から外した根拠・具体例・前後のつなぎ・想定時間（秒）を書く
   - 持ち時間が分かっていれば、想定時間の合計を持ち時間と照合する。超えていれば、文字を削るのではなく論点を減らす提案を報告に書く
4. `slide-plan.md` を保存する（Step 5 で未保存なら）

### Step 7: 一貫性と最終チェック

[references/checklist.md](references/checklist.md) で全スライドを点検する。特に、1スライド1結論か、18px 未満の文字がないか、図にできる内容を文章で済ませていないか、同じ概念に別の図を作っていないか、入力にない事実を足していないか、`slides.md` に色や `<style>` を直書きしていないか。違反は該当する Step に戻って直す。

### Step 8: ビルドと報告

`npx slidev build` を実行し、部品の参照エラーや構文エラーが無いことを確かめる。通ったら `dist/` を消す。失敗したら直して再実行し、直せない場合はエラーをそのまま報告する。

報告に書くこと:

- 書いたファイルと、`npm run dev` で開ける旨
- 本編に入れなかった情報と置き場所
- 確認が必要な事項（最新情報の確認、結論の候補のうち選ばなかった方、飛躍の指摘）
- イラストを足すならどのスライドにどういう絵か（候補のみ）
- ビルドでは分からない点として、はみ出し・文字の重なりを実機で見てほしいこと。想定時間の合計と持ち時間

## 避けるパターン

| パターン | 避ける理由 |
|---|---|
| 入力の順や枚数を黙って変える | 利用者が整理した構造がこの Skill の入力契約。変えるなら計画で提案し、承認を取る |
| 下の階層が無いスライドに、文脈から結論を作って断定する | 入力にない主張になる。候補を示して決めてもらう |
| 結論行をタイトルの言い換えにする | 2段構成の意味が無くなる。結論は下の階層から導く |
| 図を置くために内容を作る | 図は内容の型から選ぶ。型が無ければ図なし |
| 同じ概念をスライドごとに違う図で描く | 聴衆が毎回図を読み直す。同じ部品・同じ並びで、強調だけ変える |
| `slides.md` に `<style>` や色・サイズを直書きする | デザインが部品から漏れ、差し替えできなくなる。足りない表現は部品に足す |
| 比較で勝敗を示す | 色や語で優劣を示さない。軸ごとの違いを事実で並べる |
| 空いた領域を装飾やイラストで埋める | 余白は情報の無さの表れであって欠陥ではない。装飾は内容より目立つ |
