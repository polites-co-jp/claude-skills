# テスト自動化の導入

- 目的: 開発部の月例会で、回帰テストの自動化を段階的に始める合意を取る
- 聴衆: 開発部のメンバーとリーダー。テストの現状は知っている
- 持ち時間: 15分。口頭で発表する

## 現状

- 回帰テストは手作業で、リリース前に2人で3日かかっている
  - 画面テストの項目は約400
  - リリースは月2回
- 手作業のテストは同じ項目の繰り返しで、見落としも起きている
  - 直近3か月で、リリース後の不具合が4件
  - うち3件は既存のテスト項目に含まれていた
  - 残り1件はテスト項目になかったケース

## 進め方

- 自動化は一度に全部やらず、3段階で広げる
  - 第1段階: ログインと主要な画面遷移（約50項目）
  - 第2段階: 入力フォームの検証（約150項目）
  - 第3段階: 残りの画面（約200項目）
- 自動化の対象は「繰り返し回数が多く、仕様が安定している項目」から選ぶ
  - 繰り返しが多い項目ほど、自動化の効果が大きい
  - 仕様が安定している項目ほど、テストの書き直しが少ない
  - 仕様変更が多い画面は手作業のまま残す
- ツールは Playwright と Cypress を比べて Playwright にする
  - 対応ブラウザ: Playwright は Chromium・Firefox・WebKit、Cypress は Chromium 系と Firefox
  - 言語: Playwright は TypeScript・Python など、Cypress は JavaScript・TypeScript
  - 社内の実績: Playwright は隣の部署で使用中、Cypress は実績なし

## 運用

- テストコードは機能のコードと同じリポジトリに置き、CI で毎回動かす
  - プルリクエストごとに第1段階のテストを実行
  - 夜間に全テストを実行
- 失敗したテストの扱いを最初に決めておく
  - 不具合なら修正する
  - 仕様変更ならテストを更新する
  - 不安定なら隔離して原因を調べる
- 第1段階の完了を来月末とし、リリース前の手作業を3日から2日に減らすことを目標にする
