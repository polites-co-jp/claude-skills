# 区分 C: 技術の決め方

## 決める粒度

必ず決めるのは次の6項目。

| 項目 | 例 |
|---|---|
| 言語 | TypeScript、Python、Go、C++、Swift |
| ランタイム | Node.js、ブラウザ、CPython、JVM、ネイティブ |
| パッケージマネージャ（ビルドシステムを含む） | pnpm、npm、uv、Cargo、CMake |
| 主要フレームワーク | Next.js、FastAPI、Electron、`none` |
| DB 種別 | PostgreSQL、SQLite、`none` |
| デプロイ先種別 | 特定のクラウド、コンテナ基盤、パッケージレジストリ、アプリストア、`none` |

この粒度にしている理由は、次の Skill が Agent に許可するコマンドを具体的な名前で書くからだ。
「テストを実行してよい」ではなく、どのパッケージマネージャのどのコマンドかまで書く。言語とパッケージマネージャが未定のままでは書けない。

逆に、これより細かい選択は決めない。

- テストランナー、linter、フォーマッタ
- ORM、クエリビルダ
- UI ライブラリ、状態管理
- API の様式（REST か GraphQL か）
- 認証のライブラリやサービス

これらは後続の詳細設計が、機能の要件を見てから決める。次の Skill は検証を「プロジェクトが提供する単一の検証コマンド」経由で配線するので、テストランナーが未定でも困らない。
ユーザーがこれらを指定してきたら、否定せず区分 H に `[deferred]` として残す。

## いつ聞くか

目的（区分 A）とシステム境界（区分 B）が見えてから。冒頭では聞かない。
境界が分かって初めて「DB が要るのか」「サーバーが要るのか」が決まり、候補を絞れる。

## 手順

### 1. 指定済みの技術を拾う

ユーザーがアイデアの説明で既に技術を指定していれば、モードに関係なく `decided` として採用する。
「Next.js で作りたい」なら、言語（TypeScript か JavaScript か）とランタイム（Node.js）はほぼ決まる。
そこから自明に決まる項目は仮定として埋め、Step 4 で確認する。

6項目がすべて決まったら、モードを聞かずに終わる。

### 2. モードを1回だけ聞く

残りがあるときだけ聞く。

- **Mode 1**: 候補を見て自分で選びたい
- **Mode 2**: 任せたい

### 3a. Mode 1: 構成を 2〜3 案提示する

6項目を1つずつ聞かない。要件に合う**構成**を 2〜3 案作り、理由と向き不向きを添えて提示する。
案同士は、はっきり性格が違うものにする（例: 一体型で素早く作る案／接点と処理を分けて育てやすくする案）。部品が1つ違うだけの案を並べない。

提示の例:

```text
案 1（推奨）: 一体型で素早く作る
  TypeScript / Node.js / pnpm / Next.js / PostgreSQL / コンテナ基盤
  画面と API を1つのフレームワークで書ける。試作から本番まで構成を変えずに進めやすい。
  向かない場合: 後で API だけを別のクライアント（モバイルなど）にも公開したい

案 2: 画面と API を分ける
  TypeScript / Node.js / pnpm / React + Fastify / PostgreSQL / コンテナ基盤
  API が独立するので、接点が増えても対応しやすい。
  向かない場合: 一人で素早く試作したい（書くものが増える）
```

1つ選んでもらい、変えたい項目があればそこだけ調整する。調整で組み合わせが不整合になる場合は、その場で指摘する。

### 3b. Mode 2: 構成を1つ決めて示す

次の優先順位で決める。

1. **ユーザーが過去に採用してきた構成に寄せる**。「よく使う構成があれば教えてください」を1回だけ聞く。
   答えがあれば、要件上の問題がない限りその構成に寄せる。個別の部品ではなく構成として扱う。
   「TypeScript + React + Node.js + PostgreSQL + Docker をよく使う」と言われたら、React だけを拾うのではなく、全体をその構成に合わせる。
   慣れた構成は、ユーザーが Agent の成果物をレビューできるという意味でも価値がある
2. **答えが無ければ、その要件に対して一般的によく使われている構成を選ぶ**。珍しい選択をしない。
   情報が多く、つまずいたときに解決策が見つかりやすいことを優先する
3. **その中で、Agent による開発・保守との相性を考える**。型のある言語、コマンドラインで完結するツール、
   速く決定的に終わる検証（型チェック、テスト）が揃う構成は、Agent が自分の誤りに気づきやすい

決めた構成を、理由とともに一度で示す。異議がある項目だけ直す。この場合の状態は、ユーザーが認めた時点で `assumed`。

## 整合性を確かめる

構成を確定する前に、次を確かめる。

- 言語とランタイムとパッケージマネージャが噛み合っているか
- 主要フレームワークが、区分 B の接点と処理の置き場所に合っているか（サーバーを持たない構成にサーバー用のフレームワークを選んでいないか）
- DB 種別が、区分 B の保存先と区分 E の実行環境に合っているか（利用者の端末で動くものにサーバー型の DB を選んでいないか）
- デプロイ先種別が、区分 B の配布・実行場所と合っているか
- 区分 A の制約（技術の指定、予算、既存の仕組みとの互換）に反していないか

## ツールチェーンが複数あるとき

モバイルアプリ（Swift）と Backend（Go）のように、構成要素によって言語が違う場合は、構成要素ごとに6項目を決め、表を分けて書く。
無理に1つの言語に揃えようとしない。ただし、揃えられるのに分かれている場合（特に理由なく画面と API で言語が違う）は、揃える案を提示する価値がある。

## `none` の扱い

該当しない項目は `none` と書く。

- ライブラリや CLI の DB 種別 → `none`
- フレームワークを使わない小さなツール → 主要フレームワーク `none`
- 手元で使うだけで配布しない → デプロイ先種別 `none`
