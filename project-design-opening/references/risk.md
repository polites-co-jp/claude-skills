# 区分 D: リスクの聞き方

## なぜ聞くのか

次の Skill は、開発を担う Agent に対して「自動でやってよい操作」「人の承認が要る操作」「禁止する操作」の線を引く。
結果が重い操作ほど、固いゲートを置く。

| 操作の重さ | 例 | 扱い |
|---|---|---|
| 読むだけ | ファイルを読む、検索する | 自動 |
| 可逆な変更 | 作業場所のファイルを編集する、テストを走らせる | 自動 |
| 外部作用 | メッセージを送る、デプロイする、課金する | 人の承認 |
| 不可逆・機微 | データを消す、認証情報を変える、全体に公開する | 強いゲートか禁止 |

この線は、ユーザーがどんなに軽いハーネスを選んでも必ず作られる安全の下限であり、区分 D はその唯一の材料になる。
ここで「決済がある」ことが漏れると、Agent が開発中に本物の課金 API を叩くのを止める仕組みが作られない。
だから区分 D の3項目は `deferred` にせず、必ず「ある」か `none` かを確定させる。

## 聞き方

ユーザーは「外部作用」「不可逆操作」という言葉では考えていない。「外部作用はありますか」と聞いても答えは返ってこない。
区分 B で挙がったものを1つずつ取り上げ、具体的に聞く。

1. **外部とのやりとりを1つずつ確かめる**。「その決済サービスには、実際にお金が動く操作を依頼しますか」「そのメール送信は、実在の人に届きますか」。
   読むだけの連携（天気を取得する、など）は外部作用に当たらない。書き込む・送る・動かす連携が当たる
2. **配布・実行場所を確かめる**。「作ったものを、他の人が使う場所に出しますか」。デプロイ、パッケージの公開、アプリストアへの提出は外部作用
3. **データの保存先を確かめる**。「消えたら困るデータ、間違って書き換わったら困るデータは入りますか」「本番のデータは、開発中に触れる場所にありますか」
4. **秘密情報と個人情報を確かめる**。「API キーやパスワードのような秘密の値を使いますか」「氏名、連絡先、決済情報のような、人に関する情報を扱いますか」

質問は多くて3〜4回。区分 B から明らかなもの（決済があると既に聞いている、など）は聞かずに埋め、Step 4 で確認する。

## 運用中の作用と、開発中の作用

区分 D が対象にするのは、完成したシステムが行う操作だけではない。**開発中の Agent が触れてしまう可能性のある操作**も対象にする。
ハーネスが守るのは、開発している間の事故だからだ。

| 完成したシステムが行うこと | 開発中に起こりうる事故 |
|---|---|
| 利用者にメールを送る | テストの実行で、実在の人にメールが飛ぶ |
| カードに課金する | 動作確認で、本物の課金が走る |
| 本番の DB にデータを保存する | マイグレーションの試行で、本番のデータが書き換わる |
| パッケージを公開する | 作業中の版が、取り消せない形で公開される |

したがって「本番環境はあるか（区分 E）」「開発用の接続先と本番用の接続先は分かれているか」は、区分 D を埋めるうえで確かめる価値がある。
ただし、分け方の設計には踏み込まない。「本番がある／これから作る」「分かれている／まだ決めていない」まで分かれば十分。

## 項目ごとの例

### 外部作用

- メール、SMS、プッシュ通知、チャットへの投稿など、人に届くメッセージの送信
- 課金、決済、返金、購入
- 外部の API やサービスへの書き込み（データの登録・更新・削除）
- SNS やブログへの投稿
- デプロイ、リリース、パッケージレジストリへの公開、アプリストアへの提出
- 外部システムへのジョブの投入、機器の操作

### 不可逆・機微な操作

- 本番データの削除や一括変更、DB のマイグレーション
- 認証情報や鍵の発行・変更・失効
- 公開範囲の変更（非公開のものを全体に公開する）
- 公開済みの版の取り下げや上書き（多くのレジストリでは取り消せない）
- 利用者のアカウントの削除や停止
- 費用が発生する基盤の操作（リソースの作成・削除）

### 秘密情報・個人情報

- 秘密情報: API キー、アクセストークン、DB の接続情報、署名用の鍵
- 個人情報: 氏名、住所、連絡先、位置情報、行動の履歴
- 特に慎重な扱いが要る情報: 決済情報、健康や医療に関する情報、本人確認書類、子どもに関する情報

## `none` も答え

小さな CLI やライブラリでは、3項目とも `none` になることがある。それで正しい。`none` と明記されていれば、次の Skill は安全策を省いてよいと判断できる。
ただし、ライブラリでも「パッケージレジストリへの公開」は外部作用かつ不可逆な操作に当たる。配布する予定があるなら `none` にはならない。

## 踏み込まないこと

粒度は「何があるか」まで。次のものは書かない。

- 誰が何を承認するかの流れ
- 権限やロールの設計
- 暗号化やマスキングの方式
- 法令対応の具体策

ユーザーがこれらを話したら、要点を区分 H に `[deferred]` として残す。

## 書き方の例

| 項目 | 内容 | 状態 |
|---|---|---|
| 外部作用 | 決済サービスへの課金と返金の依頼 | decided |
| 外部作用 | 予約確認メールの送信（実在の利用者に届く） | assumed |
| 外部作用 | クラウドへのデプロイ | assumed |
| 不可逆・機微な操作 | 本番 DB のマイグレーションとデータ削除 | assumed |
| 秘密情報・個人情報 | 秘密情報: 決済サービスとメール送信の API キー、DB の接続情報 | assumed |
| 秘密情報・個人情報 | 個人情報: 利用者の氏名・メールアドレス・電話番号。カード番号は自前で保持しない | decided |
