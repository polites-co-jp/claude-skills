# 走査の手順

リポジトリから、入力契約 A〜H のうち読み取れる項目を読み取る手順。
目的は境界を知ることであって、コードを理解することではない。実装の中身は、ほとんど読まなくてよい。

## 読む順

安く確実なものから読む。上の段で答えが出た項目を、下の段で確かめ直さない。

1. **最上位の配置**。リポジトリ直下のファイルとフォルダの一覧。これだけで、種類・言語・構成の大枠が分かる
2. **構成ファイルと依存の定義**。`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`CMakeLists.txt`、`Gemfile`、`*.csproj`、`Package.swift` など。lockfile は、存在と種類だけを見る（中身は読まない）
3. **実行とデプロイの設定**。`Dockerfile`、`docker-compose.yml`、`fly.toml`、`vercel.json`、`netlify.toml`、`wrangler.toml`、`Procfile`、`serverless.yml`、`*.tf`、Kubernetes のマニフェスト
4. **CI の定義**。`.github/workflows/`、`.gitlab-ci.yml` など。何が自動で走り、どこへ出しているかが分かる
5. **環境変数の雛形**。`.env.example`、`.env.sample`、`.env.template`。キーの名前から、外部サービスと秘密情報の有無が分かる
6. **README と既存の文書**。目的、やること、使い方。`docs/`、`doc/`、`design/` などの設計文書の場所
7. **git の情報**。リモートの URL（ホスティング）、コミットの著者の数（ソロかチームか）、タグ（リリースの有無）
8. **エントリポイント**。ここまでで境界が分からないときだけ、`main`、`index`、`app`、ルーティングの定義などを、必要な分だけ読む

## 読まないもの

- **実際の値が入っている環境変数のファイル**。`.env`、`.env.local`、`.env.production`、`.env.*.local` など。存在することだけを控える。中身は読まない
- 鍵や証明書のファイル（`*.pem`、`*.key`、`id_rsa` など）、`secrets/` のようなフォルダの中身
- lockfile の中身、`node_modules/` や `vendor/` などの依存の実体、ビルドの成果物
- 実装のコードの全体。境界が分からないときに、エントリポイントを必要な分だけ読む

秘密の値を含むファイルを誤って開いてしまったら、その値を成果物にも対話にも書かない。

## 区分ごとの読み取り元

| 区分・項目 | 読み取り元 |
|---|---|
| A 目的、やること | README の冒頭、構成ファイルの `description`、既存の文書。「やらないこと」と「制約」は、ほぼ書かれていないので聞く |
| B 利用者との接点 | フレームワークの種類（Web、CLI、モバイル）、`bin` の定義、公開している API やパッケージの入口 |
| B 処理 | サーバーの有無（サーバー用のフレームワーク、`Dockerfile`、`Procfile`）、定期実行の定義（cron、ワークフローの schedule） |
| B データの保存先 | DB のドライバや ORM の依存、`docker-compose.yml` のサービス、マイグレーションのフォルダ、`DATABASE_URL` などのキー |
| B 外部とのやりとり | 外部サービスの SDK の依存、環境変数のキーの名前、Webhook の受け口 |
| B 利用者の識別（認証） | 認証のライブラリやサービスの依存、セッションやトークンに関するキー |
| B 配布・実行場所 | デプロイの設定ファイル、CI のデプロイや公開の手順、パッケージの `publishConfig` |
| C 言語、ランタイム | 構成ファイルの種類、`engines`、`.nvmrc`、`.python-version`、`rust-toolchain`、`go.mod` の `go` の行 |
| C パッケージマネージャ | lockfile の種類（`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock`、`bun.lockb`、`uv.lock`、`poetry.lock`、`Cargo.lock`）、`packageManager` の欄 |
| C 主要フレームワーク | 依存の定義。骨格になるものを1つ選ぶ。補助のライブラリを並べない |
| C DB 種別 | ドライバの依存、`docker-compose.yml` のイメージ、ORM の設定の `provider` |
| C デプロイ先種別 | デプロイの設定ファイル、CI の手順。特定の製品名が分かれば、その名前で書く |
| E 開発環境 | OS は、いま動いている環境のもの。コンテナ利用は `docker-compose.yml` や `.devcontainer/` の有無 |
| E 実行環境の段階 | 環境ごとの設定ファイル、CI の環境の定義、デプロイの設定の環境名。読めなければ聞く |
| E ホスティング | git のリモートの URL |
| E CI | CI の定義ファイルの有無 |
| F 単一か分離か | ワークスペースの定義（`pnpm-workspace.yaml`、`workspaces`、`Cargo.toml` の `[workspace]`）、サブモジュール |
| F 最上位の配置 | リポジトリ直下のフォルダ。コードを置く領域を拾う |
| F 設計文書の場所 | `docs/` 以外にある設計文書のフォルダ（`doc/`、`design/`、`spec/`、`adr/` など）。無ければ行を作らない |
| G ソロかチームか | コミットの著者の数。手がかりとして示し、確かめる |
| G 試作か本番品質か | バージョン、本番向けのデプロイ設定、CI の有無。手がかりとして示し、確かめる |
| H 既存の検証系コマンド | 構成ファイルの scripts やタスクの定義（test、lint、typecheck、format） |

**製品名が分かるなら、製品名で書く**。「クラウド」ではなく「Fly.io」、「決済サービス」ではなく「Stripe」。
次の Skill は、定義に名前が出ている道具についてだけ、承認や禁止の規則を作る。既存プロジェクトの強みは、この名前が具体的に分かることにある。

## 区分 D: 検出の手がかり

検出できるのは「ある」だけである。下の手がかりが見つかれば、その行を「あり」として控える。見つからなければ「未検出」として控え、Step 3 で聞く。

| 項目 | 手がかり |
|---|---|
| 外部作用: メッセージの送信 | メール・SMS・プッシュ通知・チャットの SDK の依存、`SMTP_*`・`SENDGRID_*`・`TWILIO_*`・`SLACK_*` などのキー |
| 外部作用: 課金 | 決済の SDK の依存、`STRIPE_*`・`PAYPAL_*` などのキー、Webhook の受け口 |
| 外部作用: 外部 API への書き込み | 外部サービスの SDK の依存、API キーのキー名 |
| 外部作用: デプロイ、公開 | デプロイの設定ファイル、CI のデプロイや公開の手順、scripts の `deploy`・`publish`・`release` |
| 不可逆・機微: データの削除や変更 | マイグレーションのフォルダと道具、scripts の `db:reset`・`db:drop`・`seed`、本番向けの接続設定、デプロイの設定に書かれた自動のマイグレーション（`release_command` など） |
| 不可逆・機微: 認証情報の扱い | 鍵や証明書を扱う設定、シークレット管理の道具の設定 |
| 不可逆・機微: 公開済みの版の変更 | パッケージレジストリへの公開の設定、リリースの自動化 |
| 秘密情報 | `.env` の類の存在、雛形のキーの名前（`*_SECRET`、`*_KEY`、`*_TOKEN`、`*_PASSWORD`、`DATABASE_URL`） |
| 個人情報 | 利用者のモデルやテーブルの定義に、氏名・連絡先・住所などがあること。認証の仕組みがあること。ここはエントリポイント付近を必要な分だけ読む |

検出した操作は、**道具とコマンドの名前つきで**控える。デプロイなら `flyctl deploy`、マイグレーションなら `prisma migrate deploy`、scripts に包まれているなら scripts の名前（`pnpm db:reset`）と中のコマンドの両方。次の Skill は、名前のある道具にしか規則を作れない。

**リポジトリに痕跡が残らないもの**があることを、常に念頭に置く。管理画面からの手動デプロイ、手作業でのリリース、本番 DB への手作業の接続、外部サービスの管理画面での操作。これらは、聞かなければ分からない。

## 確信の度合い

読み取った内容の確からしさは、根拠によって違う。Step 2 で見せるとき、弱いものにはその旨を添える。

| 確からしさ | 例 |
|---|---|
| 強い | lockfile の種類、構成ファイルに明記された値、実際に使われている設定ファイル |
| 中くらい | 依存に入っているライブラリ（使われていないこともある）、README の記述（古いこともある） |
| 弱い | フォルダの名前からの推測、コミットの著者の数からの推測、雛形のキーの名前だけからの推測 |

食い違う手がかりが見つかったら（lockfile が2種類ある、README と構成ファイルで言っていることが違う、など）、まず根拠の強さを比べる。片方に強い根拠が揃っているなら（`packageManager` の欄・CI・Dockerfile が一致している、など）、そちらを読み取った値として見せ、食い違う手がかりが残っていることを添える。強さが同じくらいなら、片方を選ばずに、両方を根拠つきで見せて確かめる。

## 大きなリポジトリ、複数の構成要素

- 読む量に上限を置く。構成ファイルと設定ファイルを中心に、多くて数十ファイル。それで分からない項目は、読み続けるより聞いた方が速くて確実である
- ワークスペースやモノレポでは、最上位の構成ファイルと、各構成要素の構成ファイルだけを読む
- 構成要素によってツールチェーンが違う場合（Swift のモバイルアプリと Go の Backend、など）は、構成要素ごとに区分 C の6項目を控える。成果物でも、区分 C の表を構成要素ごとに分ける
- 同じツールチェーンで書かれた複数のパッケージは、1つの構成として扱う。パッケージの数だけ表を分けない

## 走査の結果の控え方

利用者に見せる一覧の形で控える。区分 B・C・E・F は Step 2 で、区分 A・D・G は Step 3 で、それぞれの質問の冒頭に見せる。

```text
区分 C 技術
  言語              TypeScript          根拠: package.json, tsconfig.json
  パッケージマネージャ  pnpm                根拠: pnpm-lock.yaml, package.json の packageManager
  DB 種別           PostgreSQL          根拠: docker-compose.yml の image, prisma/schema.prisma の provider
区分 D リスク
  外部作用          Stripe への課金                        根拠: 依存 stripe, .env.example の STRIPE_SECRET_KEY
  外部作用          Fly.io へのデプロイ（flyctl deploy）     根拠: fly.toml, .github/workflows/deploy.yml
  不可逆・機微       pnpm db:reset（prisma migrate reset）   根拠: package.json の scripts
  秘密情報・個人情報  （個人情報は未検出）                     → Step 3 で聞く
```

根拠を示せない項目は、読み取ったことにしない。根拠は、ファイルのほか、git の情報や、いま動いている環境でもよい（「根拠: git のリモート」「根拠: いま動いている環境」）。
開発環境の OS は、いま動いているこの1台のものである。チームで開発しているなら、他の人の環境は違うかもしれないことを、一覧に一言添える。
