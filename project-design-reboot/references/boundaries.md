# 区分 B: システム境界の捉え方

システム境界とは「このプロジェクトには何があって、どうつながっているか」の大きな見取り図。
後続の Skill がプロジェクトの地図を書き、リスクを洗い出すための骨格になる。

## 6つの問い

種類を問わず、次の6つで捉える。Web サービスの用語（フロントエンド、Backend、DB）を前提にしない。
CLI にもライブラリにも、接点と処理と配布場所はある。

| 問い | 項目 |
|---|---|
| 利用者はどこから触るのか | 利用者との接点 |
| 主な処理はどこで動くのか | 処理 |
| 何かを永続的に残すのか。どこに | データの保存先 |
| 自分たちが作らない外部の何とやりとりするのか | 外部とのやりとり |
| 利用者を識別する必要があるのか | 利用者の識別（認証） |
| 作ったものをどこに置き、どこで動かすのか | 配布・実行場所 |

該当しないものは `none`。6つすべてが埋まる必要はなく、「無い」ことが分かっていることが大事。

## 種類別の典型例

あくまで典型であり、当てはめるための型ではない。ユーザーの説明が典型から外れていたら、説明の方を信じる。

| 種類 | 接点 | 処理 | 保存先 | 外部 | 認証 | 配布・実行場所 |
|---|---|---|---|---|---|---|
| Web サービス | Web 画面 | サーバー（API） | DB | 決済、メール送信など | あり | クラウド |
| Web サービス（静的） | Web 画面 | 利用者のブラウザ | `none` | `none` か外部 API | `none` | 静的ホスティング |
| モバイルアプリ + Backend | モバイルアプリ | 端末とサーバー | 端末内と DB | プッシュ通知など | あり | アプリストアとクラウド |
| CLI ツール | コマンドライン | 利用者の端末 | `none` か設定ファイル | `none` か外部 API | `none` | パッケージレジストリ |
| ライブラリ | 公開 API（関数・クラス） | 呼び出し側のプロセス | `none` | `none` | `none` | パッケージレジストリ |
| デスクトップアプリ | デスクトップの画面 | 利用者の端末 | ローカルファイルか端末内 DB | 更新配信など | `none` か あり | インストーラ配布 |
| バッチ処理 | `none`（人は触らない）か管理画面 | 定期実行の基盤 | DB かファイル | 取り込み元・連携先 | `none` | クラウドか社内サーバー |

## 典型から読み取り、外れだけ聞く

「店舗向けの予約管理を Web で作りたい。カード決済もしたい」と聞いたら、Web サービスの典型から次のように読み取れる。

- 接点: Web 画面（利用者向けと店舗向けの2つがありそう → 要確認）
- 処理: サーバー
- 保存先: DB（予約を保存するはず）
- 外部: 決済サービス（明言あり）。予約確認のメール送信もありそう → 要確認
- 認証: あり（店舗側は確実。利用者側は → 要確認）
- 配布・実行場所: クラウド

聞くのは「要確認」の3点だけでよい。既存プロジェクトでは、その多くも走査で答えが出る。残りは仮定として埋め、Step 2 でまとめて確認する。

## 図の描き方

表の下に、境界同士の関係をテキストで描く。矢印は「どちらがどちらを呼ぶか」。細部は要らない。

Web サービスの例:

```text
利用者向け Web 画面 ─┐
                     ├→ API サーバー → DB
店舗向け管理画面   ──┘       │
                             ├→ 決済サービス（外部）
                             └→ メール送信サービス（外部）
配布・実行場所: クラウド
```

C++ のライブラリの例:

```text
利用側のアプリケーション → 公開 API（ヘッダ） → ライブラリ本体
保存先: none ／ 外部: none ／ 認証: none
配布・実行場所: パッケージレジストリ経由で、利用側のプロセス内で動く
```

Electron のデスクトップアプリの例:

```text
デスクトップの画面（レンダラ） → メインプロセス → ローカルファイル
                                       └→ 更新配信サーバー（外部）
配布・実行場所: インストーラを配布し、利用者の端末で動く
```

## 踏み込まないこと

次の話が出たら、区分 H に要点を残して先へ進む。

- 画面の一覧や遷移、コンポーネントの構成
- API のエンドポイント、データの項目やテーブル
- 認証の方式（パスワード、SSO、トークンの種類）
- ディレクトリの細かい構造

また、境界を Agent の分け方に読み替えない。「Web と API と DB だから Agent は3つ」という対応は成り立たない。
Agent をどう分けるかは、責務・ツール・権限・リスク・検証方法から次の Skill が決める。ここでは境界を正しく写し取ることに集中する。
