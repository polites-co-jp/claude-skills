# 入力契約 A〜H

`docs/project-definition.md` が持つ8区分と、各項目が「埋まった」と言える基準。
この契約は、次の Skill（`project-design-harness`）が Agent とハーネスを設計するときに必要とする情報から逆算して決めてある。
各区分の「使い道」を読めば、なぜその項目が要るのか、どの粒度で十分なのかが判断できる。

点検表として使う。上から順に聞く質問票ではない。

## A 目的とスコープ

**使い道**: Agent に渡すタスク契約（何を達成するか、どこまでが範囲か、何を変えてはいけないか）の土台になる。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 目的 | 誰の、どんな困りごとを、どう解決するものか | 1〜3文で言える。「予約管理システム」のような名詞だけでは不足。誰が何のために使うかが入っている |
| やること | このプロジェクトが提供する大まかな範囲 | 3〜7個程度の大きな塊で言える。個々の機能の一覧にはしない |
| やらないこと | 意図的に範囲から外すもの | 少なくとも、ユーザーの話から「やりそうに見えるが、やらない」ものが拾えている。無ければ `none` |
| 制約 | 守らなければならない前提。使う技術の指定、予算、期限、法令、既存の仕組みとの互換など | 聞いたうえで、あれば列挙、無ければ `none` |

「やること」を細かくしすぎない。「予約の受付」「店舗側の管理画面」「決済」で十分で、「予約の変更は前日まで」は後続の詳細設計の話。細かい話が出たら区分 H に回す。

## B システム境界

**使い道**: Agent が最初に読むプロジェクトの地図の骨格になる。また、外部とのやりとりとデータの保存先は、区分 D のリスクを洗い出す出発点になる。

種類を問わない6つの問いで捉える。種類別の典型例と図の描き方は [boundaries.md](boundaries.md)。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 利用者との接点 | 利用者がどこから触るか。Web 画面、モバイルアプリ、コマンドライン、公開 API、デスクトップの画面など | 接点の種類が列挙されている。複数あれば行を分ける |
| 処理 | 主な処理がどこで動くか。サーバー、利用者の端末、定期実行など | 処理の置き場所が言える。接点と同じ場所で完結するならそう書く |
| データの保存先 | 何かを永続的に保存するか。するなら、どんな種類の保存先か | 保存の有無が確定している。無ければ `none`。「何を保存するか」は大まかでよい |
| 外部とのやりとり | 自分たちが作らない外部のサービス・API・システムとの接続 | 1つずつ行を分け、何のために使うかが一言ある。無ければ `none` |
| 利用者の識別（認証） | 利用者を識別する必要があるか | 要否が確定している。方式（パスワード、SSO など）は決めない。不要なら `none` |
| 配布・実行場所 | 作ったものをどこに置き、どこで動かすか。クラウド、利用者の端末、パッケージ配布、社内サーバーなど | 大まかな置き場所が言える |

表に加えて、境界同士の関係を示すテキストの図を置く。

ここで書くのはシステムの境界であって、Agent の分け方ではない。コンポーネント設計やディレクトリ構造にも踏み込まない。

## C 技術

**使い道**: 次の Skill は、Agent に許可するコマンドを具体的な名前で書く（例: 特定のパッケージマネージャのテスト実行を許可する）。そのため、ツールチェーンが決まる粒度までは確定している必要がある。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 言語 | 主に使うプログラミング言語 | 確定している |
| ランタイム | 実行環境。Node.js、ブラウザ、JVM、ネイティブなど | 確定している |
| パッケージマネージャ | 依存の管理とスクリプト実行に使うもの。ビルドシステムを含む（CMake など） | 確定している。同じ言語でも複数の選択肢がある場合（npm / pnpm / yarn など）は1つに決める |
| 主要フレームワーク | アプリケーションの骨格になるもの | 確定している。使わないなら `none` |
| DB 種別 | データベースの製品（PostgreSQL、SQLite など） | 区分 B で保存先があれば確定している。無ければ `none` |
| デプロイ先種別 | どの種類の場所に出すか。特定のクラウド、コンテナ基盤、パッケージレジストリ、アプリストアなど | 確定している。配布しない（手元で使うだけ）なら `none` |

既存プロジェクトでは、技術は走査で読み取る（[scan.md](scan.md)）。この6項目より細かい選択（テストランナー、linter、ORM、UI ライブラリ、API の様式）は決めない。ユーザーが指定してきた場合は、区分 H に `[deferred]` として残す。

ツールチェーンが複数ある場合（Swift のモバイルアプリと Go の Backend など）は、構成要素ごとに表を分ける。次の Skill は、ツールチェーンの違いを Agent を分ける根拠の1つにする。

## D リスク

**使い道**: 次の Skill は、ここから「自動でやってよい操作／人の承認が要る操作／禁止する操作」の線を引く。この線はどんなに軽い構成を選んでも必ず作られる安全の下限であり、区分 D はその唯一の材料である。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 外部作用 | システムの外へ影響が出る操作。メッセージ送信、課金、外部 API への書き込み、公開、デプロイなど | 区分 B の「外部とのやりとり」と「配布・実行場所」を1つずつ確かめてある。無ければ `none` |
| 不可逆・機微な操作 | 取り返しがつかない、または影響が大きい操作。本番データの削除・変更、認証情報の扱い、全体公開、公開済みの版の変更など | 区分 B の「データの保存先」と本番環境の有無を踏まえて確かめてある。無ければ `none` |
| 秘密情報・個人情報 | API キーなどの秘密情報を扱うか。個人情報や決済情報などの機微な情報を扱うか | それぞれの有無が確定している。無ければ `none` |

聞き方と例は [risk.md](risk.md)。粒度は「何があるか」まで。承認の流れ、権限の設計、暗号化の方式は書かない。

## E 環境

**使い道**: 許可するコマンド（コンテナ操作を含むか）、触ってはいけない環境（本番）、失敗からの戻し方（バージョン管理と CI）を決める材料になる。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 開発環境 | 開発に使う OS。コンテナ（Docker など）を開発に使うか | OS と、コンテナ利用の有無が確定している |
| 実行環境の段階 | local のほかに、staging や本番があるか（または作る予定か） | 段階の有無が確定している。試作で local だけならそう書く |
| リポジトリのホスティング | GitHub、GitLab、社内サーバーなど | 確定している。まだ決めていなければ `deferred` でよい |
| CI | 自動のビルド・テストの仕組みを使うか | 有無が確定している。後で考えるなら `deferred` でよい |

## F リポジトリ構成

**使い道**: プロジェクトの地図と、Agent ごとの書き込み範囲を決める材料になる。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| 単一か分離か | 1つのリポジトリで進めるか、複数に分けるか | 確定している。迷うなら単一を仮定として提案する |
| 最上位の配置 | リポジトリ直下の大きな区切り（例: `apps/web`、`apps/api`、`docs`） | 大きな区切りが言える。その下の構造は決めない |
| 新規か既存か | まっさらな状態から始めるか | この Skill では常に「既存」 |
| 設計文書の場所 | `docs/` 以外に設計文書のフォルダがある場合だけ足す行（`doc/`、`design/` など） | 走査で見つからなければ、この行を作らない |

## G 運用前提

**使い道**: 誰が承認者になるか、引き継ぎのための記録をどこまで手厚くするかの判断材料になる。

| 項目 | 書くこと | 埋まったと言える基準 |
|---|---|---|
| ソロかチームか | 開発する人の数。一人か、複数か | 確定している |
| 試作か本番品質か | 動くものを早く見たい試作か、実際の利用者に出す品質を目指すか | 確定している。途中で変わる予定があればそれも書く |

## H 未決・持ち越し

**使い道**: 次の Skill は読むだけ。後続の詳細設計が出発点として使う。

- ここで決めなかったこと、ユーザーが判断できなかったこと
- ユーザーが話した詳細な機能、画面のイメージ、API やテーブルの案など、この Skill の範囲外の情報の要点
- ユーザーが指定してきた、6項目より細かい技術の選択

各行の先頭に `[deferred]` を付ける。整理しすぎない。ユーザーの言葉に近い形で要点を残せば十分で、ここで分類や構造化を始めると詳細要件の入口になる。何も無ければ「なし」と書く。

## 状態の付け方

| 状態 | 使う場面 |
|---|---|
| `decided` | ユーザーが自分の言葉で述べた。または、提示した選択肢からユーザーが選んだ |
| `assumed` | この Skill がコードから読み取り、Step 2 か Step 3 で見せて、ユーザーがそのまま認めた |
| `none` | 該当するものがない、とユーザーが述べた。または推測して確認が取れた |
| `deferred` | ここでは決めない。理由とともに区分 H にも1行書く |

終了の判定は機械的に行う。A〜G の全行が4つの状態のいずれかを持ち、区分 H が（空なら「なし」と）書かれていれば終了。

`deferred` を逃げ道にしない。区分 C の6項目と区分 D の3項目は、次の Skill が具体的な権限と安全策を書くために必要なので、`deferred` にしてはいけない。ユーザーが決められないなら、推測を提案して `assumed` の確認を取る。
