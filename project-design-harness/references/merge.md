# 既存ファイルとの統合と、再実行

このスキルは、既にハーネスのファイルがあるプロジェクトでも動く。レベルを後から上げる、失敗を受けて直す、プロジェクト定義が変わったので作り直す、といった自分自身の再実行も同じ手順で扱う。
原則は3つ。**書く前に読む。人が書いたものは保つ。承認されてから書く。**

## 初回か再実行かを見分ける

`docs/agent-architecture.md` があり、frontmatter に `generated-by: project-design-harness` があれば再実行。
その「部品一覧」が、前回このスキルが生成したファイルの一覧である。

| 状況 | 扱い |
|---|---|
| 根拠記録が無い。ハーネスのファイルも無い | 初回。すべて新規作成 |
| 根拠記録が無い。`.claude/` や `CLAUDE.md` は既にある | 初回。既存のものはすべて人が書いたものとして扱う |
| 根拠記録がある | 再実行。部品一覧に載っているものだけを、このスキルの持ち物として扱う |

部品一覧に載っているのに実体が無いファイルは、人が消したと見なす。理由を利用者に聞き、要らないなら部品一覧から外す。黙って復活させない。

## ファイルの計画

書き込む前に、計画を利用者に見せて承認を得る。新規のプロジェクトでも同じ手順を踏む。権限と hook は、有効になった瞬間から利用者の環境の振る舞いを変えるので、中身を見てから適用できるようにする。

計画は3分類で示す。

```text
新規作成
  .claude/harness.json              役ごとの書き込み規則
  .claude/hooks/write-boundary.mjs  書き込み境界の hook
  ...
変更
  .claude/settings.json             hooks と permissions を追記（既存の allow 12 件は保持）
  CLAUDE.md                         生成ブロックを末尾に追加（既存の本文は保持）
そのまま
  .claude/skills/my-skill/          人が書いたもの。触らない
```

「変更」に挙げたファイルは、何を足して何を保つのかを1行で添える。利用者が最も気にするのは、自分が書いたものが消えないかどうかである。

## ファイルごとの統合のしかた

### `.claude/settings.json`

JSON として読み、キーごとに追記する。ファイル全体を置き換えない。

- `permissions.deny` / `ask` / `allow`: 配列に、無いものだけを足す。既存の規則は消さない。`Read(.env*)` と、それに続く `Read(!.env.example)` などの除外は、この順番のまま、ひとかたまりで足す（`!` の規則は、それより前にある規則にしか効かない）
- **既存の `allow` が、これから足す `ask` や `deny` と重なる場合**（例: 既存の `Bash(git *)` と、新しい `ask: Bash(git push *)`）。評価の順は `deny` → `ask` → `allow` なので、足した `ask` は効く。消す必要はないが、重なっていることを計画に書いて知らせる
- `hooks.<イベント>`: 配列に、このスキルのハンドラを足す。同じスクリプトを指すハンドラが既にあれば、足さずに内容だけ更新する。人が登録した hook は消さない
- 雛形の `"//"` キー（説明用）は、すべて取り除いてから書く
- 個人用の `.claude/settings.local.json` には触らない

### `CLAUDE.md`

生成ブロックを、目印のコメントで挟んで書く。

```text
<!-- project-design-harness:begin ... -->
（このスキルが管理する内容）
<!-- project-design-harness:end -->
```

- 目印が既にあれば、その間だけを置き換える。目印の外は一切触らない
- 目印が無く `CLAUDE.md` が既にあれば、末尾に生成ブロックを足す。既存の本文が、生成ブロックの内容（主セッションは `docs/` 以外を書かない、など）と矛盾していたら、矛盾を利用者に示して、どちらを直すか決めてもらう。黙って上書きしない
- `CLAUDE.md` が無ければ、生成ブロックだけのファイルを作る

### `.mcp.json`

`mcpServers` に、無いサーバーだけを足す。既存のサーバーの設定は変えない。利用者が明示したサーバー以外は足さない。

### `.claude/agents/*.md`、`.claude/skills/*/`、`.claude/hooks/*`、`.claude/rules/*.md`

- 同じ名前のファイルが無ければ、新規作成
- 同じ名前のファイルが部品一覧にあれば（前回このスキルが作った）、置き換えの候補。ただし、前回の生成後に人が手を入れている可能性がある。雛形から作り直した内容と現在の内容を比べ、雛形に無い追記があれば、それを保ったまま更新するか利用者に聞く
- 同じ名前のファイルが部品一覧に無ければ（人が作った）、触らない。名前が衝突する役（`implementer` など）が既にある場合は、利用者に、既存のものを使うか、このスキルのものに置き換えるかを聞く
- hook のスクリプト（`.mjs`）は、人が編集することを想定していない。部品一覧にあれば、最新の雛形で置き換える

### `.claude/harness.json`

- `roles`: このスキルが生成した役の規則は更新する。利用者が足した役（部品一覧の役の一覧に無い名前）は保つ
- `verify`、`trace`、`level`: 選ばれたレベルに合わせて更新する
- `messages`: 利用者が書き換えた文は保つ

### `docs/agent-architecture.md`

このスキルの持ち物なので、作り直してよい。ただし「変更履歴」は消さずに、今回の変更を1行足す。
振り返り skill で足された部品が部品一覧に載っていれば、それも保つ。

### `docs/harness/state.md` とタスクのフォルダ

既にあれば、触らない。中身は作業の記録であり、このスキルの再実行で作り直すものではない。

## 再実行の場合分け

| きっかけ | やること |
|---|---|
| レベルを上げる | 足されるレベルの生成物だけを計画に載せる。既にあるレベルの部品は、雛形が変わっていなければ「そのまま」 |
| レベルを下げる | 外れるレベルの部品を「削除」として計画に載せる。削除も承認を得てから。`docs/harness/` の記録（状態、契約、レシート、トレース）は消さない |
| プロジェクト定義の C・D・E が変わった | Policy 表を作り直して、もう一度利用者に確認する。役の構成（ツールチェーンの数、運用役の要否）も判定し直す |
| 振り返りの結果を反映する | 通常は `harness-retro` skill がその場で適用する。このスキルの再実行は、レベルの変更か、プロジェクト定義の変更を伴うときに使う |
| スキル自体が新しくなった | 部品一覧のファイルを最新の雛形と比べ、差があるものを「変更」として載せる |

再実行でも、3段階の確認（レベル、Policy 表、ファイルの計画）は省かない。ただし前回から変わらない段階は、「前回と同じです」と一言で済ませてよい。

## 書き込むとき

- `.claude/` と `.mcp.json` は Claude Code の保護パスなので、書き込みのたびに承認の確認が出ることがある。計画を承認した直後に確認が続くのは正常な動作だと、先に利用者へ伝えておく
- 既にこのスキルの書き込み境界 hook が有効なプロジェクトでは、ハーネスのファイルへの書き込みごとに hook が承認を求める。これも正常
- 書く順は、`harness.json` → hook のスクリプト → agents → skills → rules → `docs/harness/state.md` → `docs/agent-architecture.md` → `CLAUDE.md` → `.mcp.json` → **最後に `settings.json`**。
  設定ファイルの hook は、書いた時点からそのセッションでも効き始めうる。`settings.json` を先に書くと、まだ設定が揃っていない状態で関門が動き、残りの生成が、ハーネスのファイルへの書き込みとして1つずつ承認待ちになる。最後に書けば、それを避けられる
- 書き終えたら、実体と部品一覧が一致しているかを確かめる
