## 出発点: 失敗の多くは環境の失敗

Agent がうまくいかないとき、多くの人は指示文を書き直し、モデルを替え、道具を足す。しかし失敗の多くは推論の失敗ではなく、モデルを取り巻く環境の不備から起きる。
指示文が変えるのは1回の試行で、環境（ハーネス）が変えるのはすべての試行である。

典型的な環境の失敗は6つあり、それぞれに対応するハーネスの部品がある。**このスキルが生成するものはすべて、この6つのどれかを防ぐためにある**。どれも防がない部品は生成しない。

| 環境の失敗 | 防ぐ部品 | 区分 |
|---|---|---|
| どのファイルが大事か分からなかった | プロジェクトの地図、パス別のローカル指示 | Context |
| 正しい道具を、間違った場所で使った | 役ごとの書き込み境界、道具の絞り込み | Tools |
| 前のセッションで決めたことを失った | 永続状態（事実・判断・進捗・教訓） | State |
| 検査を走らせずに、成功したと言った | 完了ゲート、検証役、変更レシート | Verification |
| 一部だけ失敗したあと、同じ操作を繰り返した | 失敗の分類、再試行の上限、エスカレーション | Recovery |
| 承認が要るはずの操作を、実行する権限があった | 承認と禁止の規則、ハーネス自身の保護 | Policy |

ハーネス設計の目的は、モデルの不確かさを無くすことではない。不確かさを、観測でき、検証でき、回復できる仕組みの内側に封じ込めることである。

## 8つの区分

Agent に意味のある自律性を与える前に、次の8区分を定義する。未定義の区分があるなら、その Agent は自律しているのではなく、即興で動いている。
`docs/agent-architecture.md` の「8区分の設計」は、この順で書く。

### 1. Contract（タスク契約）

**定義**: 曖昧な依頼を、実行の前に契約へ変換したもの。5つの問いに答える。あるべき結果は何か。スコープの内側は何か。変えてはいけないものは何か。何が完了の証拠か。承認が要る操作はどれか。

**なぜ要るか**: 契約が無いと、Agent は「次に何をしようか」を考え、もっともらしい活動を最適化する。契約があると、「どの操作が、約束した結果に環境を近づけるか」を考え、検証された完了を最適化できる。

**実現**: プロジェクト skill `task-contract` と、`docs/harness/tasks/<タスクID>/contract.md`。契約を書くのは主セッション（ユーザーに質問できる唯一の役）。プロジェクト全体に共通する「変えてはいけないもの」と「承認が要る操作」は、プロジェクト定義の区分 A・D から skill に埋め込む。

### 2. Context（地図と文脈）

**定義**: 常に読み込む小さな地図と、必要になったときに辿る詳細。文脈は、情報が存在するからではなく、タスクが必要とするから広がる。

```text
タスク → プロジェクトの地図 → 関係する領域 → 該当のファイル → その場所のローカル指示
```

**なぜ要るか**: リポジトリと文書と会話履歴をすべて文脈に流し込むのは、文脈の設計ではなく洪水である。目指すのは文脈の最大化ではなく、トークンあたりの信号の最大化。

**実現**: `CLAUDE.md` は地図であって説明書ではない。書くのは、何がどこにあるかの対応表とコマンドだけ。中身の説明は `docs/` に置いて指す。領域ごとの決まりは `.claude/rules/*.md` に `paths:` つきで置くと、その場所のファイルを触ったときだけ読み込まれる。`CLAUDE.md` の生成ブロックは 80 行以内を目安にする（公式の目安は 1 ファイル 200 行以内）。

**鮮度**: 地図が古くなると、無いより悪い。構成が変わったら地図を直すことを、実装役の報告形式（「変更点」）と振り返りで拾う。

### 3. Tools（道具の関門）

**定義**: 道具を積み上げるのではなく、関門を通して使わせること。モデルは操作を提案でき、関門が、その操作を実行してよいかを決める。

```text
モデルが意図を決める → 関門が操作を検証する → 道具が環境を変える → 結果を観測する
```

**なぜ要るか**: 道具を20個渡すことは、20通りの間違い方を渡すことでもある。

**実現**: 関門がやれることと、Claude Code での対応。

| 関門の働き | 実現 |
|---|---|
| 関係のない道具を隠す | subagent 定義の `tools` / `disallowedTools` |
| パスを制限する | 書き込み境界 hook（役ごと）、`permissions` の `Edit(...)` / `Read(...)` 規則 |
| 危険な操作に確認を求める | `permissions.ask`、hook の `ask` 判定 |
| 時間切れを付ける | hook の `timeout`、検証コマンドの `timeoutSec` |
| 成功の申告ではなく証拠を返させる | 検証コマンドの出力をそのまま Agent に返す（完了ゲート） |
| 外部の道具を絞る | `.mcp.json` に載せるサーバーを、プロジェクト定義にある外部サービスに限る |

### 4. State（永続状態）

**定義**: 会話履歴を、明示的な状態に変換したもの。最低限、4種類を保つ。事実（環境について分かった、変わりにくい情報）。判断（決めたことと、その理由）。進捗（完了・作業中・停止中・残り）。教訓（次の振る舞いを変えるべき失敗）。

**なぜ要るか**: 会話履歴は記憶ではなく、出来事の流れである。50ページの記録を読み返させて、大事な1行に気づくことを期待するより、状態として渡す方がはるかに確実。生の履歴は監査のために残し、実行のためには編集された状態を使う。

**実現**: `docs/harness/state.md`。`CLAUDE.md` から `@docs/harness/state.md` で読み込むので、毎セッションの文脈に入る。だから短く保つ（80 行以内）。終わったタスクの詳細はレシートに移す。生の履歴は Claude Code の transcript が持っている。

**頭・手・履歴の分離**: 推論する役（頭）、限られた環境で操作を実行する役（手）、文脈が消えたあとも起きたことを保つもの（履歴）を分ける。このスキルでは、主セッションと各 subagent が頭と手、`docs/` の設計文書と `docs/harness/` が履歴にあたる。分けておくと、途中から再開でき、部分だけを取り替えられる。

### 5. Policy（承認と禁止）

**定義**: モデルが覚えているかどうかに依存させてはいけない決まり。承認なしに公開しない。秘密を漏らさない。作業場所の外に書かない。走らせていないテストを通ったことにしない。これらは指示文の提案ではなく、Policy である。

**なぜ要るか**: 最も安全な設計は、Policy を推論の外に置く。自律とは統制が無いことではなく、はっきり強制された境界の内側で自由に動けることである。

**実現**: 結果が重いほど、関門を固くする。詳しくは [policy.md](policy.md)。

| 階級 | 例 | 扱い |
|---|---|---|
| 読むだけ | 読む、検索する | 自動 |
| 可逆な変更 | 作業場所の編集、テストの実行 | 自動 |
| 外部作用 | メッセージ送信、デプロイ、課金 | 明示の承認（`ask`） |
| 不可逆・機微 | データ削除、認証情報の変更、全体公開 | 禁止（`deny`）か、強い関門 |

### 6. Verification（検証）

**定義**: 2つの別々の仕組み。**完了の証拠**（完了は、環境の観測できる変化で決まる）と、**敵対的検証**（作る側と壊す側で目的を分ける）。

**なぜ要るか**: Agent が「終わった」と言うのは証拠ではなく、もう1つのモデル出力にすぎない。モデルは完了を提案でき、証明できるのは環境だけ。また、同じ Agent に同じ文脈で「確かめ直して」と頼むと、誤りを生んだ思い込みが引き継がれる。検証はセカンドオピニオンではなく、反証の試みである。

**実現**:

- 完了の証拠は、安く決定的な検査から走らせる。構文 → 型 → 対象を絞ったテスト → 結合テスト → 目で見る確認 → 人の承認。コンパイラやテストで答えが出ることに、別のモデルを使わない
- プロジェクトは「検証を一括で走らせる単一のコマンド」を提供する、と取り決める。完了ゲート hook（`SubagentStop`）がそれを実行し、落ちたら実装役を止めずに出力を返して続けさせる。テストランナーが何であっても同じ形で動く
- 検証役 subagent は、却下の基準を明示され、成果物と契約を読め、実装役とは別の文脈で動き、**直さずに却下する権限**を持つ（書き込みは仕組みで止める）

### 7. Recovery（回復）

**定義**: 失敗の種類を見分けてから、次の一手を選ぶこと。「失敗した、もう一度」は回復ではなく反復である。再試行は、関係のある条件を少なくとも1つ変えなければ、同じ失敗を費用をかけて再現するだけになる。

| 失敗の種類 | 次の一手 |
|---|---|
| 時間切れ | 間隔をあけて再試行 |
| 引数の誤り | 呼び出しを直す |
| 情報の不足 | 必要な出典を特定して読む |
| テストの失敗 | 失敗している振る舞いを調べる |
| 権限で拒否 | 承認を求めるか、安全な経路を選ぶ |
| 要件の矛盾 | 人に判断を仰ぐ |
| 変化のない失敗の繰り返し | ループを止める |

**なぜ要るか**: 信頼できる Agent は、続け方を知っているだけでなく、続けることがもう合理的でない時点を知っている。どのループにも予算が要る。試行回数、時間、費用、破壊的な操作の範囲、エスカレーションの条件。

**実現**: 完了ゲートの `maxBlocks`（上限を超えたら止めて人に伝える）は L5 から入る。L6 で、実装役の定義に失敗の分類表と「同じ原因で2回失敗したら止まる」を足し、subagent 定義に `maxTurns` を付ける。安全に戻す手段は git（作業の区切りでコミットし、戻せる点を作る）。

### 8. Observability（観測）

**定義**: 最終成果物だけでなく、過程を再構成できること。目的は監視ではなく、その場での修理。18手目で失敗したら、全体をやり直すのではなく、信頼できる地点から再開できるようにする。

**なぜ要るか**: きれいな成果物が、ひどい過程を隠していることがある。間違ったデータを見た。失敗したコマンドを無視した。外部操作を2回実行した。正しい答えに、間違った理由で辿り着いた。

**実現**: 2つの成果物。

- **トレース**（L6）: 節目の出来事だけを `docs/harness/traces/` に1行ずつ追記する。止められた操作、検証の合否、役の開始と終了。ツールの入力内容は記録しない（秘密情報が混入するため）。全履歴は transcript に任せる
- **変更レシート**（L5）: タスクの終わりにまとめる小さな文書。目的／変更点／検証済み／未検証／判断／リスク／承認待ち。Agent が言ったことの要約ではなく、仕組みが証明できることの要約

## 区分をまたぐ3つの原則

### 指示は、仕組みへ移す

指示文は、その場の事情を説明するには役立つが、強制としては弱い。繰り返し大事になる決まりは、下の段へ移す。

```text
説明 → チェックリスト → 雛形 → 自動の検査 → 強制
```

指示文は判断を説明するためのもの。変わらない決まりを守らせるのは、ハーネスの仕事である。
このスキルが、設計書駆動の分業を「指示」ではなく書き込み境界 hook で実現しているのは、この原則による。

### 失敗は、ハーネスを育てる

失敗した成果物を直すだけでなく、それを許した仕組みを直す。診断は8つの問い（契約は曖昧だったか、文脈は見えていたか、間違った道具が使えたか、前提条件は欠けていたか、結果は検証できたか、決まりは指示文の中にしか無かったか、回復は大ざっぱすぎたか、トレースは足りたか）。
直した答えはその1回を助け、直したハーネスは以後のすべてを助ける。実現はプロジェクト skill `harness-retro`（L6）。

### ハーネスも古びる

ハーネスは多いほど良いものではない。昨日のモデルの弱点のために作った回避策が、今日のモデルのより良いやり方を妨げることがある。
部品は本番のコードと同じように扱い、まだ効いているかを測る。部品ごとに5つを問う。どの失敗を防ぐか。その失敗は今も起きるか。どれだけの遅さと複雑さを足しているか。もっと単純にできないか。外したら何が起きるか。

**外すために作る**。このスキルが `docs/agent-architecture.md` に「部品一覧」と「防ぐ失敗」を必ず書くのは、後でこの5つに答えられるようにするためである。

## 生成物を評価する物差し

最良のハーネスは最大のものではなく、**意図と証拠の間の溝を確実に埋める、最小の仕組み**である。
このスキルでハーネスを生成するとき、次の4つを自分に問う。

1. **この部品は、6つの失敗のどれを防ぐか**。答えられなければ生成しない
2. **このプロジェクトに、その失敗は起こりうるか**。外部作用の無い CLI に、運用役は要らない
3. **指示文で済ませていないか**。何度も大事になる決まりなら、仕組みに落とす。1回限りの事情なら、指示文のままでよい
4. **後で外せるか**。部品一覧に載り、防ぐ失敗が書かれ、消せば元に戻る形になっているか

測るべきは Agent の活動量ではなく、人の注意あたりの、信頼できる成果である（受け入れられた成果 ÷（人のレビュー時間 ＋ 実行費用））。
忙しく見える Agent が、高くつくレビュー作業を生んでいることがある。
