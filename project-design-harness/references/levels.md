# 土台と6つのレベル

生成物は「必ず入る土台」と、その上に累積で足す「6つのレベル」からなる。
利用者への説明は一言で言うと、**土台は必ず入る。その上にどこまで足すかを選ぶ**。

このファイルは、利用者にレベルを説明するときの元になる。ハーネスに詳しくない利用者でも選べるかどうかは、この説明の分かりやすさに懸かっている。
説明するときは部品の名前ではなく、**防げる失敗**で語る。

## 一覧

| 層 | 防ぐ失敗（利用者への一言） | 足されるもの |
|---|---|---|
| 土台 | 設計を経ずにコードが変わる。承認が要る操作を実行してしまう。Agent が自分の権限を広げる | 役（主セッション・実装役・調査役）、書き込み境界、Policy 下限、根拠記録 |
| L1 | 曖昧な依頼のまま作業が始まり、終わりの条件が無い | タスク契約の skill と雛形 |
| L2 | どこに何があるか分からず、全部読むか、見当違いを読む | 地図とコマンド一覧、パス別のローカル指示 |
| L3 | 確認の要らない操作で毎回止まる。関係のない道具を使う | 許可リスト、役ごとの道具の絞り込み、外部ツールの設定 |
| L4 | セッションが変わると、決めたことと進み具合を失う | 作業状態のファイルと更新の決まり |
| L5 | 検査を走らせずに「終わった」と言う。作った本人の確認で済ませる | 完了ゲート、検証役、変更レシート |
| L6 | 同じ失敗を繰り返す。失敗の経緯が追えない。ハーネスが古びる | 失敗の分類と上限、トレース、振り返り skill |

## 土台

レベルに関係なく、常に生成する。このスキル体系の前提（設計書から始める分業と、最低限の安全）を成り立たせる部分なので、選択の対象にしない。

| 生成物 | 内容 |
|---|---|
| `.claude/agents/implementer.md` | コードを書く役。ツールチェーンが複数あれば複数になる（[agents.md](agents.md)） |
| `.claude/agents/researcher.md` | 読み取り専用の調査役 |
| `.claude/agents/operator.md` | 区分 D を根拠にした承認つきコマンドが、1つ以上できたときだけ（[agents.md](agents.md)） |
| `.claude/harness.json` | 役ごとの書き込み規則、承認・禁止するコマンド、保護するパス（[harness-config.md](harness-config.md)） |
| `.claude/hooks/write-boundary.mjs`、`.claude/hooks/lib/harness.mjs` | 関門の hook。コマンドの承認と禁止（役ごと）、書き込み境界、ハーネス保護 |
| `.claude/settings.json` | hook の登録、2枚目の網としての `deny` と `ask`、秘密情報ファイルの読み取り禁止 |
| `CLAUDE.md`（生成ブロック） | 主セッションの役割、安全の決まり、プロジェクト定義を更新するときの決まり |
| `docs/agent-architecture.md` | 根拠記録。役の一覧、Policy 表、部品一覧、変更履歴 |

**代償**: 軽微な修正でも「設計文書 → 委任」の往復が発生する。小さな変更は遅くなる。これは、設計と実装が静かにずれていく失敗と引き換えにしている。

## L1 境界のあるタスク

**防ぐ失敗**: 「〜を改善して」のまま作業が始まり、Agent がもっともらしい活動を積み上げる。終わったかどうかを誰も判定できない。

| 生成物 | 内容 |
|---|---|
| `.claude/skills/task-contract/SKILL.md` | 依頼を5つの問いで契約に変換する手順 |
| `.claude/skills/task-contract/contract.template.md` | 契約の雛形 |
| `CLAUDE.md` の「作業の流れ」 | 委任の前に契約を書く、という流れ |

契約の置き場は `docs/harness/tasks/<タスクID>/contract.md`。
**代償**: 委任のたびに契約を書く手間。小さな依頼なら5行で済む。

## L2 読める環境

**防ぐ失敗**: Agent がどのファイルが大事か分からず、リポジトリ全体を読んで文脈を使い果たすか、見当違いの場所を直す。

| 生成物 | 内容 |
|---|---|
| `CLAUDE.md` の「地図」 | 知りたいこと → 場所 の対応表。プロジェクト定義の区分 B・F から作る |
| `CLAUDE.md` の「コマンド」 | 依存の導入、起動、検証など。区分 C・E から作る |
| `.claude/rules/<領域>.md` | コードを置く領域ごとの、`paths:` つきローカル指示。その場所を触ったときだけ読み込まれる。雛形は `assets/rules/area.template.md` |

既存プロジェクトでは、地図は今ある場所の対応表になり、コマンドの一覧には、区分 H に持ち越された既存の検証系コマンドも載せる。
新規プロジェクトではコードがまだ無いので、地図は「これから置く場所」の対応表になる。コマンドの一覧に載せるのは、プロジェクト定義から確定しているもの（依存の導入、L5 以上なら検証コマンド）だけ。開発サーバーの起動のような、まだ決まっていないコマンドを推測で載せない。
領域ごとのローカル指示は、区分 F の最上位の配置に、コードを置く領域が2つ以上あるときだけ作る。1つしかないなら作らない。`docs` は領域に数えない。
**代償**: 構成が変わったら地図を直す必要がある。古い地図は、無いより悪い。

## L3 制御された操作

**防ぐ失敗**: 安全な操作（テストの実行など）で毎回承認を求められて流れが止まる。逆に、役に関係のない道具まで使えてしまう。

| 生成物 | 内容 |
|---|---|
| `.claude/settings.json` の `allow` | ツールチェーンの日常操作の許可リスト。区分 C・E から導く（[policy.md](policy.md)）。開発環境が Windows なら `PowerShell(...)` の形でも書く |
| 各 subagent の `disallowedTools` | `.mcp.json` を作った場合だけ、その役に要らない MCP サーバーをサーバー単位で外す。コマンドの制限には使わない |
| `.mcp.json` | 区分 B の外部サービスに対応する MCP サーバーを使う、と利用者が明示したときだけ。推測で足さない |

**代償**: 許可リストに無いコマンドは承認待ちになる。ツールチェーンが増えたら、リストを足す必要がある。

## L4 永続実行

**防ぐ失敗**: セッションが変わるたびに、前に決めたことと進み具合を失い、同じ議論と同じ調査を繰り返す。

| 生成物 | 内容 |
|---|---|
| `docs/harness/state.md` | 事実・判断・進捗・教訓 |
| `CLAUDE.md` の「作業状態」 | `@docs/harness/state.md` の読み込みと、更新の決まり |

実装役は `docs/harness/` 以下に書けるので、進捗と教訓を自分で更新できる。設計文書には書けない。
**代償**: 状態ファイルは毎セッションの文脈に入るので、短く保つ手間が要る。終わったタスクの詳細はレシートに移す。

## L5 証拠

**防ぐ失敗**: Agent が検査を走らせずに「終わりました」と言う。作った本人に確かめさせて、思い込みごと通してしまう。長いやりとりを人が読み返せない。

| 生成物 | 内容 |
|---|---|
| `.claude/harness.json` の `verify` | 検証コマンド、実行する場所、時間切れ、対象の役、続けさせる回数の上限 |
| `.claude/hooks/completion-gate.mjs` と、`SubagentStop`・`PostToolUse`（`Agent`）への登録 | 実装役が完了を報告して終わろうとしたら検証コマンドを走らせ、落ちたら出力を返して続けさせる。上限を超えたら止めて、利用者と主セッションの両方に「未検証」を伝える。差し戻し（`HANDBACK:` で始まる報告）は完了の主張ではないので、検証せずに通す |
| `.claude/agents/verifier.md` | 別の文脈で結果を壊しにいく役。直さずに却下する |
| `.claude/skills/change-receipt/` | 変更レシートの手順と雛形 |

**検証コマンドの取り決め**: プロジェクトは、検証を一括で走らせる単一のコマンドを、プロジェクトのルートから実行できる形で提供する（例: `pnpm run verify`、`make verify`）。名前は区分 C のパッケージマネージャから決める。中身（何のテストを走らせるか）は後続の詳細設計と実装が決める。まだ無い状態で実装役が終わろうとすると、ゲートが落ち、「まずこのコマンドを用意せよ」という指示が返る。これは意図した動作で、最初のタスクで検証の入口が作られる。
**代償**: 実装役が終わるたびに検証コマンドの実行時間がかかる。検証役への委任で、タスクあたりの時間と費用が増える。

## L6 回復と学習

**防ぐ失敗**: 同じ失敗を、条件を変えずに繰り返す。失敗したとき、どこで何が起きたのか追えない。効かなくなった対策が、摩擦として残り続ける。

| 生成物 | 内容 |
|---|---|
| 実装役の定義の「失敗したとき」 | 失敗の分類表と、同じ原因で2回失敗したら止まる決まり |
| 各 subagent の `maxTurns` | 1回の委任の上限 |
| `.claude/harness.json` の `trace.enabled: true`、`.claude/hooks/trace.mjs` と登録 | 節目の出来事の記録 |
| `.claude/skills/harness-retro/SKILL.md` | 失敗から育てる、効かない部品を外す |

トレースに記録するのは、止められた操作、検証の合否、役の開始と終了だけ。ツールの入力内容は記録しない。
設計への差し戻しと再試行の理由は hook からは観測できないので、実装役の報告とレシートに残る。
**代償**: 最も部品が多い。初回から入れても、振り返りの材料（失敗と教訓）がまだ無い。

## 推奨と、上げ下げの目安

**標準は常に L3**。入力によって変えない。L3 は、このプロジェクトに最適だという診断ではなく、どのプロジェクトにも共通の出発点である。
利用者には「標準は L3 です。ここから、プロジェクトに合わせて上げ下げしてください」と伝え、下の目安を添える。どの目安が当てはまるかを判断するのは利用者である。この Skill は、プロジェクト定義を見て「あなたの場合は L5 が良い」のような個別の推奨をしない。

下げてよいのは、次が当てはまるとき。

- 作業が短く、成果物を目で見てすぐ確かめられる
- 失敗しても安く済む。外部への作用が無い
- 人が常に画面を見ている

上げた方がよいのは、次が当てはまるとき。

- 作業が複数のセッションにまたがる → L4
- 行動に現実の結果が伴う。完了を人の目で判定しにくい → L5
- 同じ失敗が繰り返し現れる。人のレビューが詰まりになっている → L6

L6 は、失敗と教訓が溜まってから再実行で上げるのが自然である。複雑さは、観測された失敗で獲得するもの。ただし利用者が最初から選ぶことは妨げない。
どのレベルでも、安全の下限（土台の Policy）は同じ。レベルが軽いから危険、ということにはならない。

## 利用者への見せ方

レベルの選択を求めるときは、次の要素を含める。

1. 土台は必ず入ること、その中身を2〜3行で
2. 各レベルを「防ぐ失敗」で1行ずつ。部品の名前は括弧で添える程度にする
3. 標準は L3 であること、下げる目安と上げる目安。目安は一般論として示し、個別の診断にしない
4. 後から上げ下げできること（このスキルの再実行で）

選択式の質問ツール（`AskUserQuestion`）は選択肢が4つまでなので、6レベルの説明は先に本文で示し、質問では「L3（標準）／L5／L1〜L2 に下げる／L6」のように代表的な選択肢を出して、それ以外は自由入力で受ける。
