# 土台と、仕組みの6段階

生成物は「必ず入る土台」と、その上に累積で足す「仕組みの6段階」からなる。
メンバー（役）は土台に入っていて、利用者がどの段階を選んでも全員揃う。段階が変えるのは、仕組みだけである。

## 利用者に見せる言葉

**利用者に、段階の番号や記号を見せてはいけない**。「L3」「レベル 5」「段階 4 まで」と言われても、利用者には何のことか分からない。
利用者に見せるのは、下の表の「呼び名」と、「普段の使い方がどう変わるか」「何を防げるか」である。番号は、内部の記録（`harness.json` の `level`、雛形の出し分けの目印）にだけ使う。根拠記録は利用者が開く文書なので、frontmatter にも番号ではなく呼び名を書く（`mechanisms:`）。

| 番号（内部用） | 呼び名（利用者に見せる） | 普段の使い方がどう変わるか | 防げること |
|---|---|---|---|
| 0 | メンバーと安全の決まりだけ | 設計は主セッションと話し、コードとテストは担当の役が書く。危険な操作は承認か禁止になる | 設計を経ずにコードが変わる。通らないテストを書き換えて通す。承認が要る操作を実行してしまう |
| 1 | 依頼を契約にしてから始める | 「〜を直して」と頼むと、作業の前に、何ができたら終わりかを短い文書にする | 曖昧な依頼のまま作業が始まり、終わったかどうかを誰も判定できない |
| 2 | プロジェクトの地図を持たせる | 何がどこにあるか、どのコマンドを使うかを、Agent が最初から知っている | 全部読んで文脈を使い果たす。見当違いの場所を直す |
| 3 | 日常の操作で止まらないようにする（標準） | テストの実行や依存の導入のような安全な操作で、いちいち承認を求められなくなる | 承認の確認が多すぎて、考えずに承認する癖が付く |
| 4 | セッションをまたいで引き継ぐ | 決めたことと進み具合がファイルに残り、次のセッションがそこから始まる | 日をまたぐたびに、同じ議論と同じ調査を繰り返す |
| 5 | 終わったと言う前に検査を通す | 実装役が「終わりました」と言う前に、検査が自動で走る。通らなければ作業に戻される。タスクごとに、何が証明され、何が証明されていないかの短い報告が残る | 検査を走らせずに「終わった」と言う。長いやりとりを読み返さないと、何が起きたか分からない |
| 6 | 失敗を記録して、仕組みを育てる | 止められた操作や検査の失敗が記録され、同じ失敗が続いたら、仕組みの側を見直す手順が使える | 同じ失敗を、条件を変えずに繰り返す。効かなくなった対策が、摩擦として残り続ける |

段階は累積である。「セッションをまたいで引き継ぐ」を選ぶと、それより上の行（契約、地図、日常の操作）もすべて入る。

## 土台

段階に関係なく、常に生成する。このスキル体系の前提（設計書から始める分業と、最低限の安全）を成り立たせる部分なので、選択の対象にしない。

| 生成物 | 内容 |
|---|---|
| `.claude/agents/researcher.md`、`test-writer.md`、`implementer.md`、`reviewer.md`、`verifier.md` | 常に作る役（[agents.md](agents.md)）。ツールチェーンが複数あれば、コード実装とテスト実装は複数になる |
| `.claude/agents/security-reviewer.md` | 区分 D の3項目のうち、1つでも `none` でないものがあるとき |
| `.claude/agents/operator.md` | 区分 D を根拠にした承認つきコマンドが、1つ以上できたとき |
| `.claude/harness.json` | 役ごとの書き込み規則、設計文書とテストの置き場、承認・禁止するコマンド、保護するパス（[harness-config.md](harness-config.md)） |
| `.claude/hooks/write-boundary.mjs`、`.claude/hooks/lib/harness.mjs` | 関門の hook。コマンドの承認と禁止（役ごと）、書き込み境界、ハーネス保護 |
| `.claude/settings.json` | hook の登録、2枚目の網としての `deny` と `ask`、秘密情報ファイルの読み取り禁止 |
| `CLAUDE.md`（生成ブロック） | 主セッションの役割、メンバー、作業の流れ（テストが先）、安全の決まり、プロジェクト定義を更新するときの決まり |
| `docs/agent-architecture.md` | 根拠記録。役の一覧、Policy 表、部品一覧、変更履歴 |

**代償**: 軽微な修正でも「設計文書 → テスト → 実装 → レビュー → 検証」の往復が発生する。小さな変更は遅くなる。これは、設計と実装が静かにずれていく失敗、テストが形だけになる失敗と引き換えにしている。

## 段階 1: 依頼を契約にしてから始める

| 生成物 | 内容 |
|---|---|
| `.claude/skills/task-contract/SKILL.md` | 依頼を5つの問いで契約に変換する手順 |
| `.claude/skills/task-contract/contract.template.md` | 契約の雛形 |

契約の置き場は `docs/harness/tasks/<タスクID>/contract.md`。この段階を入れない場合、主セッションは、依頼を4点（あるべき結果、スコープ、変えてはいけないもの、完了の証拠）に口頭で整理してから委任する。
**代償**: 委任のたびに契約を書く手間。小さな依頼なら5行で済む。

## 段階 2: プロジェクトの地図を持たせる

| 生成物 | 内容 |
|---|---|
| `CLAUDE.md` の「地図」 | 知りたいこと → 場所 の対応表。プロジェクト定義の区分 B・F から作る |
| `CLAUDE.md` の「コマンド」 | 依存の導入、検証など。区分 C・E から作る |
| `.claude/rules/<領域>.md` | コードを置く領域ごとの、`paths:` つきローカル指示。その場所を触ったときだけ読み込まれる。雛形は `assets/rules/area.template.md` |

既存プロジェクトでは、地図は今ある場所の対応表になり、コマンドの一覧には、区分 H に持ち越された既存の検証系コマンドも載せる。
新規プロジェクトではコードがまだ無いので、地図は「これから置く場所」の対応表になる。コマンドの一覧に載せるのは、プロジェクト定義から確定しているものだけ。開発サーバーの起動のような、まだ決まっていないコマンドを推測で載せない。
領域ごとのローカル指示は、区分 F の最上位の配置に、コードを置く領域が2つ以上あるときだけ作る。1つしかないなら作らない。`docs` は領域に数えない。
**代償**: 構成が変わったら地図を直す必要がある。古い地図は、無いより悪い。

## 段階 3: 日常の操作で止まらないようにする（標準）

| 生成物 | 内容 |
|---|---|
| `.claude/settings.json` の `allow` | 日常の操作の許可リスト。依存の導入、テストと画面テストの実行、コンテナの操作、検索、設計文書への書き込み、作業ブランチへのコミットと push。区分 C・E と git から導く（[policy.md](policy.md)）。開発環境が Windows なら `PowerShell(...)` の形でも書く |
| 各 subagent の `disallowedTools` | `.mcp.json` を作った場合だけ、その役に要らない MCP サーバーをサーバー単位で外す。コマンドの制限には使わない |
| `.mcp.json` | 区分 B の外部サービスに対応する MCP サーバーを使う、と利用者が明示したときだけ。推測で足さない |

**代償**: 許可リストに無いコマンドは承認待ちになる。ツールチェーンが増えたら、リストを足す必要がある。

## 段階 4: セッションをまたいで引き継ぐ

| 生成物 | 内容 |
|---|---|
| `docs/harness/state.md` | 事実・判断・進捗・教訓 |
| `CLAUDE.md` の「作業状態」 | `@docs/harness/state.md` の読み込みと、更新の決まり |

コード実装役とテスト実装役は `docs/harness/` 以下に書けるので、進捗と教訓を自分で更新できる。設計文書には書けない。
**代償**: 状態ファイルは毎セッションの文脈に入るので、短く保つ手間が要る。終わったタスクの詳細はレシートに移す。

## 段階 5: 終わったと言う前に検査を通す

| 生成物 | 内容 |
|---|---|
| `.claude/harness.json` の `verify` | 検証コマンド、実行する場所、時間切れ、対象の役、続けさせる回数の上限 |
| `.claude/hooks/completion-gate.mjs` と、`SubagentStop`・`PostToolUse`（`Agent`）への登録 | コード実装役が完了を報告して終わろうとしたら検証コマンドを走らせ、落ちたら出力を返して続けさせる。上限を超えたら止めて、利用者と主セッションの両方に「未検証」を伝える。差し戻し（`HANDBACK:` で始まる報告）は完了の主張ではないので、検証せずに通す |
| `.claude/skills/change-receipt/` | 変更レシートの手順と雛形 |

検証役は土台に入っているので、この段階で足されるのは「自動で走る検査」と「レシート」である。
対象はコード実装役だけ。テストが先の流れでは、テスト実装役が終わる時点でテストが落ちているのが正しいので、テスト実装役には掛けない。

**検証コマンドの取り決め**: プロジェクトは、検証を一括で走らせる単一のコマンドを、プロジェクトのルートから実行できる形で提供する（例: `pnpm run verify`、`make verify`）。名前は区分 C のパッケージマネージャから決める。中身（何のテストを走らせるか）は後続の詳細設計と実装が決める。まだ無い状態でコード実装役が終わろうとすると、検査が落ち、「まずこのコマンドを用意せよ」という指示が返る。これは意図した動作で、最初のタスクで検証の入口が作られる。
**代償**: コード実装役が終わるたびに、検証コマンドの実行時間がかかる。

## 段階 6: 失敗を記録して、仕組みを育てる

| 生成物 | 内容 |
|---|---|
| コード実装役の定義の「失敗したとき」 | 失敗の分類表と、同じ原因で2回失敗したら止まる決まり |
| 各 subagent の `maxTurns` | 1回の委任の上限 |
| `.claude/harness.json` の `trace.enabled: true`、`.claude/hooks/trace.mjs` と登録 | 節目の出来事の記録 |
| `.claude/skills/harness-retro/SKILL.md` | 失敗から育てる、効かない部品を外す |

記録するのは、止められた操作、検査の合否、役の開始と終了だけ。コマンドの文字列やファイルの内容は記録しない。
設計への差し戻しと再試行の理由は hook からは観測できないので、役の報告とレシートに残る。
**代償**: 最も部品が多い。初回から入れても、振り返りの材料（失敗と教訓）がまだ無い。

## 標準と、上げ下げの目安

**標準は常に「日常の操作で止まらないようにする」（段階 3）**。入力によって変えない。これは、このプロジェクトに最適だという診断ではなく、どのプロジェクトにも共通の出発点である。
どの目安が当てはまるかを判断するのは利用者である。この Skill は、プロジェクト定義を見て「あなたの場合はこれが良い」のような個別の推奨をしない。

軽くしてよいのは、次が当てはまるとき。

- 作業が短く、成果物を目で見てすぐ確かめられる
- 失敗しても安く済む。外部への作用が無い
- 人が常に画面を見ている

重くした方がよいのは、次が当てはまるとき。

- 作業が複数のセッションにまたがる → 「セッションをまたいで引き継ぐ」まで
- 行動に現実の結果が伴う。完了を人の目で判定しにくい → 「終わったと言う前に検査を通す」まで
- 同じ失敗が繰り返し現れる。人のレビューが詰まりになっている → 「失敗を記録して、仕組みを育てる」まで

最後の段階は、失敗と教訓が溜まってから再実行で足すのが自然である。複雑さは、観測された失敗で獲得するもの。ただし利用者が最初から選ぶことは妨げない。
どの段階でも、メンバーと安全の下限は同じ。軽いから危険、ということにはならない。

## 利用者への見せ方

確認 1（仕組みをどこまで入れるか）で利用者に見せる文面の決まり。

1. **最初に、必ず入るものを具体的に言う**。メンバーの顔ぶれ（誰が何をするか）と、安全の決まり。ここは選択の対象ではないことも言う
2. **選ぶのは「仕組みをどこまで入れるか」だと言う**。メンバーは変わらないことも言う
3. **段階は、呼び名と、普段の使い方がどう変わるかで説明する**。上の表の文を、プロジェクトの言葉に置き換えて使う（「テストの実行」ではなく、そのプロジェクトのコマンドの名前で言えるなら、そう言う）
4. **番号や記号を出さない**。「L3」「レベル 5」「段階 4」のどれも出さない。選択肢のラベルも、呼び名で書く
5. 標準と、軽くする目安・重くする目安を添える。目安は一般論として示し、個別の診断にしない
6. 後から、この Skill の再実行で足したり外したりできることを言う

文面の例（プロジェクトに合わせて言い換える）。

```text
メンバーは次のとおり、必ず全員揃います。
  設計の相談相手（いま話しているこのセッション）／調査／テストを書く役／コードを書く役／
  コードレビュー／検証／セキュリティレビュー
テストを書く役とコードを書く役は別で、コードを書く役はテストを書き換えられません。
本番へのデプロイと DB のマイグレーションは、実行の前に必ずあなたの承認を求めます。DB の初期化は禁止です。

選んでいただくのは、その上にどこまで仕組みを入れるかです。下へ行くほど手厚く、上の行はすべて含みます。

  ・依頼を契約にしてから始める
      「〜を直して」と頼むと、作業の前に、何ができたら終わりかを短い文書にします。
  ・プロジェクトの地図を持たせる
      何がどこにあるか、どのコマンドを使うかを、最初から知っている状態にします。
  ・日常の操作で止まらないようにする（標準）
      pnpm のテストや依存の導入で、いちいち承認を求められなくなります。
  ・セッションをまたいで引き継ぐ
      決めたことと進み具合がファイルに残り、次の日はそこから始まります。
  ・終わったと言う前に検査を通す
      コードを書く役が「終わりました」と言う前に検査が自動で走り、通らなければ作業に戻されます。
      タスクごとに、何が確かめられて何が確かめられていないかの短い報告が残ります。
  ・失敗を記録して、仕組みを育てる
      止められた操作や検査の失敗を記録し、同じ失敗が続いたら仕組みの側を見直します。

試作なら軽く、日をまたぐ作業や、実際にお金やデータが動くものなら手厚く、が目安です。後から足すことも外すこともできます。
```

選択式の質問ツール（`AskUserQuestion`）は選択肢が4つまでなので、説明は先に本文で示し、質問の選択肢は呼び名で4つ出す。
「日常の操作で止まらないようにする（標準）」「セッションをまたいで引き継ぐ」「終わったと言う前に検査を通す」「失敗を記録して、仕組みを育てる（全部）」。
それより軽くしたい場合は自由入力で受ける、と本文に書いておく。

確認 1 だけでなく、Policy 表、ファイルの計画、最後の報告、根拠記録の概要でも、段階は呼び名で書く。
