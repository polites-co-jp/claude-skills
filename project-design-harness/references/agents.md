# 役の設計

どの役を作り、どこで分け、それぞれ何を書けて何を使えるかの決め方。
同じプロジェクト定義からは、同じ役の構成が出ることを目指す。分け方を、実行のたびの裁量にしない。

## 基本の役

| 役 | 実体 | 仕事 | 入るレベル |
|---|---|---|---|
| 主セッション | `CLAUDE.md` の役割定義 | ユーザーとの設計の対話、設計文書の更新、委任、結果の取りまとめ | 土台 |
| implementer（実装役） | subagent | コード・テスト・設定の変更 | 土台 |
| researcher（調査役） | subagent | ユーザーとの往復が要らない調査。読み取り専用 | 土台 |
| verifier（検証役） | subagent | 別の文脈で結果を壊しにいく。直さずに却下する | L5 |
| operator（運用役） | subagent | 外部作用・不可逆な操作の実行 | 条件つき（後述） |

このプロジェクト体系は設計書駆動で動く。初期の開発だけでなく、その後の変更や修正も、設計文書の更新から始める。
だから調査と設計の役は、最初の設計のための使い捨てではなく、常設のハーネスの一部である。

## 主セッションが設計の対話役である理由

subagent は `AskUserQuestion` を使えない。subagent 定義の `tools` に書いても外される。つまり、subagent にした役はユーザーに質問できない。

設計は、ユーザーとの往復そのものである。設計役を subagent にすると、分からない点は「質問の一覧を返す → 主セッションがユーザーに聞く → 答えを添えて委任し直す」という伝言になり、遅く、文脈も欠ける。
そこで、ユーザーと直接話している主セッションに設計の対話を受け持たせ、往復の要らない仕事（調査、実装、検証）だけを subagent に出す。

主セッションの役割は `CLAUDE.md` と プロジェクト skill で定義し、書き込み境界は hook で強制する。hook の入力に `agent_id` が無ければ主セッションである。

`--agent` や `agent` 設定で主セッション自体を特定の Agent にする方法は採らない。Agent のシステムプロンプトが Claude Code 既定のものを丸ごと置き換えるため、既定の振る舞いを失う。

## 基本の役を超えて分ける条件

**システムの構成要素の数は、分ける理由にならない**。Web・API・DB という構成だからといって、Agent は3つにならない。
分ける引き金は、次の2つだけ。

### 引き金 1: ツールチェーンが違う

プロジェクト定義の区分 C が、構成要素ごとに表を分けて書かれている場合（例: Swift のモバイルアプリと Go の Backend）。
使うコマンドも、検証の方法も、書ける場所も別物になる。1つの実装役に両方を持たせると、許可するコマンドが両方の和集合に広がり、片方の作業でもう片方を壊せてしまう。

→ 実装役を `implementer-<構成要素名>` に分ける。それぞれ、自分の構成要素の場所にだけ書ける。

同一のツールチェーンで書かれる Web と API（例: Next.js のフルスタック、同じ言語のモノレポ）は、実装役1つのままにする。

### 引き金 2: リスク階級が違う

[policy.md](policy.md) の手順 2〜3 で、**区分 D の行を根拠にした `ask` のコマンドが1つ以上できた**場合。
コードの編集は間違えても戻せるが、デプロイや課金やデータの削除は戻せない。結果の重さが違う操作を、同じ役に持たせない。

→ 運用役 `operator` を作る。

判定は機械的に行う。根拠が区分 E だけの行（`git push`、DB への直接接続）や、共通の行しか無いなら、運用役は作らない。その場合、`ask` の操作を実行できるのは主セッションだけになる。
区分 D に外部作用があっても、道具が未定でコマンドにできなかった場合も、運用役は作らない。担当するコマンドが無い役は、防ぐ失敗を持たない。道具が決まって再実行したときに作られる。

**実装役から、これらのコマンドを外す仕組み**。`harness.json` の `commands` で `ask` にしたコマンドは、承認を求められる役が `roles`（省略時は `main` と `operator`）に限られる。
実装役が実行しようとすると、承認の確認すら出ずに拒否され、「自分で実行せず、必要であることを報告せよ」と返る。
例外は、どのプロジェクトにも入れる共通の行のうち、未コミットの作業を消す操作（`git clean`、`git reset --hard`）。失敗した試みを捨てて戻すのは実装役の正当な回復手段なので、`roles` に、主セッション・運用役に加えて**コードを書く役をすべて**入れる。実装役が実行しようとすると、利用者に承認の確認が出る。
subagent 定義の `disallowedTools` は、この目的に使ってはいけない。`Bash(git push *)` のような指定を書くと、特定のコマンドではなく **Bash ツールが丸ごと外れ**、実装役がテストも実行できなくなる。

### 分けたら、理由を書く

分けるたびに、`docs/agent-architecture.md` の「基本の役を超えて分けた理由」に、引き金と**防ぐ失敗**を書く。
「役割が明確になるから」は理由にならない。「Backend の作業中に、モバイルのビルド設定を書き換える事故を防ぐ」のように、具体的な失敗で書く。
これ以上の分割（フロントエンド担当とバックエンド担当に分けたい、など）は、初回の生成ではしない。実際に失敗が観測されてから、振り返りを経て足す。

## 書き込み境界

`.claude/harness.json` の `roles` に、役ごとの規則を書く。規則は `+`（書ける）と `-`（書けない）で始まる glob の並びで、**最後に一致した規則が勝つ**。どれにも一致しなければ書けない。

| 役 | 規則 | 意味 |
|---|---|---|
| `main` | `["-**", "+docs/**"]` | `docs/` 以下だけに書ける |
| `implementer` | `["+**", "-docs/**", "+docs/harness/**"]` | 設計文書以外のすべてと、作業状態に書ける |
| `verifier` | `["-**"]` | どこにも書けない（L5 以上で足す） |
| `operator` | `["-**"]` | どこにも書けない（運用役を作るときに足す） |
| `implementer-<名前>` | `["-**", "+<その構成要素の場所>/**", "+docs/harness/**"]` | 自分の構成要素の場所と、作業状態に書ける |
| `researcher` | `["-**"]` | どこにも書けない |
| `*`（その他の Agent） | `["-**"]` | どこにも書けない |

- ハーネスのファイル（`protected`: 任意の深さの `.claude/` と `CLAUDE.md`、ルートの `.mcp.json`）は、規則より先に判定される。主セッションは承認、subagent は拒否。入れ子の `CLAUDE.md` も対象にしているのは、それも文脈に読み込まれるので、subagent が指示を仕込めてしまうため
- **検査されるのは、編集系のツールと、シェルのコマンドのうち書き込み先が引数から読めるもの**（リダイレクト、`tee`、`rm`、`mv`、`cp`、`touch`、`mkdir`、`sed -i`、PowerShell の `Set-Content` や `Remove-Item` など）。スクリプトを介した書き込みまでは追えない。だから利用者に「絶対に書けない」とは言わない
- プロジェクトの外のパス（一時ファイルなど）は、この hook では判定せず、Claude Code の通常の権限に任せる
- `*` を「書けない」にしているのは、組み込みの汎用 Agent などがコードを書くと、設計書駆動の流れを迂回できてしまうためである。利用者が他の Agent に書かせたい場合は、`roles` にその名前を足す

**区分 F に「設計文書の場所」の行がある場合**（既存プロジェクトが、`docs/` 以外に設計文書のフォルダを持っている）。その場所も、設計文書の置き場として扱う。
`main` の規則に `+<その場所>/**` を足し、コードを書く役の規則には `-<その場所>/**` を足す（例: `implementer` は `["+**", "-docs/**", "-design/**", "+docs/harness/**"]`）。
`main` の `onDeny` の文と、`CLAUDE.md` の生成ブロックの書ける場所の記述も、その場所を含めて書く。作業状態（`docs/harness/`）と根拠記録の置き場は、`docs/` のまま変えない。

実装役を分けた場合、共有の設定ファイル（リポジトリ直下の CI 設定など）は、どの実装役にも書けなくなる。必要なら、どれか1つの実装役の規則に `+<そのファイル>` を足し、根拠記録に理由を書く。

`onDeny` には、止められた役が次に何をすべきかを書く。「書けません」だけでは、Agent は回避策を探し始める。実装役なら「設計の誤りに気づいたのなら、直さずに報告して差し戻す」まで書く。
雛形に無い役（`verifier`、`operator`、分けた実装役）の `onDeny` は、その役の定義に書いた「役割の範囲」と同じ趣旨で、1〜2文で書く。

## 役ごとの道具

土台では粗く絞り、L3 で役に要る道具だけに絞る。

| 役 | 土台 | L3 以上 |
|---|---|---|
| implementer | 指定なし（すべて継承）。コマンドの制限は `harness.json` の `commands` で行う | `.mcp.json` を作った場合だけ、実装に使わない MCP サーバーを `disallowedTools` にサーバー単位（`mcp__<サーバー名>`）で入れる |
| researcher | `tools: Read, Grep, Glob, WebSearch, WebFetch` | 同じ |
| verifier | `tools: Read, Grep, Glob, Bash` | 同じ |
| operator | `tools: Read, Grep, Glob, Bash` | 同じ |

調査役に Bash を持たせないのは、Bash 経由の書き込みという抜け道をそもそも作らないため。調査に Bash は要らない。
検証役は検査を走らせるために Bash が要る。Bash 経由でファイルを書ける余地は残るが、検証役の定義で「直さない」理由を説明し、書き込みツールは持たせない。

`model` は `inherit` にする。役ごとにモデルを変えるのは費用の最適化であり、失敗を防ぐ部品ではない。必要になってから足す。

L6 では、各 subagent の frontmatter に `maxTurns: <数>` の行を足す（雛形には入っていない）。目安は実装役 80、検証役 40、調査役 40、運用役 30。1回の委任が際限なく続くのを止めるための予算で、届いたら途中経過が返る。

## 生成するときの決まり

- `name` は小文字とハイフン。`description` には、**いつ委任するか**と**委任のときに何を渡すか**を書く。主セッションはこの説明を見て委任先を選ぶ
- 本文（システムプロンプト）には、決まりだけでなく理由を書く。Claude Code 本体のシステムプロンプトは、subagent には渡らない。一方で `CLAUDE.md` は subagent にも読み込まれるので、`CLAUDE.md` の側で、主セッション向けの内容と全員向けの内容を書き分ける（生成ブロックの雛形は、そうなっている）
- 雛形の二重波括弧を、プロジェクトの内容で置き換える。置き換える内容が無い節は、節ごと削る。空の節や「該当なし」を残さない
- 生成した役は、必ず `harness.json` の `roles` と、`docs/agent-architecture.md` の「役の一覧」の両方に載せる。片方だけだと、書き込みがすべて拒否されるか、根拠が残らない
- L5 の完了ゲートの対象（`harness.json` の `verify.roles` と、`settings.json` の `SubagentStop` の `matcher`）には、コードを書く役の名前をすべて入れる。実装役を分けたのに `implementer` のままだと、ゲートが一度も動かない
