# 役の設計

どの役を作り、それぞれ何を書けて何を使えるかの決め方。
この Skill は、プロジェクトを進めるのに必要な役を一揃い作る。同じプロジェクト定義からは、同じ顔ぶれが出るようにする。

## 役の顔ぶれ

開発の工程が一通り揃うように作る。**役は、利用者がどの重さを選んでも、常に全部作る**。重さの選択が変えるのは仕組みだけで、メンバーではない。

| 役 | 実体 | 仕事 | 防ぐ失敗 |
|---|---|---|---|
| 主セッション | `CLAUDE.md` の役割定義 | ユーザーとの設計の対話、設計文書の更新、委任、結果の取りまとめ | 設計を経ずにコードが変わる |
| `researcher` | subagent | ユーザーとの往復が要らない調査。読み取り専用 | 調査の生データで、設計の対話の文脈が埋まる |
| `test-writer` | subagent | テストコード。契約の「完了の証拠」を、実装の前にテストにする | 通らないテストの方を書き換えて通す。実装の振る舞いを、そのまま正としてテストにする |
| `implementer` | subagent | 本体のコードと設定。先に書かれたテストを通す | 設計の対話と実装が同じ文脈に混ざり、設計が実装に引きずられる |
| `reviewer` | subagent | コードレビュー。設計文書との適合、読めること、直せること。読み取り専用 | 検査には通るが、設計文書とずれたコード、後で直せないコードが通る |
| `verifier` | subagent | 検証。契約に照らして、結果を壊しにいく。直さずに却下する | 検査を走らせずに「終わった」と言う。作った本人の確認で済ませる |
| `security-reviewer` | subagent | 秘密情報・個人情報・外部作用に関わる変更を、安全の観点だけで見る。読み取り専用 | 秘密情報や個人情報の扱いの誤りが、機能の検証をすり抜ける |
| `operator` | subagent | 外部作用・不可逆な操作の実行。どの操作も承認つき | 戻せない操作を、戻せる操作と同じ軽さで実行する |

下の2つ（`security-reviewer`、`operator`）は、条件を満たすときだけ作る。上の6つは常に作る。

防ぐ失敗を言えない役は作らない。役を足すときも、この列を埋められることが条件である。根拠記録の部品一覧には、役ごとにこの列を書く。

## 分ける軸は工程。構成要素ではない

**システムの構成要素の数は、分ける理由にならない**。Web・API・DB という構成だからといって、画面担当・API 担当・DB 担当の実装役を作らない。
同じツールチェーンの中で構成要素ごとに分けると、画面と API にまたがる変更のたびに役の往復が起き、新規プロジェクトでは、まだ無いフォルダに対して書き込み範囲を推測で決めることになる。

分ける軸は、開発の工程である。設計する、調べる、テストを書く、実装する、読んで確かめる、壊しにいく、外へ出す。
工程で分けることには、役ごとに目的を逆にできる、という意味がある。実装役は通そうとし、検証役は落とそうとする。テスト実装役は契約から書き、実装役はそのテストを通す。同じ役に両方をやらせると、この緊張が消える。

## 主セッションが設計の対話役である理由

subagent は `AskUserQuestion` を使えない。subagent 定義の `tools` に書いても外される。つまり、subagent にした役はユーザーに質問できない。

設計は、ユーザーとの往復そのものである。設計役を subagent にすると、分からない点は「質問の一覧を返す → 主セッションがユーザーに聞く → 答えを添えて委任し直す」という伝言になり、遅く、文脈も欠ける。
そこで、ユーザーと直接話している主セッションに設計の対話を受け持たせ、往復の要らない仕事だけを subagent に出す。

主セッションの役割は `CLAUDE.md` とプロジェクト skill で定義し、書き込み境界は hook で強制する。hook の入力に `agent_id` が無ければ主セッションである。

`--agent` や `agent` 設定で主セッション自体を特定の Agent にする方法は採らない。Agent のシステムプロンプトが Claude Code 既定のものを丸ごと置き換えるため、既定の振る舞いを失う。

## 条件つきで足す役

判定は機械的に行う。

| 役 | 作る条件 |
|---|---|
| `security-reviewer` | プロジェクト定義の区分 D の3項目（外部作用／不可逆・機微な操作／秘密情報・個人情報）のうち、1つでも `none` でないものがある |
| `operator` | [policy.md](policy.md) の手順 2〜3 で、**区分 D の行を根拠にした `ask` のコマンドが1つ以上できた** |

`operator` について。根拠が区分 E だけの行（`git push`、DB への直接接続）や、共通の行しか無いなら、作らない。その場合、`ask` の操作を実行できるのは主セッションだけになる。
区分 D に外部作用があっても、道具が未定でコマンドにできなかった場合も、作らない。担当するコマンドが無い役は、防ぐ失敗を持たない。道具が決まって再実行したときに作られる。

**コードを書く役から、承認つきのコマンドを外す仕組み**。`harness.json` の `commands` で `ask` にしたコマンドは、承認を求められる役が `roles`（省略時は `main` と `operator`）に限られる。
実装役が実行しようとすると、承認の確認すら出ずに拒否され、「自分で実行せず、必要であることを報告せよ」と返る。
例外は、どのプロジェクトにも入れる共通の行のうち、未コミットの作業を消す操作（`git clean`、`git reset --hard`）。失敗した試みを捨てて戻すのは、コードを書く役の正当な回復手段なので、`roles` に、主セッション・運用役に加えて**コード実装役とテスト実装役をすべて**入れる。
subagent 定義の `disallowedTools` は、この目的に使ってはいけない。`Bash(git push *)` のような指定を書くと、特定のコマンドではなく **Bash ツールが丸ごと外れ**、実装役がテストも実行できなくなる。

## ツールチェーンが複数あるとき

プロジェクト定義の区分 C が、構成要素ごとに表を分けて書かれている場合（例: Swift のモバイルアプリと Go の Backend）。
使うコマンドも、テストの書き方も、書ける場所も別物になる。1つの役に両方を持たせると、片方の作業でもう片方を壊せてしまう。

→ コード実装役とテスト実装役を、ツールチェーンごとに分ける。`implementer-<構成要素名>` と `test-writer-<構成要素名>`。それぞれ、自分の構成要素の場所にだけ書ける。
レビュー・検証・調査の役は分けない。読むだけの役は、分けても防げる失敗が増えない。

同一のツールチェーンで書かれる Web と API（例: Next.js のフルスタック、同じ言語のモノレポ）は、分けない。

## 作業の流れ: テストが先

`CLAUDE.md` の生成ブロックに、この順を書く。

```text
設計文書の更新（主セッション）
  → タスク契約（主セッション）
    → テスト（test-writer）       契約の「完了の証拠」をテストにする。この時点で落ちるのが正しい
      → 実装（implementer）       テストを通す。テストは書き換えられない
        → レビュー（reviewer、必要なら security-reviewer）
          → 検証（verifier）      契約に照らして壊しにいく
            → 変更レシート（主セッション）
```

- テストは、実装ではなく契約と設計文書から書かれる。実装役には「これを通せば終わり」という決定的な目標が渡る
- 実装役が、テストの方が誤っていると考えたら、書き換えずに差し戻す（最後のメッセージを `HANDBACK:` で始める）。主セッションが内容を確かめ、テスト実装役に戻す
- テストが要らない変更（文書だけ、コメントだけ）では、テストの段を省いてよい。省いたことと理由を、契約に書く
- **コミットは、検証が通ったあとに主セッションが行う**。subagent はコミットしない。実装役が先にコミットすると、レビュー役と検証役が変更の範囲（`git diff`）を見失う。push、プルリクエストの作成とマージは、承認つきの操作である（[policy.md](policy.md) の手順 4）。どのブランチに積むかは、プロジェクトの運用に従う。この Skill はブランチの運用を決めない
- 完了ゲート（終わる前の自動検査）の対象は、**コード実装役だけ**にする。テスト実装役が終わる時点では、テストは落ちているのが正しい。ゲートを掛けると、永久に終われない

## 流れの外にある仕事の持ち主

一揃いの役を作っても、どの役の定義にも書かれていない仕事が残ると、そこで流れが止まるか、主セッションが自分の文脈でやり始める。次の仕事は、新しい役を足さずに、既存の役に持たせる。雛形には、この分担が書いてある。

| 仕事 | 持ち主 | 理由 |
|---|---|---|
| コミット | 主セッション | 上のとおり。検証の後の1か所に寄せる |
| push、プルリクエスト、マージ | 主セッションか `operator`（承認つき） | 外部作用。マージは、push と同じ結果を別の経路で起こす |
| 不具合の再現と、原因の切り分け | `verifier`（コードを読むだけで足りるなら `researcher`） | 動かして確かめ、証拠だけを返し、直さない、という仕事が同じ。`researcher` は Bash を持たないので、再現できない。再現の手順が、契約の「完了の証拠」と、最初のテストになる |
| 設計文書のレビュー | `reviewer` | 設計文書は、主セッションが1人で書く。変更が大きいときだけ、実装の前に別の文脈の目を通す。毎回は通さない。小さな変更の往復が増えるだけになる |
| 実装の途中で要る、承認つきの操作（マイグレーションの生成など） | 実装役が `HANDBACK:` で返し、主セッションか `operator` が実行して、続きを実装役に委任し直す | 実装役は、承認を求めることができない。コマンドが生成するファイルは、コマンドの結果であって、運用役が書いたものではない（hook が見るのは、編集ツールと、書き込み先が引数に現れるコマンドだけ） |
| 設計文書の置き場の外にある文書（`README.md`、変更履歴） | `implementer` | 書き込み境界のとおり。主セッションには書けない |

## 書き込み境界

`.claude/harness.json` に書く。まず `pathSets` で「設計文書の置き場」と「テストの置き場」に名前を付け、`roles` の規則からその名前を参照する。
規則は `+`（書ける）と `-`（書けない）で始まる並びで、**最後に一致した規則が勝つ**。どれにも一致しなければ書けない。`@名前` は `pathSets` の一覧を指す。

| 役 | 規則 | 意味 |
|---|---|---|
| `main` | `["-**", "+@design"]` | 設計文書の置き場だけに書ける |
| `implementer` | `["+**", "-@design", "+docs/harness/**", "-@tests"]` | 設計文書とテストを除くすべてと、作業状態に書ける |
| `test-writer` | `["-**", "+@tests", "+docs/harness/**"]` | テストのファイルと、作業状態にだけ書ける |
| `implementer-<名前>` | `["-**", "+<その構成要素の場所>/**", "+docs/harness/**", "-@tests"]` | 自分の場所のうち、テスト以外 |
| `test-writer-<名前>` | `["-**", "+@tests-<名前>", "+docs/harness/**"]` | 自分の場所のテストだけ |
| `researcher`、`reviewer`、`verifier`、`security-reviewer`、`operator` | `["-**"]` | どこにも書けない |
| `*`（その他の Agent） | `["-**"]` | どこにも書けない |

ツールチェーンごとに分けたテスト実装役のために、`pathSets` に構成要素ごとのテストの置き場を足す。
例: `"tests-mobile": ["apps/mobile/**/*Tests/**", "apps/mobile/**/*Tests.swift"]`。`pathSets.tests` には、すべての構成要素のテストの置き場を入れておく（実装役がテストに書けないようにするため）。

**`pathSets.tests`（テストの置き場）の既定**は、`tests/**`、`test/**`、`e2e/**`、`**/__tests__/**`、`**/*.test.*`、`**/*.spec.*`、`**/*_test.*`、`**/test_*.*`。
決め方は、**既定を残して、足す**。既定の8個は消さない。下の表のうち、区分 C の言語の行にあって既定に無い形を足す。区分 F や既存のリポジトリに、別のテストの置き場があれば、それも足す。
その言語の慣習に無い形を残しておいても害は無いが、慣習にある形が抜けていると、実装役がテストを書き換えられてしまう。既定の形を削ってよいのは、それが本体のコードに当たっていると分かったときだけで、削った理由を根拠記録に書く。

| 言語 | テストの置き場の慣習 | 既定に足すもの |
|---|---|---|
| TypeScript / JavaScript | `**/*.test.*`、`**/*.spec.*`、`**/__tests__/**`、`tests/**`、`e2e/**` | なし |
| Python | `tests/**`、`**/test_*.py`、`**/*_test.py` | なし |
| Go | `**/*_test.go` | なし |
| Rust | `tests/**`（単体テストは本体と同じファイルに書くので、分けられない） | なし |
| Swift | `**/*Tests/**`、`**/*Tests.swift` | `**/*Tests/**`、`**/*Tests.swift` |
| C / C++ | `tests/**`、`test/**` | なし |

**既知の限界**。テストを本体と同じファイルに書く流儀の言語（Rust の単体テストなど）では、分けられるのは別ファイルのテストだけ。Policy 表の「仕組みでは止められないもの」に載せる。

**`pathSets.design`（設計文書の置き場）の既定**は `docs/**`。プロジェクト定義の区分 F に「設計文書の場所」の行がある場合（既存プロジェクトが、`docs/` 以外に設計文書のフォルダを持っている）、その場所を足す（`["docs/**", "design/**"]`）。
`main` の `onDeny` の文と、`CLAUDE.md` の生成ブロックの書ける場所の記述も、その場所を含めて書く。作業状態（`docs/harness/`）と根拠記録の置き場は、`docs/` のまま変えない。

その他の決まり。

- ハーネスのファイル（`protected`: 任意の深さの `.claude/` と `CLAUDE.md`、ルートの `.mcp.json`）は、規則より先に判定される。主セッションは承認、subagent は拒否。入れ子の `CLAUDE.md` も対象にしているのは、それも文脈に読み込まれるので、subagent が指示を仕込めてしまうため
- **検査されるのは、編集系のツールと、シェルのコマンドのうち書き込み先が引数から読めるもの**（リダイレクト、`tee`、`rm`、`mv`、`cp`、`touch`、`mkdir`、`sed -i`、PowerShell の `Set-Content` や `Remove-Item` など）。スクリプトを介した書き込みまでは追えない。だから利用者に「絶対に書けない」とは言わない
- プロジェクトの外のパス（一時ファイルなど）は、この hook では判定せず、Claude Code の通常の権限に任せる
- `*` を「書けない」にしているのは、組み込みの汎用 Agent などがコードを書くと、設計書駆動の流れを迂回できてしまうためである。利用者が他の Agent に書かせたい場合は、`roles` にその名前を足す
- テストランナーの設定ファイル（`vitest.config.ts` など）は、テストの置き場に含めない。設定は実装役の担当で、テスト実装役は、要る設定を報告に書く
- 役を分けた場合、共有の設定ファイル（リポジトリ直下の CI 設定など）は、どの実装役にも書けなくなる。必要なら、どれか1つの実装役の規則に `+<そのファイル>` を足し、根拠記録に理由を書く

`onDeny` には、止められた役が次に何をすべきかを書く。「書けません」だけでは、Agent は回避策を探し始める。実装役なら「テストが誤っていると考えたのなら、書き換えずに報告して差し戻す」まで書く。
雛形に無い役（`security-reviewer`、`operator`、分けた役）の `onDeny` は、その役の定義に書いた「役割の範囲」と同じ趣旨で、1〜2文で書く。

## 役ごとの道具

| 役 | `tools` |
|---|---|
| `implementer`、`test-writer` | 指定なし（すべて継承）。コマンドの制限は `harness.json` の `commands` で行う |
| `researcher` | `Read, Grep, Glob, WebSearch, WebFetch` |
| `reviewer`、`verifier`、`security-reviewer`、`operator` | `Read, Grep, Glob, Bash` |

- 調査役に Bash を持たせないのは、Bash 経由の書き込みという抜け道をそもそも作らないため。調査に Bash は要らない
- レビュー・検証の役は、変更の範囲を見る（`git diff`）、検査を走らせる、ために Bash が要る。書き込みは hook が止める
- `.mcp.json` を作った場合だけ、その役に要らない MCP サーバーを `disallowedTools` にサーバー単位（`mcp__<サーバー名>`）で入れる。コマンドの制限には使わない
- `model` は `inherit` にする。役ごとにモデルを変えるのは費用の最適化であり、失敗を防ぐ部品ではない。必要になってから足す

「失敗を記録して、仕組みを育てる」段階（6）では、各 subagent の frontmatter に `maxTurns: <数>` の行を足す（雛形には入っていない）。目安は、コード実装 80、テスト実装 60、レビュー・検証・セキュリティレビュー・調査 40、運用 30。1回の委任が際限なく続くのを止めるための予算で、届いたら途中経過が返る。

## 生成するときの決まり

- `name` は小文字とハイフン。`description` には、**いつ委任するか**と**委任のときに何を渡すか**を書く。主セッションはこの説明を見て委任先を選ぶ。雛形の内部事情（「条件を満たすときだけ作られる」など）を `description` に書かない
- 本文（システムプロンプト）には、決まりだけでなく理由を書く。Claude Code 本体のシステムプロンプトは、subagent には渡らない。一方で `CLAUDE.md` は subagent にも読み込まれるので、`CLAUDE.md` の側で、主セッション向けの内容と全員向けの内容を書き分ける（生成ブロックの雛形は、そうなっている）
- 雛形の二重波括弧を、プロジェクトの内容で置き換える。置き換える内容が無い節は、節ごと削る。空の節や「該当なし」を残さない
- 生成した役は、必ず `harness.json` の `roles`、`CLAUDE.md` の「メンバー」の表、`docs/agent-architecture.md` の「役の一覧」の3か所に載せる。抜けがあると、書き込みがすべて拒否されるか、主セッションが委任先を知らないか、根拠が残らない
- 完了ゲートの対象（`harness.json` の `verify.roles` と、`settings.json` の `SubagentStop` の `matcher`）には、**コード実装役の名前をすべて**入れる。テスト実装役は入れない。実装役を分けたのに `implementer` のままだと、ゲートが一度も動かない
