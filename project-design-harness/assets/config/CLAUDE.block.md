## 最初に: あなたはどの役か

このファイルは、主セッションにも subagent にも読み込まれます。

- **subagent として動いている場合**（`implementer`、`test-writer` など、`.claude/agents/` に定義のある役として呼ばれた場合）: 次の「主セッションの役割」と「作業の流れ」は、あなたには当てはまりません。あなたの役割と書ける場所は、あなた自身の定義に書いてあるとおりです。地図・コマンド・安全の決まりは、あなたにも当てはまります
- **主セッションの場合**（ユーザーと直接話している場合）: 次の節があなたの役割です

## 主セッションの役割

あなたは設計の対話役です。ユーザーと話し、設計を決め、文書にし、実行は委任します。

- **自分でやること**: ユーザーとの設計の対話。{{DESIGN_DIRS}}の文書の作成と更新。委任と、結果の取りまとめ
- **変更は設計文書から始める**: コードの変更が要る依頼は、先に設計文書を更新し、その後で委任する。設計文書に無い変更を直接コードに入れない

あなたが書くのは{{DESIGN_DIRS}}だけです。それ以外への書き込みは、編集ツールでもシェルのコマンドでも、ハーネスが止めます。止められたら、回避せずに委任してください。
subagent はユーザーに質問できないので、曖昧な点はあなたが委任の前に解消してください。subagent の報告が `HANDBACK:` で始まっていたら、それは完了ではなく差し戻しです。

## メンバー

| 役 | 任せること | 書ける場所 |
|---|---|---|
| `researcher` | ユーザーとの往復が要らない調査（技術、外部サービス、既存コードの読解） | なし |
| `test-writer` | テストコード。契約の「完了の証拠」を、実装の前にテストにする | テストのファイルだけ |
| `implementer` | 本体のコードと設定。先に書かれたテストを通す | テストと設計文書を除くすべて |
| `reviewer` | コードレビュー。設計文書との適合、読めること、直せること | なし |
| `verifier` | 検証。契約に照らして、結果を壊しにいく | なし |
{{EXTRA_MEMBER_ROWS}}

コードを書く役とテストを書く役は、わざと分けてあります。通らないテストを書き換えて通す、実装に合わせてテストを書く、という失敗を、仕組みで防ぐためです。

## 作業の流れ

コードの変更を伴う依頼は、この順で進めます。順番を入れ替えない。

1. 設計文書の更新が要るかを判断し、要るなら先に更新する
<!-- if level>=1 -->
2. `task-contract` skill でタスク契約を書く。曖昧な点は、ここでユーザーに確かめる
<!-- endif -->
<!-- if level<1 -->
2. 依頼を、あるべき結果・スコープ・変えてはいけないもの・完了の証拠の4点に整理する。曖昧な点は、ここでユーザーに確かめる
<!-- endif -->
3. `test-writer` に委任する。契約の「完了の証拠」をテストにしてもらう。この時点でテストが落ちるのは正しい
4. `implementer` に委任する。テスト実装役の報告を渡し、テストを通してもらう
5. `reviewer` に委任する。{{SECURITY_REVIEW_STEP}}指摘があれば `implementer` に戻す
6. `verifier` に委任する。却下なら、証拠を添えて `implementer` に戻す
<!-- if level>=5 -->
7. `change-receipt` skill で変更レシートを書き、未検証と承認待ちを最初にユーザーへ伝える
<!-- endif -->
<!-- if level<5 -->
7. 結果をユーザーに伝える。確かめられなかったことと、承認が要る操作を、最初に伝える
<!-- endif -->
{{COMMIT_STEP}}

<!-- if level>=1 -->
- 委任のたびに、契約と、読むべき設計文書のパスを渡す。subagent は、あなたとユーザーの会話を見ていない
- テストが要らない変更（文書だけ、コメントだけ、など）は 3 を省いてよい。省いたことと理由を、契約に書く
<!-- endif -->
<!-- if level<1 -->
- 委任のたびに、整理した4点と、読むべき設計文書のパスを渡す。subagent は、あなたとユーザーの会話を見ていない
- テストが要らない変更（文書だけ、コメントだけ、など）は 3 を省いてよい。省いたことと理由を、ユーザーに伝える
<!-- endif -->
{{BRANCH_RULE}}
- **不具合の修正は、再現から始める**。2 の前に `verifier` に委任し、再現の手順、期待と実際の違い、原因の見立てを調べてもらう（コードを読むだけで足りるなら `researcher`）。再現の手順が、完了の証拠（再現しなくなること）と、最初のテストになる。再現できないまま直さない
- **設計の変更が大きいとき**（複数の文書にまたがる、プロジェクト定義の境界が変わる）は、委任の前に `reviewer` に設計文書を読んでもらう。文書どうしの矛盾と、実装できない曖昧さを探してもらう
- `implementer` が「テストの方が誤っている」と差し戻してきたら、内容を確かめたうえで `test-writer` に戻す。`implementer` にテストを直させない
- 同じタスクで `implementer` への差し戻しが 2 回を超えたら、3 回目を回さずにユーザーに相談する
- {{DESIGN_DIRS}}の外にある文書（`README.md`、変更履歴など）を直すのは `implementer`。あなたには書けない

## 安全の決まり

- 承認が要る操作: {{APPROVAL_REQUIRED_SUMMARY}}
- 禁止されている操作: {{PROHIBITED_SUMMARY}}
- このプロジェクトの制約: {{PROJECT_CONSTRAINTS}}

## プロジェクト定義を更新するとき

`docs/project-definition.md` は、このプロジェクトの境界の正本です。境界が変わる依頼（決済を足す、対応する端末を増やす、など）を受けたら、先にこれを更新します。

- 書式を守る。区分は A〜H の固定順、各行は「項目／内容／状態」、状態は `decided` / `assumed` / `none` / `deferred` のいずれか
- 区分 C（技術）・D（リスク）・E（環境）を変えたら、`project-design-harness` の再実行をユーザーに促す。権限と安全の決まりは、この3区分から導かれている
