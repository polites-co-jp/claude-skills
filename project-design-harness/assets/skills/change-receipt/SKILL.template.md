# 変更レシート

長いやりとりの記録は、人には読み返せない。タスクの終わりに、小さなレシートにまとめる。
レシートは、Agent が言ったことの要約ではない。**仕組みが証明できることの要約**である。
人にとっては短時間で確認できる面になり、次のセッションにとっては信頼できる出発点になる。
最良の引き継ぎは「これが会話の記録です」ではなく、「これが状態と、証拠と、残っているリスクです」。

## 手順

1. 材料を揃える。タスク契約、実装役の報告、検証役の報告
2. `docs/harness/tasks/<タスクID>/receipt.md` に書く。雛形は同じフォルダの [receipt.template.md](receipt.template.md)
3. 契約の「完了の証拠」を1つずつ、「検証済み」か「未検証」に振り分ける。振り分けの根拠は報告に書かれた実行結果だけ。「たぶん大丈夫」は未検証
4. `docs/harness/state.md` の進捗を更新する。判断と教訓があれば、それも移す
5. ユーザーにはレシートの要点を伝える。未検証と承認待ちは、必ず最初に伝える

## 書き方の決まり

- **未検証を空欄にしない**。確かめられなかったことが本当に無ければ「なし」と書く。未検証の欄は、このレシートで最も読まれるべき場所である
- 検証役が却下した場合は、レシートを書かずに実装役へ差し戻す。同じタスクの差し戻しが 2 回に達したら、3 回目は行わず、その時点の状態をレシートに書いてユーザーに判断を仰ぐ
- 承認が要る操作を実行していない場合は、「承認待ち」に、実行するコマンドと対象の環境を書く
- 実装役が設計の誤りを報告していたら、「差し戻し」に書き、設計文書の更新を先に行う
