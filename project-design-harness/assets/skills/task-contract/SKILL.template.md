# タスク契約

「オンボーディングを改善して」は会話には十分でも、任せて実行させるには足りない。
契約が無いと、Agent は「次に何をしようか」と考え、もっともらしい作業を積み上げる。
契約があると、「どの操作が、約束した結果に環境を近づけるか」を考えられる。目指すものが、活動から検証された完了に変わる。

## 手順

1. 依頼から、下の5つの問いに答えを出す。答えが依頼と設計文書から読み取れないものは、推測で埋めずにユーザーに聞く。契約を書くのは主セッションの仕事で、主セッションだけがユーザーに質問できる
2. 設計文書の変更が要る依頼なら、先に設計文書を更新する。契約はその後に書く。このプロジェクトでは、変更は設計文書から始まる
3. `docs/harness/tasks/<タスクID>/contract.md` に書く。雛形は同じフォルダの [contract.template.md](contract.template.md)。タスクID は `YYYYMMDD-短い名前`（例: `20260920-coupon-duplicate`）
4. 契約のパスと、読むべき設計文書のパスを渡して、まずテスト実装役（`test-writer`）に委任する。契約の「完了の証拠」をテストにしてもらう。そのあとで、コード実装役（`implementer`）に委任する

## 5つの問い

| 問い | 書くこと | よくある失敗 |
|---|---|---|
| あるべき結果は何か | 終わったときに成り立っている状態。作業の内容ではない | 「〜を調査して改善する」のように、作業を書いてしまう |
| スコープの内側は何か | 触ってよい機能・場所 | 書かないので、ついでの変更が広がる |
| 変えてはいけないものは何か | 既存の振る舞い、公開している約束事、他の人が作業中の場所 | 「特になし」と書く。必ず何かある |
| 何が完了の証拠か | 環境を観測して確かめられること。通るべきテスト、出るべきイベント、再現しなくなる手順。テスト実装役は、ここに書かれたことをテストにする | 「動作確認する」のように、観測できない書き方をする |
| 承認が要る操作はどれか | この作業の中で発生しうる、外部作用・不可逆な操作 | プロジェクト共通の一覧を見ずに書く |

完了の証拠は、安く決定的に確かめられるものから並べる。構文、型、対象を絞ったテスト、結合テスト、目で見る確認、人の承認の順。
コンパイラやテストで答えが出ることを、読んで判断する項目にしない。

## 不具合の修正のとき

契約を書く前に、再現する。`verifier` に再現を委任し、返ってきた再現の手順を、そのまま「完了の証拠」に書く（この手順で再現しなくなること）。再現できていない不具合の契約は、完了を確かめようがない。

## 小さな依頼のとき

1行の修正にも契約は要るが、長く書く必要はない。5つの問いにそれぞれ1行で足りる。
契約を省いてよいのは、コードの変更を伴わない作業（設計文書の更新、調査）だけ。
