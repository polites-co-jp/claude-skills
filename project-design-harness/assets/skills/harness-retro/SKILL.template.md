# ハーネスの振り返り

失敗した成果物だけを直すと、その1回が助かる。失敗を許した仕組みを直すと、以後のすべての実行が助かる。
一方で、ハーネスは多ければ良いものではない。モデルも道具も良くなり、昔の対策がただの摩擦になる。
最良のハーネスは最大のものではなく、意図と証拠の間の溝を確実に埋める**最小**のものである。

この skill は2つのことをする。失敗からハーネスを育てること。効かなくなった部品を外すこと。

## 材料

- `docs/harness/state.md` の教訓
- `docs/harness/traces/` のトレース（止められた操作、検証の合否、役の開始と終了）
- `docs/harness/tasks/` のレシート（未検証、差し戻し、リスク）
- `docs/agent-architecture.md` の部品一覧（各部品が防いでいる失敗）

## 手順 1: 失敗を診断する

取り上げる失敗ごとに、次の8つを問う。当てはまったものが、直すべき場所を指している。

| 問い | 当てはまるなら、直す場所 |
|---|---|
| タスク契約が曖昧だったか | 契約の雛形、`task-contract` skill |
| 大事な文脈が見えていなかったか | `CLAUDE.md` の地図、`.claude/rules/` |
| 間違った道具が使えてしまったか | Agent の `tools`、permissions |
| 前提条件の確認が欠けていたか | hook、Agent の手順 |
| 結果を検証できなかったか | 検証コマンド、検証役の却下の基準 |
| 守るべき決まりが、指示文の中にしか無かったか | hook、permissions（指示文から仕組みへ移す） |
| 回復の仕方が大ざっぱすぎたか | 失敗の分類、再試行の上限 |
| トレースが足りなかったか | 記録する出来事 |

## 手順 2: 改善案を、できるだけ下の段に置く

同じ決まりでも、置く場所によって効き方が違う。繰り返し大事になる決まりは、下の段へ移す。

```text
説明（指示文に理由を書く）
  → チェックリスト
    → 雛形（書式で抜けを防ぐ）
      → 自動の検査（検証コマンドに足す）
        → 強制（hook や permissions で止める）
```

指示文は判断を説明するためのもの。変わらない決まりを守らせるのは、仕組みの仕事である。
ただし、1回起きただけの失敗に強制を足さない。複雑さは、観測された失敗で獲得するもの。

## 手順 3: 効いていない部品を探す

`docs/agent-architecture.md` の部品一覧を上から見て、部品ごとに5つを問う。

1. この部品は、どの失敗を防いでいるか
2. その失敗は、今も起きているか（トレースとレシートに現れているか）
3. この部品は、どれだけの遅さと複雑さを足しているか
4. 同じ結果を、今ならもっと単純に得られないか
5. 外したら、何が起きるか

1 に答えられない部品と、2 が長く「起きていない」部品は、外す候補にする。

## 手順 4: 数で確かめる

印象ではなく、数えられるものを数える。見るべきは Agent の活動量ではなく、人の注意あたりの、信頼できる成果である。

- 一度で合格したタスクの割合（レシートの検証役の判定）
- 検証が落ちた回数と、上限に達して人に渡った回数（トレースの `verify.fail`）
- 同じ理由で止められた操作の回数（トレースの `boundary.deny`。多ければ、境界か役割の説明が合っていない）
- 「未検証」を残したまま閉じたタスクの数
- 人が手で直したタスクの数

## 手順 5: 提案し、承認を得てから適用する

改善案を、次の形でユーザーに見せる。

```text
変更:      何を足す／変える／外すか（ファイル名まで）
理由:      どの失敗の、どの診断から来たか
置く段:    説明／チェックリスト／雛形／自動の検査／強制
代償:      足される遅さ・複雑さ、または外すことで戻ってくるリスク
```

承認されたら、主セッションが適用する。ハーネスのファイル（`.claude/`、`CLAUDE.md`、`.mcp.json`）への書き込みには、そのつど承認の確認が出る。これは正常な動作で、Agent が自分の権限を黙って広げないための関門である。
適用したら、`docs/agent-architecture.md` の部品一覧と変更履歴を更新する。部品一覧と実体がずれると、次の振り返りができなくなる。

安全の下限（外部作用は承認、不可逆・機微な操作は禁止、ハーネス自身への書き込みは承認）は、この skill では緩めない。
緩める必要があるなら、プロジェクト定義の区分 D（リスク）を先に更新し、`project-design-harness` を再実行する。
